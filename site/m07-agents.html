With -p, Claude Code becomes a command you can call from a script. It reads stdin, writes JSON, returns an exit code and can be capped by turns and dollars. Subagents run the same agent loop inside a session, each with its own context window, and hand back only a short report. This module covers both, so you can call an agent from a scheduled job, a pipeline or a wrapper script and trust what comes back.

After this module you can

  • Run claude -p with piped input and schema-checked JSON output, and branch on its exit code, is_error, subtype and permission_denials.
  • Grant exactly the tools an unattended run needs with --allowedTools and --disallowedTools, and explain why bypass mode is a last resort.
  • Resume, continue and fork a headless session, and predict what each resumed turn costs from its cache state.
  • Isolate a run from your personal settings, hooks and MCP servers, and pick the right credential for an unattended job on a plan or on an API key.
  • Define a subagent with its own tools and model, and prove from the stream which model did which work and how many tokens stayed out of the main context.
  • Write a subagent brief and a return contract that make the report usable without a follow-up.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The outputs shown were recorded on 2.1.322 with a subscription login.
  • Windows PowerShell 5.1 or PowerShell 7. All lab commands work in 5.1.
  • A lab folder, {{LAB}}/m7. The labs create everything inside it. Lab 4 runs Sonnet for its main session. Everything else runs on Haiku, and the whole module costs a few cents at API prices.

If you skipped the prerequisites

Every request sends the whole conversation to the model: tool definitions, then the system prompt, then the messages. That stack is the context, and on current models it can hold up to a million tokens. Each request is metered in four token types: input (fresh prompt tokens after the last cache point), cache write (prompt tokens stored for reuse, 1.25x the input price for a 5-minute lifetime or 2x for one hour), cache read (stored tokens served again, 0.1x or less) and output (5x input on every current model). The cache is a prefix cache: change anything early in the stack and everything after it is written again. A hit refreshes the lifetime for free. Per million tokens, input and output, Haiku 5.5 costs $0.10 and $0.50 (up to 100k-token prompts), Sonnet 5.5 $2 and $10, Opus 5.5 $4 and $20. On a subscription plan you pay a flat fee and usage draws down a 5-hour window and weekly limits. On an API key you pay per token. The usage block of a result reports the four types as input_tokens, cache_creation_input_tokens, cache_read_input_tokens and output_tokens.

The mechanism

claude -p "prompt" (long form --print) runs the same agent loop as an interactive session: it calls tools, reads results and calls the model again until the model stops. Then it prints and exits. Nobody is there to answer a question or approve a tool call, and that one fact shapes everything in this module.

Input comes from the prompt argument and from stdin. Piped text is added to the prompt, so Get-Content build.log | claude -p "explain the root cause" needs no file permission at all. Piped stdin is capped at 10 MB. Above that the run exits non-zero with an error, so write big inputs to a file and name the path in the prompt instead.

Caps: turns, dollars, model

--max-turns N limits agentic turns. There is no limit by default. With a cap of 1 on a task that needed two file reads, the run stopped with num_turns 2, subtype error_max_turns and exit 1. The count includes the turn that hit the cap, so read num_turns as "turns used", not as a hard ceiling.

--max-budget-usd X stops the run once the estimated spend reaches X. The check runs between requests, so a request that is already in flight finishes. With a cap of $0.0001 the run spent $0.0011 on its first request and then stopped with error_max_budget_usd. Spend from subagents counts toward the cap. Once the cap is reached, spawning another subagent fails with Budget limit reached. On a subscription the dollar figure is notional, but the cap still stops the run, so it works as a runaway guard on either kind of account.

--fallback-model sonnet,haiku names models to switch to when the primary is overloaded or unavailable, tried in order. It is not a cost control, and it is not restored when you resume a session.

Timeouts you add yourself

The CLI reference lists no wall-clock limit for a run. What exists is narrower. A foreground shell command inside the run times out after BASH_DEFAULT_TIMEOUT_MS (120,000 ms by default, and the model may ask for up to BASH_MAX_TIMEOUT_MS, 600,000 ms by default). After the last turn, a run that is still waiting on background work stops it after 10 idle minutes (CLAUDE_CODE_PRINT_BG_WAIT_CEILING_MS). For a hard limit on the whole run, start claude as a child process, wait with a timeout and kill the process tree. Lab 5 builds such a wrapper.

Give every unattended run three caps (turns, dollars and seconds) and check three things after it: exit code, is_error and permission_denials.

What a headless run may do by default

In an interactive session, a tool call that needs approval stops and asks you. In -p nobody can answer. Since v2.1.302, a -p run with no permission mode set starts in Manual mode (config value default), and a call that needs approval is denied unless something approves it: an allow rule, a PermissionRequest hook or --permission-prompt-tool. Reads inside the working directory and the read-only command set need no approval, so they run anyway.

The denial does not end the run. The model is told the call was refused, it carries on, and the run finishes normally. This is the run from lab 2 with no permission flags, asked to write two files:

exit 0  subtype success  is_error False  turns 3

  {"tool_name": "Write", "tool_use_id": "toolu_01ASki...",
   "tool_input": {"file_path": "...\\lab2\\out\\a.txt", "content": "one"}},
  {"tool_name": "Write", "tool_use_id": "toolu_011SNS...",
   "tool_input": {"file_path": "...\\lab2\\keep\\b.txt", "content": "two"}}

Granting tools: rules

--allowedTools takes permission rules. A rule is a tool name, optionally with a specifier in parentheses. You can pass several, space- or comma-separated.

RuleMatches
ReadEvery call to the tool.
Bash(git diff *)Commands that start with git diff. The space before * matters: Bash(git diff*) also matches git diff-index.
PowerShell(Get-ChildItem *)Same shape for the PowerShell tool. Aliases are canonicalized, so ls, dir and gci match too.
Edit(out/**)File writes and edits under out/ relative to the working directory. The Write tool is checked against Edit rules, so write Edit(...), not Write(...).
mcp__acme__deployOne MCP tool. MCP tools are named mcp__<server>__<tool>.

--disallowedTools takes deny rules, and they act in two ways. A bare tool name removes the tool from the model's context entirely: with --disallowedTools "Write", the tools list in the stream's init event no longer contains Write. A scoped rule such as Edit(keep/**) leaves the tool available and denies only matching calls. Deny rules win in every mode, including bypass. To shrink the built-in tool set instead, use --tools "Read,Grep". --tools does not touch MCP tools. Deny those with --disallowedTools "mcp__*".

Permission modes

--permission-modeRuns without askingHeadless use
default (alias manual)Reads only. Anything else needs a rule, or is denied.The baseline. Add an exact allowlist.
dontAskWorking-directory reads and pre-approved tools. Everything that would prompt is denied.Locked-down CI with an exact allowlist.
acceptEditsReads, file edits and common filesystem commands (mkdir, touch, mv, cp) in the working directory.Jobs that edit files but run no other commands.
planReads. Edits stay blocked in -p.Read-only analysis.
autoMost actions, each reviewed by a classifier.Long tasks where you cannot list the commands in advance. Only some models support it.
bypassPermissionsEverything. Allow rules have no effect.Only inside a disposable container or VM.

--permission-prompts none (v2.1.259 and later) tells the run that nobody can answer. Requests that nothing else resolves are denied, the model is told not to retry them, and tools that need a person, such as AskUserQuestion, are removed. In stream-json, each denial also appears as a permission_denied system event as it happens.

Why bypass mode is a last resort

bypassPermissions (same as --dangerously-skip-permissions) skips the safety checks too, including writes to protected paths. A model that misreads a task, or that reads a hostile instruction in a file or web page, acts with your full rights. The documentation pairs this mode with one setup only: a container, VM or sandbox runtime. Even there, deny rules still apply and a short list of actions is still refused. For almost every scripted job, dontAsk or the default mode with an exact --allowedTools list does the same work, and its denials show up in the result where you can see them.

Without --bare or the isolation flags, a -p run in a folder runs the hooks in that folder's .claude/settings.json and starts the servers in its .mcp.json. It shows no trust dialog first. Running claude -p inside a repository you did not write means running that repository's hooks. Lesson 5 shows how to keep them out.
Start from nothing and allow the narrowest rule that lets the job finish. Prefer a scoped rule, such as Bash(npm test) or Edit(out/**), to a bare tool name.

Schema-checked output

Asking for JSON in the prompt gets you JSON most of the time. --json-schema '<schema>' together with --output-format json gets you an object that has been checked against your schema, in the structured_output field of the result. Under the hood the run gives the model a StructuredOutput tool whose input is your schema. In a stream of the lab 1 run, the model first answered with a Markdown table. Claude Code then sent [structured-output-enforce] You MUST call the StructuredOutput tool, and the model called the tool. That took 3 turns for a task that needs 1 without a schema, so give schema runs some turn headroom.

  • If the run ends without valid output, for example because the model declined, the result has no structured_output field. Test for it before you use it.
  • An invalid schema stops the run before it starts, with Error: --json-schema is not a valid JSON Schema on stderr and exit 1.
  • The format keyword ("format":"email") is accepted as an annotation and not enforced.
  • The result field also holds the same object as text.
Windows PowerShell 5.1 strips embedded double quotes when it passes an argument to a native program. --json-schema $schema arrives as {type:object,...} and fails with Error: --json-schema is not valid JSON: JSON Parse error: Expected '}'. Pass ($schema -replace '"','\"'), or put the JSON in a file where the flag accepts a path (--settings, and --agents with -p).

Per-request usage from the stream

Each assistant event carries the usage of the API request that produced it. When the model calls several tools in one response, those events share the same message.id and the same usage, so count each id once. The sum of input, cache write and cache read on a request is the context size the model saw. That makes the stream the place to watch a context grow. The documentation warns that per-step output_tokens is a placeholder, so take output totals from the result.

$seen = @{}
claude -p "..." --output-format stream-json --verbose | ForEach-Object {
  $e = $_ | ConvertFrom-Json
  if ($e.type -eq 'assistant' -and -not $seen.ContainsKey($e.message.id)) {
    $seen[$e.message.id] = 1
    $u = $e.message.usage
    '{0,-8} {1,-18} context {2,7}' -f $(if ($e.parent_tool_use_id) {'sub'} else {'main'}), $e.message.model, ($u.input_tokens + $u.cache_creation_input_tokens + $u.cache_read_input_tokens)
  }
  if ($e.type -eq 'result') { 'done: {0} cost {1:N4}' -f $e.subtype, $e.total_cost_usd }
}
Read structured_output for data, init to check what loaded, assistant usage for growth, and the result line for totals.

Every run is a session

Each -p run gets a session_id, and its conversation is saved as a JSONL transcript. By default that is ~/.claude/projects/<project>/<session-id>.jsonl, where <project> is the working directory path with every non-alphanumeric character replaced by -. Subagent transcripts sit beside it in <session-id>/subagents/agent-<agentId>.jsonl. CLAUDE_CONFIG_DIR moves the whole tree.

FlagEffect
--session-id <uuid>Start a new session with an ID you chose, so a script knows it before the run.
--resume <id|name|path>Continue a specific session. The ID is found in any project on the machine. An absolute path to a .jsonl transcript also works.
--continueContinue the most recent conversation in the current directory. With -p it includes earlier -p sessions. Interactive --continue skips them.
--fork-sessionWith --resume or --continue: load the history but write to a new session ID, leaving the original untouched.
--no-session-persistenceSave nothing. Resuming that ID later fails with No conversation found with session ID: ... and exit 1.
-n <name>Give the session a display name you can resume by.

What a resumed turn costs

Resuming sends the whole conversation again. Whatever part of the prefix is unchanged and still within its cache lifetime is a cache read. Everything else is written again at the cache write rate. The lifetime depends on the account. On a subscription within plan usage, the main conversation gets a one-hour cache. On an API key, usage credits or a cloud provider it gets five minutes, unless you set CLAUDE_CODE_PROMPT_CACHE_TTL=1h or the promptCacheTtl setting. These are three Haiku runs from lab 3, each a few seconds after the last:

TurnHowinputcache writecache readoutputtotal_cost_usd
1--session-id27,22214,51740.00159
2--resume24,10017,67850.00259
3--continue26921,75370.00283

Two things to read from this. First, usage covers only that run, while total_cost_usd is the running total for the conversation. Turn 3 itself cost about $0.00024, not $0.00283. To get a per-run cost, subtract the previous total. Second, the first resume wrote about 4,100 tokens again, but the second wrote only 69. Budget for one partial rewrite on the first resume, then near-pure cache reads while the cache is warm. --max-budget-usd counts only the new run's spend, not the restored total.

What resuming does not bring back

  • Launch flags: --mcp-config, --settings, --plugin-dir, --fallback-model and --add-dir must be passed again. Settings files are re-read.
  • Permission mode: a -p resume starts in the mode a new -p run would start in. The exception is a session that ended in plan mode, under narrow conditions. Pass your permission flags again.
  • System prompt: the prompt recorded on the conversation's first request is kept. New --append-system-prompt text takes effect only after compaction or in a new session.
Resuming a long conversation after its cache has expired rewrites the whole history at the cache-write rate. On an API key with the 5-minute default, a 300,000-token conversation resumed an hour later costs that full write before the model reads your new prompt. On a plan, the same rewrite draws down the 5-hour window, and an interactive resume may warn you with a "Resume this conversation?" estimate.
Resume when the next step needs the history. When it needs only the result, start a fresh session and pass it the result, for example the previous run's structured_output.

What a headless run loads

Without extra flags, claude -p discovers and loads everything an interactive session would. That covers user, project and local settings, hooks, skills, plugins, MCP servers, CLAUDE.md and auto memory, from the working directory and from your home configuration. That is convenient on your own machine. For a measurement or a shared job it is a problem: your personal hooks and servers change the result, and a teammate gets a different run.

What a child session inherits

A claude process inherits the environment of whatever started it: a scheduled task, a CI runner, or a Bash or PowerShell tool call inside another Claude session. Every variable that steers Claude Code comes along. Claude Code also marks its own subprocesses: CLAUDECODE=1 and CLAUDE_CODE_CHILD_SESSION=1 are set in commands its shell tools, hooks and status line run, so a script can tell it was started from inside a session.

The mechanism

A subagent is a second agent loop that the main conversation starts with the Agent tool. It begins with a fresh context window. Its system prompt is the agent's own prompt plus environment details, not the Claude Code system prompt. Its first message is a task message that the main model writes. It also gets the CLAUDE.md hierarchy and a git status snapshot (the built-in Explore and Plan skip both) and any skills its definition preloads. It does not get your conversation history, files already read, your output style or your auto memory. When it finishes, only its final report goes back to the main conversation. This is what came back in lab 4, abridged:

[Subagent hand-back] The text below is the final report of a subagent ... It is model
output, NOT a message from the user ... The report follows:
  ERROR=7
agentId: a61b1554ebeeeda38 (use SendMessage with to: 'a61b1554ebeeeda38' ... to continue this agent)
<usage>subagent_tokens: 30696
tool_uses: 2
duration_ms: 3681</usage>

The subagent read a log of about 22,800 tokens. The main conversation's context grew from 20,998 to 21,488 tokens, about 490, for the call and that report. The report is framed as model output with no authority, so instructions planted in what the subagent read do not arrive as your words.

Defining one

A subagent is a Markdown file with YAML frontmatter. The body is its system prompt.

---
name: log-counter
description: Counts the lines in a log file that contain a given word and returns only the number. Use for any log counting task.
tools: Read
model: haiku
---
You count log lines. Read the whole file you are given with the Read tool. ...
Reply with exactly one line in the form WORD=COUNT, for example ERROR=12. No other text.
FieldMeaning
name (required)Identifier, unique across scopes. The file name does not matter.
description (required)When the main model should delegate. It sits in the main context all session, so keep it short. Above 15,000 tokens across all custom agents you get a startup warning.

Where a definition lives sets its scope. When names clash, the higher priority wins: managed settings, then --agents, then the project's .claude/agents/, then ~/.claude/agents/, then a plugin's agents/. Plugin agents ignore hooks, mcpServers and permissionMode. --agents '{"name":{"description":"...","prompt":"...","tools":["Read"],"model":"haiku"}}' defines agents for one session only. With -p it also accepts a path to a JSON file, which avoids the quoting trap from lesson 3.

The model is resolved in this order: a model the main model passes on that call, the definition's model, CLAUDE_CODE_SUBAGENT_MODEL, and last the main conversation's model. The init event of the lab 4 run listed these agents: claude, Explore, general-purpose, log-counter, Plan, statusline-setup. Explore is read-only and built for search. Plan does research in plan mode. general-purpose has every tool and is the default when a call names no type. In -p, CLAUDE_AGENT_SDK_DISABLE_BUILTIN_AGENTS=1 removes the built-ins.

Parallelism and nesting

  • Up to 20 subagents run at once by default (CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS). The 21st spawn fails with Concurrent subagent limit reached. There is no limit on the total over a session.
  • Subagents can spawn their own, up to three layers below the main conversation (CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, where 1 turns nesting off).
  • A subagent spawned from the main conversation starts in the background by default. In -p the main model may wait for it, and the run waits for background subagents before it prints the result. Background subagents get a smaller tool set.
  • subagent_stats in the result counts spawned, completed, failed and refused (depth, concurrency, budget) subagents, by type.

What a subagent costs

A subagent has its own prefix: its own system prompt and tool set. Its first request cannot read the parent's cache, so it pays cache write on its own prefix and on everything it reads. Its requests use the 5-minute cache lifetime even on a subscription. The parent's cache is not affected. Lab 4 has the numbers (Sonnet main, Haiku subagent, second run with the main cache warm):

Writing the brief and the return contract

The subagent knows only its system prompt, CLAUDE.md and the task message. Anything else it has to rediscover at its own cost, or guess. A good brief states:

  1. Goal, in one sentence, and why it matters to the caller.
  2. Inputs, by exact path, ID or command, plus what is already known, so the subagent does not repeat it.
  3. Scope and limits: what not to touch, what not to run, and when to stop and report instead of pressing on.
  4. Done-test: the observable condition that means finished.
  5. Return contract: the exact shape of the report, such as a fixed first line (STATUS: done|blocked|partial), the answer in a set format, evidence as paths or line numbers, and a length cap.

Put the stable parts (role, method, report format) in the definition's body, where they cost nothing until the agent runs. Put the per-task parts in the brief. Then check the report against something cheap. In lab 4, PowerShell counts the same lines in one command.

A report is a claim, not a result. A subagent that runs into its maxTurns, a denial or an API error can still return confident text. Ask for evidence the caller can check, and check it.
Delegate when the work is big and the answer is small. Brief it like a contractor who has never seen the repository, and specify the report format before the work starts.

Build a wrapper that runs claude -p with a turn cap, a budget cap and a wall-clock timeout, and returns a distinct exit code for each kind of failure. Then point it at a real chore of your own. You end up with a script your scheduler can trust.

  1. Create the wrapper. It passes stdin from a file, kills the process tree on timeout and checks exit code, is_error and permission_denials.

    param(
  [Parameter(Mandatory)][string]$InputFile,
  [Parameter(Mandatory)][string]$Prompt,
  [int]$MaxTurns = 3,
  [double]$BudgetUsd = 0.05,
  [int]$TimeoutSec = 120,
  [string]$Tools = 'Read'
)
$outFile = Join-Path $PWD 'chore-result.json'
$errFile = Join-Path $PWD 'chore-stderr.txt'
$argLine = "-p `"$Prompt`" --model haiku --setting-sources project --strict-mcp-config --max-turns $MaxTurns --max-budget-usd $BudgetUsd --allowedTools `"$Tools`" --output-format json"
$p = Start-Process -FilePath claude -ArgumentList $argLine -RedirectStandardInput $InputFile -RedirectStandardOutput $outFile -RedirectStandardError $errFile -NoNewWindow -PassThru
$null = $p.Handle
if (-not $p.WaitForExit($TimeoutSec * 1000)) {
  & taskkill.exe /T /F /PID $p.Id | Out-Null
  $null = $p.WaitForExit(5000)
  Write-Output "TIMEOUT after $TimeoutSec s, process gone: $($p.HasExited)"
  exit 3
}
$p.WaitForExit()
$code = $p.ExitCode
$r = $null
try { $r = Get-Content $outFile -Raw | ConvertFrom-Json } catch { }
if ($null -eq $r) { Write-Output "NO RESULT (exit $code): $(Get-Content $errFile -Raw)"; exit 4 }
Write-Output ("exit {0}  subtype {1}  is_error {2}  turns {3}  cost {4:N4}  denials {5}" -f $code, $r.subtype, $r.is_error, $r.num_turns, $r.total_cost_usd, $r.permission_denials.Count)
if ($code -ne 0 -or $r.is_error) { exit 2 }
if ($r.permission_denials.Count -gt 0) { Write-Output 'DENIED tool calls, see chore-result.json'; exit 5 }
Write-Output $r.result
exit 0
