An agent session spends money in four token types, and in a long session most of the bill is cache traffic, not the words you see. This module shows where a real session's money went, then works through five levers: model tier, cache discipline, context hygiene, output and turns, and work that need not be interactive. Every lever comes with a before-and-after measurement, because a saving you have not measured is a guess.

After this module you can

  • Break a session's cost down by the four token types from its JSON result and name the type that dominates.
  • Route a task to a model tier and back the downgrade with a correctness check on known answers.
  • Find and remove a prefix change that defeats the cache, and decide between resuming a cold session and starting fresh.
  • Shrink the always-loaded context (instruction files, tool output) and show the saving across a multi-turn session.
  • Cap output, turns and spend, and say which of these caps can overshoot.
  • Say what "cost" means on a subscription plan and on an API key, and work out which one is cheaper for your own usage.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The figures here come from version 2.1.322.
  • Windows PowerShell 5.1 or later.
  • About $0.20 of API usage at list price for all five labs (on a plan, a small share of one 5-hour window). Lab 1 runs one prompt on Opus and Sonnet; the rest run on Haiku or Sonnet.
  • The modules "Tokens and their price" and "Telemetry" help but are not required; the recap below covers what this one uses.

If you skipped the prerequisites

Every request is metered in four token types: input (prompt tokens after the last cache breakpoint), output (everything the model writes, thinking included, priced at 5x input on every current model), cache write (prompt tokens stored for reuse, 1.25x input for a 5-minute lifetime or 2x for 1 hour) and cache read (prompt tokens served from that store, 0.1x input, or 0.05x on Opus 5.5 and Sonnet 5.5). The cache matches the start of the request exactly, in the order tools, system prompt, messages, so a change early in the prompt forces everything after it to be written again. An agent re-sends its whole conversation on every turn, which is why a long session is mostly cache reads by volume.

claude -p "…" --output-format json returns total_cost_usd, a usage block with the four counts (input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens) and a modelUsage block per model. total_cost_usd is a client-side estimate at list price; on a subscription nothing is charged per token and the figure is notional. Across a fleet the same numbers arrive as the OpenTelemetry metrics claude_code.token.usage (with type = input, output, cacheRead, cacheCreation) and claude_code.cost.usage, and in a live session as /usage.

Three things stand out. Cache reads are 97% of the tokens but 38% of the cost. Cache writes are 3% of the tokens but nearly half the cost, because every new token is written once at twice the input price. Output, the only part you read, is 13%. Without caching the same prompts would have been billed as plain input: 887,604 tokens at $2 plus the output, about $1.81, so caching saved 88%. With an API key, Claude Code writes the main conversation at the 5-minute rate by default ($2.50 per million), which would have made this run about $0.18.

The same token counts on the other tiers, as arithmetic (a different model would take a slightly different path): Haiku 5.5 about $0.016, Opus 5.5 about $0.45, exactly twice Sonnet because every Opus 5.5 rate is twice the Sonnet 5.5 rate.

In an agent session, cache writes and cache reads are the bill. Output matters less than it feels, and plain input hardly matters at all.

Cache read is the quiet one. A turn at 400,000 tokens of context re-reads 400,000 tokens on every tool call, so a one-line question late in a long session costs as much as hundreds of lines of output. Reads scale with context size times request count, which is roughly quadratic in session length.

Model it before you change it

The session cost model below takes turns, context size, model, cache on or off, and cold restarts. Use it to see which lever matters for the session you have before you change anything. Start with the run above: 26 turns, an average context of about 33,000 tokens (860,391 reads divided by 26 requests), Sonnet 5.5, cache on, no cold restarts. Then double the turns and watch the read cost grow faster than the turn count.

The method: measure, change one lever, measure again

  1. Baseline. Run the job as it is with --output-format json and keep the result file. Record the four counts and total_cost_usd.
  2. Quality bar. Write down what a correct result is before you touch anything: known answers, a test that passes, a diff that must be empty.
  3. One lever. Change one thing. Two changes at once tell you nothing about either.
  4. Same state. Run the after case from the same cache state as the before case. A cold first run against a warm second run shows a saving that is only the cache.
  5. Measure and check. Record the counts, the cost and the quality check. Report the saving as a percentage, with the check result next to it.
The cache outlives your experiment. Run the same command twice within the cache lifetime and the second run is cheaper even though nothing changed. Lab 4 shows this: the same comparison gave a 67% saving cold and a 44% saving when repeated warm.

--fallback-model is not a cost lever. It switches models only when the primary fails with an overload or availability error, never on billing or rate-limit errors, and only for the current turn. It belongs in unattended jobs so they finish, not as a way to run cheaper.

The quality check that goes with a downgrade

A cheaper tier that is wrong 10% of the time is not cheaper once you count the rework. Before you move a recurring job down a tier:

  • Collect 10 to 20 real inputs with known good outputs (from the current tier, checked by a person).
  • Run the cheaper tier on all of them and score each output pass or fail against a fixed rule: exact match, a parse, a test.
  • Set the bar before you look: for example, no more than one failure in 20, and none on the cases that matter most.
  • Keep the scoring script. Run it again whenever the model alias moves to a new version.

The module "Evals and A/B testing" covers paired scoring and when a difference is real.

Downgrade with a scored sample, never by feel. If you cannot write the check, the task is not a good candidate for the cheap tier.
Each model has its own cache. A /model switch mid-session, a skill whose model: differs from the session's, a fallback, or opusplan toggling between plan mode and execution all make the next request re-read the whole conversation uncached. Pick the tier at the start of the session, or route the cheap work to a subagent with its own model.

Keep the prefix stable

The cache matches the start of the request byte for byte. Claude Code orders each request so that what rarely changes comes first: the system prompt with tool definitions, then project context (CLAUDE.md, memory), then the conversation. A change in a layer forces a rewrite of that layer and everything after it. A change at the end costs only the new part.

Lab 3 measures the most common self-inflicted break: a timestamp in the system prompt. Three runs with a fixed --append-system-prompt, then three with the current time in it, all on Haiku:

run       in   cw    cr out crShare    usd
---       --   --    -- --- -------    ---
stable-1   2 7222 14526   4 67%     0.0016
stable-2   2 4531 17213   4 79%     0.0011
stable-3   2    0 21744   4 100%    0.0002
stamped-1  2 7244 14526   4 67%     0.0016
stamped-2  2 7244 14526   4 67%     0.0016
stamped-3  2 7244 14526   4 67%     0.0016

The stable prompt reached a full cache hit by the third run. The stamped prompt rewrote about 7,200 tokens on every run, forever; only the tool definitions (the 14,526 read tokens, which come before the system prompt) stayed cached. Over three runs the stable version cost 40% less; at steady state, one run costs 88% less. On a job that runs every few minutes, that is the whole difference.

For scripted jobs, two more prefix inputs are easy to miss. The conversation opens with the working directory and a git status snapshot, so sessions in different folders never share a cache, and sequential runs in a repo share the context layer only while the branch and recent commits are the same. A different prompt text also writes part of the first message again: in lab 2, each new question on a warm cache wrote about 4,500 tokens, while lab 3's identical prompt wrote none. For a fleet of identical jobs, --exclude-dynamic-system-prompt-sections moves the per-machine sections out of the system prompt into the first user message, which improves reuse across machines and users. The CLI help on 2.1.322 lists those sections as cwd, env info, memory paths and git status; the docs page describes them as per-user context such as the auto memory location.

Lifetime: 5 minutes or 1 hour

A cache entry expires after a period with no hits, and each hit resets the timer for free. Claude Code chooses the lifetime per request:

RequestsSubscription, within plan usageAPI key, usage credits, cloud provider
Main conversation (interactive turns and -p runs)1 hour (write at 2x input)5 minutes (write at 1.25x)
Subagents, compaction, titles, forks5 minutes, except some helper requests5 minutes

Override with the promptCacheTtl setting or CLAUDE_CODE_PROMPT_CACHE_TTL (5m or 1h) for the main conversation, and subagentPromptCacheTtl or CLAUDE_CODE_SUBAGENT_PROMPT_CACHE_TTL for the rest. FORCE_PROMPT_CACHING_5M=1 wins over everything. Read usage.cache_creation in a JSON result to see which lifetime your writes got: every lab run in this module on a plan showed ephemeral_1h_input_tokens only.

The trade is simple arithmetic. Every token is written at least once. With a 1-hour lifetime you pay 2x instead of 1.25x on each write, 0.75x extra. With a 5-minute lifetime, one gap between 5 and 60 minutes forces a rewrite of the whole context at 1.25x. So:

One break between 5 and 60 minutes in a session pays for the 1-hour write price. Work in unbroken bursts and the 5-minute lifetime is about 37% cheaper on writes.

Do not let sessions go cold and then resume them

Resuming a session (--resume, --continue, /resume) re-sends the whole conversation. If the cache has expired, the first turn writes all of it at the write price. A 300,000-token Sonnet session resumed cold costs $0.75 for that first request at the 5-minute rate, or $1.20 at the 1-hour rate, before it does any work. Compacting a cold session is no better: the summary request reads the whole history uncached too.

Lab 3 models a 60-turn Sonnet session that starts at 20,000 tokens and grows 2,500 tokens a turn:

Two cold restarts add a third to a half to the session. A fresh session is cheaper than a cold resume whenever the history is not worth its rewrite: a new session costs its fixed overhead (about 22,000 tokens of system prompt and tools in these labs, most of it already cached) plus a short brief, against the whole context at the write price.

Idle is not free. A session-scoped scheduled task (/loop), a message from another session, or a goal check-in starts a new turn on an idle session and sends the whole context each time. If the cache has expired by then, each of those turns is a cold rewrite.

Why context size is the multiplier

Every request re-reads the whole context. Cache reads are cheap per token, but a context twice as large costs twice as much on every turn and every tool call, and a larger context also means a larger rewrite on every cache miss. Context hygiene is the lever that compounds.

Trimming at the source

Lab 5 runs the same recurring job two ways. Before: the agent reads a 1,500-line log with the Read tool and reports the hosts with errors. After: PowerShell keeps only the 12 ERROR lines and pipes them in. Both answers were correct; the trimmed run cost 78% less ($0.0013 against $0.0059).

Select-String -Path app.log -Pattern ' ERROR ' | ForEach-Object Line | claude -p "These are the ERROR lines from app.log. List the hosts, comma-separated, sorted, nothing else." --model haiku --output-format json

Inside a session, the same idea is a PreToolUse hook that rewrites a test or log command to keep only the lines that matter (the docs' example keeps the last 100 lines of a test run), or a skill that tells Claude where things are so it does not explore.

The cheapest token is the one that never enters the context. Filter first, then ask.
Compaction is not free hygiene. On a cold cache the summary request reads the whole history at the uncached rate. Compact at a natural break while the session is warm, and use /clear when you do not need continuity at all.

Lever 4: ask for less

Output is the most expensive token type per token, 5x input on every model, and thinking counts as output. In a long agent session it is a modest share of the bill (13% in lesson 1), but in short, chat-like runs it dominates the part you control. Lab 2 asks Sonnet the same question with and without a length cap, from a warm cache:

run        in   cw    cr out    usd chars
---        --   --    -- ---    --- -----
open        2 4524 16392 907 0.0288  2516
capped      2 4539 16392 174 0.0215   543
capped-low  2 4040 16891 165 0.0195   523

"At most three sentences, no headings, no lists" cut output tokens by 81% and the run's cost by 25%. The cost saving is smaller than the token saving because in a one-shot run the cache write of the prompt is the larger part. The capped answer was complete. --effort low on top changed little here (165 output tokens against 174), because a three-sentence answer needs little reasoning; effort matters on multi-step work where the model would otherwise think at length.

A budget cap is checked after a request, not before it. With --max-budget-usd 0.001 the lab 2 run still spent $0.026 on its first request, then stopped with subtype error_max_budget_usd, is_error true and exit code 1. Set the cap well above one request's cost and treat it as a runaway stop, not a precise limit.

Fewer turns also means fewer re-reads. Specific prompts ("add input validation to the login function in auth.ts") avoid broad scanning, and plan mode on a complex task avoids paying for a wrong implementation and its rework.

Lever 5: work that need not be interactive

Much of what agents do does not need an answer now: nightly reports, bulk classification, documentation passes, log summaries.

For batches longer than 5 minutes the API docs suggest the 1-hour cache lifetime for shared context, because requests in a batch can be processed far apart. The batch discount and cache pricing multiply: a cache read in a batch is half the already reduced read price.

If nobody reads the answer for an hour, it should not be priced as if they were waiting for it.

Overage

At a plan limit you can wait for the reset, upgrade, or turn on usage credits (Settings > Usage, or /usage-credits from a subscription login), which bill at standard API rates against a monthly spend limit you set. While on credits, Claude Code drops the main conversation to the 5-minute cache lifetime. The monthly API credits included with Max and Ultra cannot be used in Claude Code. On Team and Enterprise an admin turns credits on and sets the limits.

An ANTHROPIC_API_KEY in the environment wins over a subscription login, and with -p the key is always used when present. A scheduled job that inherits the variable bills the API while you believe it runs on your plan. Check apiKeySource in the stream-json init line: it is none on a subscription login.

  4. Compute the same session turn by turn at list price, for both cache lifetimes. A cold restart at turns 20 and 40 writes the whole context again.

    function Get-SessionCost([int]$Turns, [int]$Start, [int]$Grow, [int]$Out, [double]$Write, [double]$Read, [double]$OutP, [int[]]$Cold) {
  $usd = 0.0
  for ($k = 1; $k -le $Turns; $k++) {
    $ctx = $Start + ($k - 1) * $Grow
    if ($k -eq 1 -or $Cold -contains $k) { $usd += $ctx * $Write } else { $usd += ($ctx - $Grow) * $Read + $Grow * $Write }
    $usd += $Out * $OutP
  }
  $usd / 1e6
}
$p = @{ Turns = 60; Start = 20000; Grow = 2500; Out = 400; Read = 0.10; OutP = 10 }
foreach ($w in @(@{n='5-minute write (API key)'; v=2.50}, @{n='1-hour write (plan default)'; v=4.00})) {
  $warm = Get-SessionCost @p -Write $w.v -Cold @()
  $cold = Get-SessionCost @p -Write $w.v -Cold @(20, 40)
  "{0}: warm {1:N2}  two cold restarts {2:N2}  extra {3:P0}" -f $w.n, $warm, $cold, (($cold - $warm) / $warm)
}

    Expected: 5-minute write (API key): warm 1.20 two cold restarts 1.64 extra 36% and 1-hour write (plan default): warm 1.46 two cold restarts 2.16 extra 48%. With no cache at all the same session would cost about $11.49.
