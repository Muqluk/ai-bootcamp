A model knows what was in its training data and what is in front of it right now, and nothing else. Every technique in this module is a way to choose the model, or to put the right text in front of it. Know the four ways to give a model knowledge it lacks, and you can tell a retrieval problem from a model problem before you spend money on either.

After this module you can

  • Pick a model tier and an effort level for a task, and say what each costs per million tokens.
  • Choose between prompt and context, retrieval, tools and MCP, and training, for a given knowledge gap.
  • Describe the stages of a retrieval pipeline (ingestion, chunking, embedding, search, prompt) and where each one fails.
  • Measure retrieval separately from answering, with a hit rate you compute without calling a model.
  • Decide when to send a whole document and when to retrieve from it.
  • Make a model cite its sources and say "not in the documents" instead of guessing.
  • Explain training, fine-tuning and distillation, and what is and is not documented for Claude.

Effort and thinking

Current models use adaptive thinking: the model decides how much to reason before answering. Thinking is always on for Opus 5.5 and Fable 5.2. Thinking tokens are billed as output tokens, so more thinking costs more. The older budget_tokens setting returns a 400 error on current models; you control the amount with the effort parameter instead.

Effort levelsDefault
low, medium, high, xhigh, maxhigh on Fable 5.2 and Sonnet 5.5; medium on Opus 5.5 and Haiku 5.5

In Claude Code the /model command and the --model flag take aliases: default, best, opus, sonnet, haiku, fable, sonnet[1m] and opusplan. On a subscription plan the model you pick changes how fast the 5-hour window and weekly limits drain. With an API key it changes the bill per token directly.

Where models are served

The same model family is served from the Claude API and from three cloud platforms, each with its own documentation page: Amazon Bedrock, Google Cloud (Claude Models on Google Cloud) and Microsoft Foundry. Choose by where your identity, billing and data-residency rules already live. Features and limits can differ by platform, so check the platform's page before assuming a feature from the API page exists there. The Batch API, available on the Claude API, takes 50 percent off for asynchronous work: most batches finish under an hour, they expire at 24 hours and results are kept for 29 days.

Deprecations and cutoffs

A model moves through Active, Legacy, Deprecated and Retired. Publicly released models get at least 60 days' notice before retirement, and requests to a retired model fail. Every model ID is a pinned snapshot, including dateless IDs from 4.6 onward, so a pinned ID does not change behaviour under you; it does stop working on its retirement date. The docs list the current models as retiring no sooner than: Fable 5.2 on 2027-11-09, Opus 5.5 on 2027-09-22, Sonnet 5.5 on 2027-09-28, Haiku 5.5 on 2027-10-07.

The knowledge cutoff is the date after which the model knows nothing. Ask about a library released after Jun 2026 and the model will either say it does not know or invent an answer. That is the first reason the rest of this module exists.

A bigger tier is not automatically more correct. In the first lab a mid-tier model got a counting question wrong that the cheapest tier got right, and the top tier answered correctly but ignored the requested format.

The gap

When an answer is wrong, one of two things is true. The model reasoned badly from the facts it had, or it lacked the facts. Only the second is a knowledge problem. The facts can be missing because they postdate the cutoff, because they are private (your runbooks, your tickets), or because they change faster than anyone retrains a model (today's alert state). Each way of closing the gap changes where the facts come from.

Way 1: prompt and context

You paste the facts into the prompt, or load them into the session (a memory file, an attached document). The model sees them verbatim on every request. This is the simplest way and the most accurate for small amounts of text, because nothing is lost in between. Its limits are the context window, the cost of resending the text each turn (prompt caching reduces that cost), and your effort in choosing what to include.

Way 2: retrieval (RAG)

Retrieval-augmented generation keeps the documents outside the model. For each question, a search step picks the few relevant pieces, and only those go into the prompt. Use it when the corpus is too large or too changeable to include whole. The price is a pipeline you must build and measure: if search misses the right passage, the model never sees it and cannot answer.

Way 3: tools and MCP as retrieval

Instead of you running search, the model asks for it. You give it a tool (read a file, grep, query a ticket system) and it decides what to fetch. Tool use distinguishes client tools, which run in your code, from server tools, which Anthropic runs. The Model Context Protocol (MCP) is an open standard for exposing tools and data to a model through a common connector. This is how Claude Code finds facts in a repository: it searches and reads on demand rather than embedding the repo first. It handles live data well, and the model can refine its own search when the first attempt fails.

Way 4: training and fine-tuning

Changing the model's weights so the knowledge or behaviour is built in. It is the heaviest way, slowest to change and hardest to correct. Lesson 6 covers what the terms mean and what the docs say about it.

Retrieval is not a way to make a weak model smart. It supplies facts. If the task needs judgment the model cannot do, better context will not fix it; a higher tier or effort level might.

The pipeline

A retrieval system has two phases. Ingestion runs ahead of time and builds the index. Query time runs per question.

  1. Ingest: read the source files and extract text. Keep the source name and location with every piece.
  2. Chunk: cut the text into pieces small enough to retrieve precisely and large enough to make sense alone.
  3. Index: store each chunk for search, either by its words, by an embedding, or both.
  4. Search: score the chunks against the question and take the top few.
  5. Prompt: place the chunks in the request with their sources and instructions about how to use them.

Chunking

Chunk size is the first tuning knob. Tiny chunks (a sentence) match precisely but lose the surrounding facts: the sentence "restore within 4 hours" is useless without knowing which system it describes. Huge chunks (a whole document) always contain the answer but add noise, cost more and push the real passage into a crowd. A paragraph or a section, with the title carried along, is the usual start. The chunking lab in this module measures all three sizes on the same questions.

Embeddings

An embedding is a list of numbers representing the meaning of a piece of text. Texts with similar meaning get nearby vectors, so you can search by closeness rather than by shared words. Anthropic's embeddings page states that Anthropic does not offer its own embedding model, and points to Voyage AI. Its page lists the voyage-4 family (voyage-4-large, voyage-4, voyage-4-lite), voyage-code-4 for code, and contextualized chunk embeddings (voyage-context-4), which encode each chunk with awareness of its document. It also says to assess several embedding vendors.

Production systems often run both and merge the results. Keyword scoring needs no model and no service, which makes it a good first baseline.

Evaluate retrieval on its own

A wrong answer has two possible causes: search did not surface the passage, or the model misread it. Separate them. Write a set of questions with a known gold string that must appear in the answer. For each question, run only the search step and check whether any of the top results contains the gold string. The fraction of questions where it does is the hit rate. It costs no tokens. Then run the model and score answers. If hit rate is low, fix chunking and search. If hit rate is high and answers are wrong, fix the prompt or the tier.

Prompt caching with retrieval

Retrieved chunks change per question, so they cannot be cached across questions, but everything stable can: the instructions, the output format, any fixed reference document. Put stable content first and the retrieved chunks after it. Cached reads are billed at a fraction of normal input: on Haiku 5.5 up to 100k tokens, input is $0.10 per MTok and cache read is $0.01; on Sonnet 5.5 input is $2 and cache read is $0.10. The minimum cacheable prompt is 512 tokens on those models, and the default lifetime is 5 minutes, refreshed on each use (a 1-hour lifetime costs extra). Shorter prompts are processed without caching and no error is returned; check cache_read_input_tokens in the usage fields.

Measure hit rate before you measure answers. It is free, fast and it points at the stage that is broken.
A chunk that cuts a table or a numbered procedure in half retrieves well and answers badly. Split on structure, not on character count.

Just send it all

Current models take 1M tokens of context. For a single manual or a set of runbooks that fits, sending everything is often the better design: no index, no chunking, no search misses, and the model can cross-reference between sections. The cost is paid in tokens on every request, and in attention: the models handle long inputs well but not perfectly, and answer quality can drop when the relevant passage is buried in a large amount of unrelated text.

If the same large document is asked about many times, prompt caching makes the whole-document design much cheaper: the first request writes the cache and later ones read it at the discounted rate, as long as they arrive within the cache lifetime.

Prompting for long inputs

Anthropic's prompting guidance for 20k-token and larger inputs: put long documents at the top of the prompt and the question after them (queries at the end improved quality by up to 30 percent in their tests), and wrap each document in <document> tags with <source> and <document_content> subtags so the model can tell them apart and name them.

Images and PDFs

Models accept images and PDF pages as input alongside text. A single request can carry up to 600 images or PDF pages (100 for models with a 200k-token window), and large files may reach request size limits before the token limit. Pages cost tokens like any other input, so a 300-page PDF is not free. Ingestion for retrieval has an extra concern: scanned or image-only PDFs have no text layer, so a text extractor returns nothing. Either extract with a model that reads the page image, or send the PDF to the model directly.

The Files API

Uploading the same file with every request wastes bandwidth. The Files API stores a file once and returns a file_id that you reference in document, image or container_upload blocks. It is out of beta and needs no beta header. Files are retained until you delete them or they expire. Whether a given file type works depends on the model; the images are supported on all current models, and PDFs and other types have their own pages.

If it fits and you will ask many questions, put it in context and cache it. Reach for retrieval when it does not fit or when most of it is noise for each question.
Counting characters is not counting tokens. A corpus that "feels small" can exceed the window once tables and code are tokenized. Check the size before choosing the design.

Why models answer anyway

A model generates plausible text. Given a question and no relevant passage, the default is a plausible answer, not silence. Anthropic's hallucination page calls the result text that is factually incorrect or inconsistent with the given context. Grounding is the practice of tying every claim to text you supplied, and making the absence of that text an acceptable answer.

The unanswerable question

Every retrieval test set needs questions whose answer is not in the documents. The right behaviour is a fixed refusal string your code can check. If the instructions say "if the passages do not contain the answer, reply exactly NOT IN DOCUMENTS", you can count refusals mechanically, and a model that fills the gap from memory fails the check. Include at least one such question per test set; a system that has never been asked one has an unknown false-answer rate.

Citations in the API

The citations feature returns structured references to the source text rather than relying on the model to format them. Plain text and PDF documents are chunked into sentences for citation. If you chunk yourself, use custom content documents; to cite retrieved chunks, put each one in a plain text document so sentences within it can be cited. Text quoted in a citation (cited_text) does not count toward output tokens. Search result blocks (search_result) give retrieval citations with a source and title, whether the results come from a tool result or from the user message. The docs note that prompts demanding JSON-only output may yield few citations.

In Claude Code and headless runs without the API features, the same effect comes from the prompt: number the chunks, require a bracketed chunk number after every claim, and check mechanically that each cited number exists in what you supplied.

Give the model an exit, then test the exit. An unanswerable question in the test set is how you learn the exit works.
A citation proves the model pointed at a passage, not that the passage supports the claim. Spot-check by reading the cited text.

The terms

TermIn general
PretrainingLearning from a very large text corpus; builds the base model and sets the knowledge cutoff
Post-trainingFurther training on instructions and human or automated feedback to make the model helpful and safe
Fine-tuningContinuing training of an existing model on a smaller, task-specific dataset, changing its weights
DistillationTraining a smaller model to imitate the outputs of a larger one, to get most of the quality at lower cost
Embedding modelA model trained to turn text into vectors; separate from the chat model

Fine-tuning is usually discussed for changing style, format or narrow behaviour at scale, not for adding facts: facts you want updated or removed are far easier to change in a document than in weights. Distillation is a cost play when one task runs millions of times.

What the Claude docs say

Anthropic's current documentation does not document fine-tuning Claude.

What you will actually use

The first three ways. Choose a tier and effort level, put stable knowledge in context and cache it, retrieve when the corpus is big, and give the model tools or MCP servers for live data. Nobody in this course trains a model, and the work that decides success is the same in every case: a test set with known answers, a score you compute, and a change you keep only if the score rises.

Measure before you build. A retrieval pipeline or a tier change that you cannot score is a guess.

It still passes --setting-sources project and --strict-mcp-config, which keep your personal settings, hooks and MCP servers out of the measurement. --tools "" removes tools so the model answers from its own reasoning, and --max-turns 1 caps it at one turn.

$q = 'Reply with only a number. How many of these words are palindromes: level, rotor, banana, civic, kayak, apple, noon, radar, window'
$rows = foreach ($m in 'haiku', 'sonnet', 'opus') {
  $raw = claude -p $q --model $m --setting-sources project --strict-mcp-config --tools "" --max-turns 1 --output-format json

    model   = $id

    cost    = [math]::Round($j.total_cost_usd, 4)
    seconds = [math]::Round($j.duration_ms / 1000, 1)
    out_tok = $j.usage.output_tokens
  }
}
$rows | Format-Table -AutoSize

Self-check

Which tier would you pick for this task, and why? Haiku: it was correct at the lowest cost, in a task with a mechanical check. Why was Opus marked wrong although its content was right?   1. Create the script with the chunk store and the scorer. Each chunk has an id; the score is the number of distinct non-stopword terms shared with the question.

  @{ id = 'rb-06'; text = 'Monitoring runbook. Alerts for web-01 go to the ops channel. Silences last at most 4 hours.' },

$stop = 'the','a','an','of','to','is','at','in','on','and','for','by','are','after','before','what','when','who','does','do','how','which','it','be','than','or'
function Tok($s) { ($s.ToLower() -split '[^a-z0-9\-:]+') | Where-Object { $_ -and ($stop -notcontains $_) } | Select-Object -Unique }
function Get-Top($q, $k) {
  $qt = Tok $q
  $chunks | ForEach-Object {
    $ct = Tok $_.text
    [pscustomobject]@{ id = $_.id; score = @($qt | Where-Object { $ct -contains $_ }).Count; text = $_.text }
  } | Sort-Object score -Descending | Select-Object -First $k | Where-Object { $_.score -gt 0 }
}

  $raw = claude -p $prompt --model haiku --setting-sources project --strict-mcp-config --tools "" --max-turns 1 --output-format json

Self-check

Why did question 3 still retrieve a chunk? Keyword overlap scores shared words, not meaning, so any chunk sharing one term ranks above zero. Retrieval cannot tell "related" from "answers it"; the refusal came from the instruction to the model, not from the retriever.

What would you add so an unanswerable question is caught before the model call? A minimum score threshold, for example require at least 2 shared terms. The cost is missing short questions that legitimately match on one term.

What does the chunk id buy you? Every claim in the answer can be checked against one named chunk, and a missing or wrong id is a visible failure.

$stop = 'the','a','an','of','to','is','at','in','on','and','for','by','are','after','before','what','when','who','does','do','how','which','it','be','than','or','each','every'
function Tok($s) { ($s.ToLower() -split '[^a-z0-9\-:]+') | Where-Object { $_ -and ($stop -notcontains $_) } | Select-Object -Unique }
$text = $paras -join ' '
function Window($t, $size, $step) { for ($i = 0; $i -lt $t.Length; $i += $step) { $t.Substring($i, [math]::Min($size, $t.Length - $i)) } }
$sets = @(
  @{ name = 'fixed40-nooverlap'; chunks = @(Window $text 40 40) },
  @{ name = 'fixed40-overlap20'; chunks = @(Window $text 40 20) },
  @{ name = 'by-paragraph';      chunks = $paras }
)

  2. Define six questions, each with the exact string that must appear in a retrieved chunk for the retrieval to count as a hit, and a ranker that scores chunks by shared terms.

    $qs = @(
  @{ q = 'When does the nightly backup of web-01 start?'; gold = '02:30' },
  @{ q = 'How many days do audit logs stay on vault-02?'; gold = '365 days' },
  @{ q = 'Who approves requests to join the admin group?'; gold = 'security lead' },
  @{ q = 'What is the longest an alert silence can last?'; gold = 'at most 4 hours' },
  @{ q = 'On which day does the cert-renew job run?'; gold = 'day 60' },
  @{ q = 'In which order do servers reboot during the patch window?'; gold = 'web-01, web-02, db-01' }
)
function Rank($q, $chunks) {
  $qt = Tok $q; $i = 0
  $chunks | ForEach-Object { $ct = Tok $_; $i++; [pscustomobject]@{ n = $i; score = @($qt | Where-Object { $ct -contains $_ }).Count; text = $_ } } | Sort-Object @{e='score';Descending=$true}, n
}

  3. Compute hit@1 (the answer string is in the top chunk) and hit@3 (it is in one of the top three) for each chunking.

    foreach ($set in $sets) {
  $h1 = 0; $h3 = 0
  foreach ($x in $qs) {
    $r = @(Rank $x.q $set.chunks)
    $rank = 0; for ($k = 0; $k -lt $r.Count; $k++) { if ($r[$k].text.Contains($x.gold)) { $rank = $k + 1; break } }
    if ($rank -eq 1) { $h1++ }
    if ($rank -ge 1 -and $rank -le 3) { $h3++ }
  }
  $avg = [math]::Round((($set.chunks | ForEach-Object { $_.Length }) | Measure-Object -Average).Average)
  Write-Output ("{0}: chunks={1} avg_chars={2} hit@1={3}/6 hit@3={4}/6" -f $set.name, $set.chunks.Count, $avg, $h1, $h3)
}

    Expected: three lines:

    fixed40-nooverlap: chunks=26 avg_chars=40 hit@1=3/6 hit@3=3/6
fixed40-overlap20: chunks=52 avg_chars=40 hit@1=0/6 hit@3=4/6
by-paragraph: chunks=8 avg_chars=129 hit@1=6/6 hit@3=6/6
Self-check

Why did the fixed windows without overlap hit only 3 of 6? A 40-character window boundary can cut straight through an answer string such as at most 4 hours, so no single chunk contains the whole answer. Count the misses in your own run and check which strings were split.

Why did overlap raise hit@3 but drop hit@1 to 0? Overlap lets a window contain the whole string, so the answer reaches the top three more often, but neighbouring overlapping windows share words and tie on score, so the top-ranked window is often a fragment next to the answer rather than the one that holds it.

What does by-paragraph cost? Each chunk is about three times longer (129 characters against 40), so every retrieved chunk adds more input tokens. Hit rate and context cost move in opposite directions.

Why score with a known answer string instead of asking a model? It is free, repeatable and does not depend on the model's phrasing, so you can compare chunkings in seconds.

You take one knowledge need of your own, fill in a decision table for the four options, and run one measurement for the option you chose, so the choice rests on a number. The worked example below runs as written.

  1. Describe the need in five lines: what the model must know, how big that knowledge is, how often it changes, how often it is asked, and whether the answer must be exact. The example need is a three-line fact about log retention.

  2. Measure the baseline (no knowledge) and the chosen option (the facts in the prompt) with one tiny Haiku run each, then write the decision table. A rule of thumb for filling it in: small and stable goes in context; large, stable and many documents goes to retrieval; live or changing data goes behind a tool; common knowledge needs none of them.

    $q = 'How many days are audit logs kept on the acme platform? Reply with only the number, or UNKNOWN if you cannot tell.'
function Run($prompt) {
  $j = (claude -p $prompt --model haiku --setting-sources project --strict-mcp-config --tools "" --max-turns 1 --output-format json) | ConvertFrom-Json
  $inTok = $j.usage.input_tokens + $j.usage.cache_creation_input_tokens + $j.usage.cache_read_input_tokens
  [pscustomobject]@{ answer = $j.result.Trim(); input_tokens = $inTok; cost = [math]::Round($j.total_cost_usd, 5) }
}
$none = Run $q
$ctx = Run ("Facts:`n" + (Get-Content -Raw .\facts.md) + "`n`n" + $q)
$rows = @(
  [pscustomobject]@{ option = 'none';      verdict = 'rejected'; why = 'answer is UNKNOWN or a guess'; measured_answer = $none.answer; input_tokens = $none.input_tokens; correct = ($none.answer -eq '365') }
  [pscustomobject]@{ option = 'context';   verdict = 'CHOSEN';   why = '3 lines, rarely changes, asked often';  measured_answer = $ctx.answer; input_tokens = $ctx.input_tokens; correct = ($ctx.answer -eq '365') }
  [pscustomobject]@{ option = 'retrieval'; verdict = 'rejected'; why = 'needs an index for 3 lines';  measured_answer = ''; input_tokens = ''; correct = '' }
  [pscustomobject]@{ option = 'tool';      verdict = 'rejected'; why = 'no live system to query';   measured_answer = ''; input_tokens = ''; correct = '' }
)
$rows | Export-Csv -NoTypeInformation -Encoding utf8 .\decision.csv
$rows | Format-Table -AutoSize

    Expected: a table where none answers UNKNOWN with about 3,750 input tokens and correct False, and context answers 365 with about 3,800 input tokens and correct True. The other two rows stay empty.

  3. Apply the done-test: the chosen option must be correct, and must add fewer than 100 input tokens over the baseline.

    $chosen = $rows | Where-Object verdict -eq 'CHOSEN'
$delta = $chosen.input_tokens - $none.input_tokens
Write-Output "chosen=$($chosen.option) correct=$($chosen.correct) extra_input_tokens=$delta"
if ($chosen.correct -eq $true -and $delta -lt 100) { Write-Output 'DONE-TEST PASS' } else { Write-Output 'DONE-TEST FAIL' }

    Expected: chosen=context correct=True extra_input_tokens=50 (about 50) and DONE-TEST PASS.

Measure the baseline and the option you chose. Your done-test: decision.csv has four rows with reasons, the chosen row has a measured answer and input token count, and the chosen option answers correctly where the baseline does not (or you document that the baseline already did, which means the answer is none).

    Expected: a decision.csv of your own with one measured chosen row. If you chose retrieval, build the measurement from the keyword retriever in the retrieval lab; if you chose a tool, measure one run that grants the tool with --allowedTools.

Self-check

Why did the baseline say UNKNOWN instead of a number? The fact is specific to this platform and is not in the model's training data, and the prompt allowed UNKNOWN. Without that allowance it would likely have produced a plausible wrong number.

What does 50 extra input tokens tell you about the cost of context here? Putting a small fact in context is nearly free, so adding retrieval machinery for it would cost more in engineering than it saves in tokens.

When does your own choice flip? When the knowledge grows past what you are willing to send on every call (retrieval), or when it changes faster than you can edit the file (a tool that reads the live source).

What makes the table checkable by someone else? Each verdict has a reason, and the chosen row carries a measured answer and token count rather than an opinion.
