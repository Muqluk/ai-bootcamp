The Agent SDK is Claude Code's agent loop as a library: the same tools, permissions, hooks, subagents and sessions, driven from your own Python or TypeScript program instead of a terminal. Agent teams and SendMessage are the other direction: several Claude Code sessions that coordinate with each other while you watch. This module covers what the SDK adds over claude -p, how each piece maps to code, how team messaging is delivered, and when none of it is worth the bother.

After this module you can

  • Explain how the Agent SDK relates to claude -p and name what you gain by writing code instead of a shell line.
  • Read the SDK message stream (init, assistant, tool results, result) and branch on the result subtype instead of assuming success.
  • Write the options that matter in code: allowed and disallowed tools, permission mode, turn and budget caps, hooks, canUseTool, subagents and an in-process custom tool.
  • Run your own agent loop over the stream-json channel from a dependency-free Node script: send a message, read events, send a follow-up in the same session.
  • Resume and fork a session, and define a subagent from JSON.
  • Say what an agent team is, how SendMessage reaches a teammate or another session, which limits apply, and choose between a team, subagents and plain messaging.

If you skipped the prerequisites

A headless run is claude -p "prompt": the same agent loop as the terminal, with no person in it. It reads stdin, prints a result, and returns an exit code. --output-format json returns one result object with result, session_id, total_cost_usd and usage; stream-json returns one JSON event per line as the loop runs. --allowedTools pre-approves tools, --max-turns caps the loop, and --resume continues a stored session. A subagent is a second agent instance the main agent starts with the Agent tool; it works in its own context window and only its final message comes back. Every headless run should say which settings and MCP servers it loads, because the defaults pick up whatever is on the machine.

Claude Code, as a library

The docs define the Agent SDK in one sentence: it gives you the same tools, agent loop and context management that power Claude Code, programmable in Python and TypeScript. It is not a thin client for the Messages API. Both packages bundle a native Claude Code binary and run it as a subprocess, so what your program drives is the real loop: prompt, model response, tool calls, tool results, repeat until a response has no tool calls.

Defaults that differ from what you expect

Two defaults from the TypeScript options table matter on day one. settingSources defaults to the CLI defaults, meaning user, project and local settings all load, so an SDK program on your laptop picks up your CLAUDE.md, skills and hooks. Pass [] to load none. systemPrompt defaults to a minimal prompt; to get Claude Code's own prompt you pass the claude_code preset. The first is the SDK counterpart of the --setting-sources flag this course uses on every headless run; MCP servers are configured separately through mcpServers.

Decide settings isolation in the first lines of any SDK program: a program that behaves differently on your machine and on the build server is almost always loading different settings sources.
The SDK is the same loop, so it is the same cost model. An open-ended prompt with no maxTurns and no maxBudgetUsd runs until Claude decides it is done, and the docs say so plainly: without limits the loop can run long on open-ended prompts.

One call, an async stream

In TypeScript, query({ prompt, options }) returns a Query: an async generator of messages that also has control methods (interrupt(), setPermissionMode(), setModel() among them). prompt is a string, or an async iterable of user messages for streaming input (lesson 4). You consume it with for await. In Python, query() is the one-shot form and ClaudeSDKClient holds a session across several calls; the docs recommend the client when the next action depends on Claude's answer.

import { query } from "@anthropic-ai/claude-agent-sdk";

for await (const message of query({
  prompt: "Summarize this project",
  options: { allowedTools: ["Read", "Glob", "Grep"], maxTurns: 6 },
})) {
  if (message.type === "assistant") {
    for (const block of message.message.content) {
      if (block.type === "tool_use") console.log("tool:", block.name);
    }
  }
  if (message.type === "result") console.log(message.subtype, message.total_cost_usd);
}

Note the TypeScript shape: assistant and user messages wrap the raw API message, so content blocks are at message.message.content. In Python you check classes with isinstance (AssistantMessage, ResultMessage, TextBlock, ToolUseBlock) and read message.content directly.

Every result variant carries total_cost_usd, usage, num_turns and session_id, so you can log cost and resume even after a failure. A single-shot query() raises after yielding an error result, so wrap it and keep the branch on subtype inside the loop. total_cost_usd is the SDK's client-side estimate, the same number maxBudgetUsd is compared against; the docs add that spend can pass the cap by the cost of the response that crosses it, plus whatever running subagents spend before they stop.

Counting turns

A turn is one pass through the loop. The docs count each turn with tool calls plus one for the final text-only response, so maxTurns of 2 would have stopped a "run tests, read file, edit, re-run" task before the edit. Lab 2 measures this on the command line: with --max-turns 1 a read-one-file task ended as error_max_turns with no answer, and the result reported num_turns 2.

Write the result handler before the prompt. If your code only handles success, the first turn cap or budget cap turns into a silent empty answer.
Reading message.result without checking subtype. On every error subtype the field is absent, so you get undefined or a type error where you expected text.

Tools and the permission options

The built-in tools are the Claude Code set: Read, Edit, Write, Glob, Grep, Bash, WebSearch, WebFetch, ToolSearch, and the orchestration tools (Agent, Skill, AskUserQuestion, TaskCreate, TaskUpdate). Read-only tools can run in parallel; tools that change state run one at a time.

Option (TypeScript / Python)What it does
allowedTools / allowed_toolsAuto-approves the listed tools. It does not restrict Claude to them: unlisted tools stay available and fall through to the mode and canUseTool.
disallowedTools / disallowed_toolsDenies. A bare name such as "Bash" removes the tool from Claude's context; a scoped rule such as "Bash(rm *)" keeps the tool and denies matching calls in every mode.
toolsThe set of built-in tools Claude gets at all (an array of names or the claude_code preset).
permissionMode / permission_modedefault, acceptEdits, plan, dontAsk, auto, bypassPermissions.
canUseTool / can_use_toolYour callback, asked only when nothing earlier decided the call. Returns allow (optionally with updatedInput) or deny with a message.
maxTurns, maxBudgetUsdCaps on the loop; no limit by default.

In TypeScript, bypassPermissions also needs allowDangerouslySkipPermissions: true, and the docs reserve it for CI, containers and other isolated environments. The Security and Unattended and CI modules cover that decision; here the point is that it is an explicit flag in code.

The order a tool call is judged in

The docs list six steps: hooks, deny rules, ask rules, the permission mode, allow rules, then canUseTool. Two consequences matter. A hook that returns allow does not skip the deny and ask steps. And a callback you wrote may never run: with bypassPermissions, or with a bare tool name in allowedTools, calls are approved before the callback is consulted. The TypeScript SDK emits a process warning with code CLAUDE_SDK_CAN_USE_TOOL_SHADOWED when you configure that combination.

Hooks as callbacks

The Hooks module covers hooks as shell commands in settings files. In the SDK the same events take functions in options.hooks: an object keyed by event name, each value a list of matchers with a hooks array of callbacks. A callback receives the event input (it always carries session_id, cwd and hook_event_name; PreToolUse adds tool_name and tool_input), a tool use id and a context with an abort signal. It returns {} to allow, or an object whose hookSpecificOutput holds permissionDecision (allow, deny, ask, defer), permissionDecisionReason and optionally updatedInput.

const denyEnvWrites = async (input) => {
  const path = String(input.tool_input?.file_path ?? "");
  if (/(^|[\\/])\.env$/i.test(path)) {
    return { hookSpecificOutput: {
      hookEventName: input.hook_event_name,
      permissionDecision: "deny",
      permissionDecisionReason: "Cannot modify .env files",
    } };
  }
  return {};
};
// register it in options:
// hooks: { PreToolUse: [{ matcher: "Write|Edit", hooks: [denyEnvWrites],
//                         onFailure: "block" }] }

Three details from the hooks page. When several PreToolUse hooks disagree, deny beats defer beats ask beats allow. A callback that throws normally lets the action go ahead and your app gets an informational message tagged hook_callback_failed, so a guard that crashes fails open; onFailure: "block" (Python on_failure="block", needs recent SDK versions) makes it fail closed. And a matcher of Write|Edit does not see a Bash command that writes the same file, which is the usual hole in file guards.

Custom tools as an in-process MCP server

You give Claude a tool of your own by defining it with tool(name, description, schema, handler) and wrapping it in createSdkMcpServer({ name, version, tools }). The server runs in your process, not as a separate program, and you pass it in mcpServers. The tool's fully qualified name follows the MCP convention mcp__{server}__{tool}, and that is the string you put in allowedTools (a wildcard such as mcp__weather__* covers a whole server). A tool that sets readOnlyHint in its annotations may run in parallel with others; custom tools run sequentially by default. TypeScript schemas are Zod shapes. The MCP module covers the protocol underneath.

Put the policy in a hook or a deny rule, put the convenience in allowedTools. A tool allowed by name is approved before your callback is consulted.
Treating allowedTools as a sandbox. In lab 2 the run allowed only Read, and the model still ran a read-only Bash command, because read-only shell commands are approved without a rule. Restrict with tools or disallowedTools.

Defining a subagent programmatically

The Headless runs and subagents module covers subagents as markdown files. The SDK page recommends the third way for SDK programs: the agents option, a map from name to AgentDefinition. Claude starts one through the Agent tool. The CLI takes the same shape as JSON in --agents, and lab 3 uses it.

FieldRequiredMeaning
descriptionYesWhen Claude should use this agent. This is what automatic delegation matches on.
promptYesThe agent's system prompt.
toolsNoAllowed tool names; omitted means it inherits what subagents can use.
modelNoAn alias (haiku, sonnet, opus, fable), a full model id, or inherit.
maxTurns, effort, permissionMode, skills, mcpServers, backgroundNoPer-agent overrides and extras.

A non-fork subagent starts with a fresh context: no parent conversation, no parent system prompt. The only thing that crosses is the Agent tool's prompt string, so file paths, error text and decisions have to be in it. It does receive its own prompt and the project CLAUDE.md. Only its final message returns to the parent, which is the context saving the Headless runs and subagents module describes.

To see delegation in your stream, look for a tool_use block named Agent; messages produced inside a subagent carry parent_tool_use_id. The tool appears as Agent in blocks but as Task in the init tool list, so match both. Lab 4 shows the same split.

Limits on how far it fans out

Each subagent makes its own API requests and can spawn subagents of its own. The docs give three caps. Depth: CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, default 3 layers below your main agent. Concurrency: CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS, default 20 running at once, past which the spawn returns Concurrent subagent limit reached. Spend: maxBudgetUsd counts subagent requests too, refuses new spawns with Budget limit reached, and stops background subagents. The two environment variables go through the env option, which replaces the subprocess environment in TypeScript (spread process.env into it) and merges into it in Python.

Sessions: continue, resume, fork

You get the session id from ResultMessage.session_id. Resuming restores the full prior context; forking copies the history into a new session id and leaves the original unchanged. Sessions store the conversation, not the filesystem: a forked agent that edits files edits the real files, and file checkpointing is the separate feature for reverting them. Session files are local to the machine that wrote them, at ~/.claude/projects/<encoded-cwd>/<session-id>.jsonl. To resume on another host (CI workers, containers) you pass a sessionStore adapter so transcripts are mirrored to your own backend, move the file, or skip resume and pass the results you need into a fresh prompt, which the docs call often more robust.

Streaming input versus a single message

The docs prefer streaming input mode: a long-lived process where you yield user messages from an async generator. It gives you queued messages that run in order and can be interrupted, images in messages, and the full tool set, with context persisting across turns. Single-message mode is one string and one answer, with session options for follow-ups. The user message shape is { type: "user", message: { role: "user", content } }, plus parent_tool_use_id: null in TypeScript. Lab 1 sends exactly that shape to the CLI.

One conversation, many messages: hold one session open or resume by id. Do not rebuild context by pasting the transcript into a new query().
Assuming a subagent sees what the parent saw. It does not; a prompt that says "fix the failing test" with no path gives the subagent nothing to work with, and it will spend turns rediscovering it.

What a team is, and how you turn one on

An agent team is several Claude Code sessions coordinating: one lead, which spawns teammates and synthesizes results, and teammates, each a full session with its own context window. They share a task list and message each other directly, and you can talk to any teammate without going through the lead. The docs label the feature experimental and off by default. You enable it with the environment variable CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1, in your shell or in the env block of a settings file.

Enabling it changes ordinary delegation. When agent teams are on, a subagent that Claude gives a name launches as a teammate, and Claude Code does not ask you to confirm. Claude names subagents on its own so it can message them later, so a team can form when you never asked for one. Spawning teammates also requires an interactive session: in claude -p and in Agent SDK sessions, Claude does not spawn teammates, and a named subagent runs as an ordinary subagent even with the variable set. Lab 4 shows that on the command line.

The team name is session- plus the first eight characters of the session id. A message counts as sent only when the write to the recipient's mailbox file succeeds; on failure the sender gets an error and nothing is delivered. Messages arrive without the lead polling, and when a teammate finishes it notifies the lead with its final answer (or, if its turn ended on an API error, with the error text).

Display modes

The default is in-process: all teammates run inside your terminal, you pick one with the arrow keys in the agent panel, press Enter to view it and type to message it, press x to stop it, and Ctrl+T toggles the task list. Split panes give each teammate its own pane and need tmux or iTerm2 with the it2 command. The teammateMode setting takes "in-process", "auto", "tmux" or "iterm2"; claude --teammate-mode sets it for one session and, per the docs, does not appear in claude --help. Split panes are not supported in VS Code's integrated terminal, Windows Terminal or Ghostty.

SendMessage and how a message gets delivered

SendMessage is a tool Claude calls; you never call it yourself. Its documented targets: a teammate, a subagent it resumes by agent id or name, or one of your other Claude Code sessions on this machine or beyond it (Claude Code 2.1.224 or later; native Windows 2.1.234). ListAgents is the companion tool that lists who can be reached, and /list-agents (also /peers) shows you the same list. SendMessage does not need agent teams: only structured team-protocol messages such as shutdown_request and plan_approval_response do. Resuming a finished subagent by messaging it works without any team.

Delivery between your own sessions works like this. The receiver reads the message between tool calls during an active turn; if it is idle, Claude Code starts a new turn with it. It arrives as plain text, framed as coming from another session, and it cannot approve a permission prompt, change settings or CLAUDE.md, or run a slash command in its text. The receiver's own permission rules still apply to whatever the message asks for. The inbound check ends in one of three outcomes, delivered, held (set aside until you approve) or refused (dropped). A -p session cannot show the approval dialog, so a held message there waits up to dialogExpiry, five minutes by default, then is dropped; setting crossSessionInbound to accept in that worker's --settings lets it take messages unattended, and refuse stops a session from receiving them.

The channel has limits written into the docs. It carries plain text only. A same-machine message over about a million characters is refused at the sender. A rapid burst to one session is refused at the sender. In the receiver, repeats from one sender are rate-limited, identical repeats in a short window are dropped, and at most 50 accepted messages queue, so a loop between two sessions stops by itself. In auto mode a classifier reviews each agent-to-agent message before it is delivered and treats a relayed "the user approved this" as untrusted.

Team limits and permissions

  • Teammates start in the lead's permission mode; you cannot set a mode per teammate at spawn. If the lead is in dontAsk mode, a teammate starts in manual mode. Teammate permission prompts appear in the lead session.
  • One team per session; no nested teams (teammates cannot spawn teammates); the lead is fixed.
  • /resume and /rewind do not restore in-process teammates, and the lead may then message teammates that no longer exist.
  • Task status can lag: a teammate may not mark a task completed, which blocks dependents.
  • Hooks give you gates: TeammateIdle, TaskCreated and TaskCompleted each accept exit code 2 to send feedback and keep the work going (or block the task).
  • Size: the docs suggest 3 to 5 teammates to start; there is no hard limit, and token cost scales with the number active. An in-process teammate's cache holds five minutes by default, even on a subscription; subagentPromptCacheTtl set to 1h raises it, at the higher cache-write rate.
Use a team when the workers need to argue with each other or own separate pieces; use subagents when only the result matters.
Turning the variable on in a shared settings file and then watching a plain "use a subagent" prompt launch teammates. The setting changes what a named subagent means, for everyone who loads that file.

It also makes you the owner of the protocol: the docs describe the flags and the SDK, not a wire format to build on, so a host like this is a teaching tool and a stopgap. If you need callbacks, typed messages and supported control methods, install the SDK.

What each one bills

Both run Claude Code, so both spend model tokens at the same rates; the question is whose meter. The docs' guidance on authentication is blunt about the SDK. The quickstart sets ANTHROPIC_API_KEY in the shell where the agent runs (the SDK does not load .env files on its own), and names Bedrock (CLAUDE_CODE_USE_BEDROCK=1) and Google Cloud (CLAUDE_CODE_USE_VERTEX=1) as the other routes. The overview and quickstart both carry the same note: unless previously approved, third-party developers may not offer claude.ai login or rate limits in their products, including agents built on the SDK, and should use API key authentication.

Three cost controls exist in code. maxTurns and maxBudgetUsd (CLI: --max-turns, --max-budget-usd) cap one run, and the budget cap includes subagents. total_cost_usd is a client-side estimate used for that cap, not your invoice, so reconcile against the console on an API key. The model you pick per subagent (model: "haiku" in an AgentDefinition) is the biggest lever; the Cutting cost module covers the rest. On a subscription, cached prefixes of the main conversation get the one-hour lifetime, while a team's in-process teammates default to five minutes.

Write the budget cap into the program, not the runbook. A loop with no cap is an invoice or a drained plan window waiting for a prompt that never converges.
Building a product on your own subscription login because it works on your machine. It works until it is shipped, and then it is the one thing the docs say you may not do.

You write a 40-line Node host that starts Claude Code in stream-json mode, sends two messages in one session, and prints every event it receives.

Every claude -p run in this module carries --setting-sources project and --strict-mcp-config, so your personal settings, hooks and MCP servers stay out of the measurement. The script below puts them in its argument list for the same reason.

  1. Make the lab folder and write the host. The here-string is single-quoted, so nothing in it is expanded.

    New-Item -ItemType Directory -Force {{LAB}}/m14 | Out-Null
Set-Location {{LAB}}/m14
@'
// host.mjs: drive a Claude Code process over stream-json and print one trace line per event.
import { spawn } from "node:child_process";
import { createInterface } from "node:readline";
import { readFileSync } from "node:fs";

const [promptsFile, ...extra] = process.argv.slice(2);
const prompts = JSON.parse(readFileSync(promptsFile, "utf8"));
const base = ["-p", "--input-format", "stream-json", "--output-format", "stream-json", "--verbose",
  "--model", "haiku", "--setting-sources", "project", "--strict-mcp-config"];
const child = spawn(process.env.CLAUDE_BIN || "claude", [...base, ...extra], { stdio: ["pipe", "pipe", "inherit"] });

let sent = 0;
const send = (text) => {
  child.stdin.write(JSON.stringify({ type: "user", message: { role: "user", content: text } }) + "\n");
  console.log(`SEND user ${++sent}: ${text}`);
};

createInterface({ input: child.stdout }).on("line", (line) => {
  if (!line.trim()) return;
  const ev = JSON.parse(line);
  const who = ev.parent_tool_use_id ? " (from subagent)" : "";
  if (ev.type === "system" && ev.subtype === "init") {
    console.log(`RECV init session=${ev.session_id.slice(0, 8)} model=${ev.model} tools=${ev.tools.length} apiKeySource=${ev.apiKeySource}`);
  } else if (ev.type === "assistant") {
    for (const b of ev.message.content) {
      if (b.type === "text") console.log(`RECV assistant text${who}: ${b.text.slice(0, 80).replace(/\s+/g, " ")}`);
      if (b.type === "tool_use") console.log(`RECV assistant tool_use${who}: ${b.name} ${JSON.stringify(b.input).slice(0, 110)}`);
    }
  } else if (ev.type === "user") {
    for (const b of ev.message.content ?? []) {
      if (b.type === "tool_result") console.log(`RECV tool_result${who}: is_error=${!!b.is_error}`);
    }
  } else if (ev.type === "result") {
    console.log(`RECV result subtype=${ev.subtype} turns=${ev.num_turns} denials=${ev.permission_denials?.length ?? 0} session=${ev.session_id.slice(0, 8)}`);
    if (sent < prompts.length) send(prompts[sent]); else child.stdin.end();
  }
});
child.on("exit", (code) => console.log(`child exit ${code}`));
send(prompts[0]);
