A line in CLAUDE.md is a request the model weighs against everything else in its context. A hook is a program Claude Code runs at a fixed point in its loop, and when that program says no, the tool call does not happen. This module covers how hooks are wired, the exact contract between Claude Code and your script, how to write a guard that holds up, and how to test one without risking your real setup.

After this module you can

  • Name the hook events that can block an action and the ones that only observe, and pick the right one for a given policy.
  • Write a project-scoped .claude/settings.json hook entry with a matcher, an exec-form PowerShell command, a timeout and onFailure.
  • Write a PreToolUse guard that parses tool_input properly, denies with permissionDecision, fails closed on bad input and logs every decision.
  • Inject context with SessionStart or UserPromptSubmit and prove the model received it with a control run.
  • Build a Stop gate with a stop_hook_active loop guard and predict how many turns it costs when the condition can never be met.
  • Test any hook offline against a table of recorded inputs, then confirm it in one live headless run with only that hook loaded.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The labs were run on 2.1.322.
  • Windows PowerShell 5.1 or PowerShell 7. Hook scripts in this module are PowerShell.
  • About $0.03 of Haiku usage at API list price for all five labs, or the same share of a subscription's 5-hour window.
  • No prior module. This one stands alone.

Why instructions are not enough

Everything you put in CLAUDE.md, a skill or a system prompt becomes tokens in the model's context. The model reads them, weighs them against the user's request, the tool results and its own plan, and usually follows them. Usually is the problem. A long session, a persuasive tool result, a user who says "just this once", or a file the model read that contains instructions of its own can all tip the balance. You cannot audit a probability.

A hook sits outside the model. Claude Code runs it at a fixed point in its own loop: before a tool call, after one, when a prompt arrives, when the model tries to stop. The hook receives a JSON description of what is about to happen, and for the events that can block, its answer is final. A PreToolUse hook that returns deny blocks the tool call even in bypassPermissions mode or with --dangerously-skip-permissions. The model sees the denial reason in the tool result and can argue with it in prose, but it cannot make the call go through.

If breaking a rule would cost you a rebuild, a restore or an incident report, the rule belongs in a hook or a permission deny rule, not only in CLAUDE.md.

Hooks and permission rules

Claude Code already has permission rules (permissions.allow, permissions.deny, and the --allowedTools and --disallowedTools flags). Use them first: a deny rule like Bash(git push *) needs no script and cannot crash. A hook is for policy that a rule pattern cannot express: "deny any command that mentions prod", "deny recursive deletes in any spelling", "log every call", "refuse to stop until the tests pass". The two stack. A hook returning allow does not override a deny rule, and a hook returning deny wins over an allow rule.

The event map

Claude Code fires about thirty hook events. Most engineers use six of them. The column that matters is the third: only some events can stop the thing they describe.

EventFiresCan block?Typical use
SessionStartSession begins, resumes, clears or compactsNo (context only)Inject branch, environment, open tickets
UserPromptSubmitA prompt is submitted, before the model sees itYes: rejects the promptAdd context per prompt, refuse prompts that carry secrets
PreToolUseAfter the model writes the tool call, before it runsYes: blocks the callGuards, input rewriting, logging
PermissionRequestWhen a call would show a permission promptThrough its decision object only, not exit 2Auto-approve or auto-deny prompts
PostToolUseAfter a tool call succeedsNo: the tool already ranFormatters, linters, feedback to the model
PostToolBatchAfter a batch of parallel calls resolvesYes: stops the loop before the next model callBatch-level checks
StopThe main agent finishes respondingYes: sends the model back to workCompletion gates ("tests must pass")
SubagentStopA subagent finishesYesGate a subagent's report
PreCompactBefore context compactionYesAdd summary instructions or refuse
ConfigChangeA settings file changes mid-sessionYes (except managed policy)Stop a session from loosening its own settings
Notification, SessionEnd, PostCompactSide eventsNoAlerts, cleanup, audit

Others exist (TaskCreated, TaskCompleted, InstructionsLoaded, FileChanged, CwdChanged, PreModelSwitch, WorktreeCreate and more). The reference section lists the ones this module uses; the full list is in the hooks reference page of the Claude Code docs.

PostToolUse looks like a guard and is not one. By the time it fires the file is written and the command has run. Use it to tell the model what went wrong, never to prevent anything.

Three cadences

Per session: SessionStart and SessionEnd. Per turn: UserPromptSubmit and Stop. Per tool call: PreToolUse and PostToolUse. The cadence decides your latency budget. A 400 ms PowerShell start-up is nothing once per session and noticeable on every one of fifty tool calls.

The configuration shape

Hooks are a hooks key in a settings file, nested three levels deep: event, then a list of matcher groups, then a list of handlers in each group.

{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|PowerShell",
        "hooks": [
          {
            "type": "command",
            "command": "powershell",
            "args": ["-NoProfile", "-ExecutionPolicy", "Bypass", "-File",
                     "${CLAUDE_PROJECT_DIR}/.claude/hooks/guard.ps1"],
            "timeout": 30,
            "onFailure": "block"
          }
        ]
      }
    ]
  }
}

Where a hook can be defined

LocationScopeShared?
~/.claude/settings.jsonEvery project you openNo
.claude/settings.jsonThis projectYes, commit it
.claude/settings.local.jsonThis project, this machineNo
Managed policy settingsOrganisationAdmin-controlled
Plugin hooks/hooks.jsonWhile the plugin is enabledWith the plugin
Skill frontmatter (hooks:)Rest of the session once the skill is invokedWith the skill
Subagent frontmatter (hooks:)While that subagent runs; a Stop hook there becomes SubagentStopWith the agent file

Hooks merge; they do not override. A project hook adds to your user hooks, and nothing below managed policy can remove a managed hook. "disableAllHooks": true turns off every hook from the levels it can reach, and passing it with --settings turns hooks off for one run. An administrator can set allowManagedHooksOnly so that user, project, local and plugin hooks do not run at all. The same handler defined in two settings files runs once.

In a claude -p run there is no workspace trust dialog, and hooks do not wait for one: hooks committed in a repository's .claude/settings.json run the first time you script against a repo you have never opened. Before you point a headless job at someone else's repository, read its .claude/ folder or run with --settings pointing at a file containing {"disableAllHooks": true}.

Matchers

The matcher filters which occurrences of an event reach the group. What it is compared to depends on the event: the tool name for tool events, the start reason for SessionStart (startup, resume, clear, compact, fork), the agent type for SubagentStop. UserPromptSubmit, Stop and PostToolBatch have no matcher; one you add there is silently ignored.

Matcher valueRead asExample
*, empty, or omittedEverythingLog every tool call
Letters, digits, _ - , | and spaces onlyExact name, or a list split on | or ,Bash|PowerShell, Edit, Write
Anything elseUnanchored JavaScript regexmcp__github__.*; Edit.* also matches NotebookEdit

Matchers are case-sensitive. MCP tools are named mcp__<server>__<tool>, and mcp__memory on its own matches nothing because it is read as an exact name; write mcp__memory__.*.

On Windows the shell tool may be PowerShell, not Bash. Where the PowerShell tool is enabled the model routes shell commands through it, and without Git Bash the Bash tool is not registered at all. A guard matched only on Bash never fires there. Match Bash|PowerShell.

A handler can also carry if, a single permission-rule pattern such as Bash(git *), so the process only spawns when the call matches. It saves start-up time. The docs call it best-effort: when Claude Code cannot work out which commands a shell string runs, it runs the hook anyway, and your script must still do its own check.

Handler types

typeWhat runsDefault timeout

This module uses command. Note that prompt and agent handlers spend model tokens on every firing: billed per token on an API key, drawn from the 5-hour window and weekly limit on a subscription. A command hook spends no tokens unless it injects text into the context.

Exec form and shell form

With args present, Claude Code spawns command directly with that argument list and no shell (exec form). Without args, the string goes to a shell: Git Bash on Windows if it is installed, otherwise PowerShell, unless you set "shell": "powershell". Exec form is the safer default for a script path: each element is one argument, ${CLAUDE_PROJECT_DIR} is substituted as plain text, and no shell profile can print junk ahead of your JSON. Every lab here uses exec form with powershell -NoProfile -ExecutionPolicy Bypass -File.

Exit codes

ExitMeaningEffect
0Successstdout is parsed as JSON if it is one JSON object; on UserPromptSubmit and SessionStart plain-text stdout becomes context for the model; elsewhere stdout goes to the debug log
2Blocking errorOn a blockable event the action stops and stderr is the reason (shown to the model for PreToolUse and Stop, to the user for UserPromptSubmit)
anything elseNon-blocking errorThe action goes ahead; a "hook error" notice shows the first stderr line
Exit 1 does not block. It is the conventional Unix failure code and the most common bug in a first guard: the script detects the bad command, writes a message, exits 1, and the command runs. Use exit 2 or a JSON deny.

JSON on stdout

Exit 0 and print exactly one JSON object for finer control. Nothing else may be on stdout: a stray line in front of the { turns the whole thing into plain text, and the decision is silently ignored.

FieldEventsEffect
hookSpecificOutput.permissionDecisionPreToolUseallow skips the prompt, deny blocks, ask prompts the user, defer ends a -p turn so the call can be resumed later. Precedence across hooks: deny > defer > ask > allow
hookSpecificOutput.permissionDecisionReasonPreToolUseFor deny, shown to the model
hookSpecificOutput.updatedInputPreToolUseReplaces the whole tool input before it runs; include unchanged fields. Pair with allow or ask
hookSpecificOutput.additionalContextSessionStart, UserPromptSubmit, PreToolUse, PostToolUse, Stop and othersText inserted as a system reminder for the model; capped at 10,000 characters
decision: "block" + reasonUserPromptSubmit, PostToolUse, Stop, SubagentStop, PreCompact, ConfigChangeBlocks (or for PostToolUse, feeds the reason back)
continue: false + stopReasonAllStops Claude entirely; wins over any other decision
systemMessageAllWarning shown to the user

A real deny from the Lab 2 guard, produced by ConvertTo-Json so quoting is never hand-built:

{"hookSpecificOutput":{"permissionDecision":"deny","hookEventName":"PreToolUse","permissionDecisionReason":"Policy: nothing in this project may touch prod. Ask a human."}}
permissionDecision at the top level instead of inside hookSpecificOutput still parses, and Claude Code ignores it without an error. The debug log records Hook JSON output had unrecognized keys.

Timeouts, failure and parallel runs

All hooks matching an event run in parallel, not in order, so one hook cannot rely on another having run first, and two hooks both returning updatedInput for the same tool give no guarantee which rewrite wins. A hook that reaches its timeout is cancelled and its output discarded. On PreToolUse a timed-out, crashed or missing hook does not block: the call continues through normal permissions. That is fail-open, and for a guard it is wrong. Set "onFailure": "block" on the handler (Claude Code 2.1.295 or later) and a failure to start, a non-0/2 exit, invalid JSON or a timeout all block the call. onFailure has no effect on Stop hooks.

Every enforcement hook gets an explicit timeout, "onFailure": "block", and a first live run where you watch for a "hook error" notice.

Parse the input, do not grep it

Read stdin once, parse it as JSON, and pull the one field you judge. Matching a regex against the raw JSON text sounds equivalent and is not: quotes and backslashes arrive escaped (\", \\), so a pattern that works on the command fails on the JSON spelling of it. In PowerShell:

$in  = [Console]::In.ReadToEnd() | ConvertFrom-Json
$cmd = [string]$in.tool_input.command

Fail closed

A guard has three outcomes, not two: allow, deny, and "I could not tell". Decide what the third one does. For an enforcement hook it is deny. Wrap the parse in try/catch and exit 2 with a message on stderr when the input is unreadable, and set onFailure: "block" so a crash or a timeout also blocks. For a logging or context hook it is the opposite: fail open, exit 0, and never block work because a log file was locked.

SituationGuard (fail closed)Logger (fail open)
stdin is not JSONstderr + exit 2exit 0
Script throwsonFailure: "block" catches itLeave onFailure unset
TimeoutonFailure: "block" catches itShort timeout, unset
Pattern unsure (encoded, obfuscated)Deny and say whyLog it

Wrappers and spellings

The command the model writes is a string, and a shell can run the same action under many spellings. A guard anchored on the start of the string (^rm ) misses all of these:

SpellingWhy an anchored or naive guard misses it
cmd /c "git push -f origin main"Wrapped in another shell; also -f instead of --force
bash -c 'rm -rf build'Wrapped, single-quoted
powershell -Command "ri build -r"Alias ri and abbreviated -r for Remove-Item -Recurse
rm -r -f buildFlags split
git push origin +mainForce push with no force flag at all
powershell -EncodedCommand cgBtACAA...The payload is base64; there is nothing to match

Three habits cover most of it. Match unanchored, anywhere in the string, so a wrapper does not hide the inner command. List the aliases and short flags explicitly. Deny outright what you cannot inspect (-EncodedCommand, Invoke-Expression on a built string) rather than trying to decode it. The cost is false positives: echo "never git push --force" is denied too. For a guard that is the right trade, and the denial reason tells the model what to do instead.

The model can write a script with Write and then run it by path. Your shell guard sees powershell -File .\cleanup.ps1 and nothing inside it. If the action matters, also guard Write and Edit content, or deny running scripts from the working folder.

Keep it fast

A PreToolUse hook runs on every matching call and the model waits for it. In Lab 1 the debug log timed each run of a minimal PowerShell 5.1 hook at about 440 to 500 ms, almost all of it interpreter start-up, and Lab 5 measured 250 to 600 ms per offline call. Ways to keep the cost down: match narrowly (Bash|PowerShell rather than *), add an if pattern so unrelated calls never spawn a process, use -NoProfile, and do no network calls in the decision path. If a hook must do slow work, print the decision first, then start the slow part in the background with its output redirected.

Log every decision

Write one line per decision: time, verdict, rule name, the command. A guard that denies silently is indistinguishable from one that never ran, and a log is how you find the false positive that annoyed a colleague last Tuesday. The Lab 2 guard writes this:

2026-11-11T17:34:48 DENY  Bash echo deployed > prod.txt
2026-11-11T17:34:48 PASS  Bash echo built > build.txt
2026-11-11T17:34:51 DENY  Bash echo deployed > prod.txt

Do not log secrets. If commands can carry tokens, log a hash or a redacted form.

Deny with a reason the model can act on

The permissionDecisionReason goes to the model. "Blocked" invites retries in a new spelling. "Blocked by project guard: recursive delete. Ask a human to run it." tells it to stop and report, which is what Haiku did in Lab 2: it quoted the reason, said it had not tried another way, and asked for authority.

A guard is parse, decide, log, answer, in that order, and it never exits 1.

Context hooks

Not every hook says no. SessionStart and UserPromptSubmit can put text in front of the model: the current branch, which environment this folder deploys to, today's change freeze. Two channels work on exit 0:

  • Plain stdout: on these two events, text that is not a JSON object is added as context.
  • hookSpecificOutput.additionalContext: the same, inside JSON, so you can combine it with other fields.

Either way Claude Code wraps the text in a system reminder; it does not appear as a chat message. Lab 3 uses one of each and the model answered HERON-7 oncall-blue with the hooks on and NONE with them off. With --output-format stream-json --verbose --include-hook-events the stream shows a hook_started and a hook_response line per hook, ahead of the system init line, and the response carries stdout, stderr, exit_code and outcome.

Write the text as plain facts ("The deployment target is staging"), not as commands styled like a system message. The docs warn that text framed as out-of-band instructions can trigger the model's prompt-injection defences, and it then reports the text to you instead of using it. For facts that never change, CLAUDE.md is cheaper: it loads without spawning a process.

On resume, Claude Code replays the context a UserPromptSubmit hook injected on past turns instead of re-running the hook, so timestamps and commit hashes go stale. SessionStart does re-run on resume with source set to resume.

What context costs

Injected text is input tokens on every request that follows. A SessionStart line sits early in the conversation and is cached after the first request; a UserPromptSubmit line adds new tokens each prompt. On an API key that is billed per token; on a subscription it counts against the 5-hour window and weekly limit. A 50-word line is noise. A hook that dumps a 9,000-character ticket list into every prompt is not.

Stop gates

A Stop hook fires each time the main agent finishes responding, not only at the end of the task. Exit 2 (or decision: "block" with a reason) sends the model back to work with your stderr or reason as the explanation. That makes a completion gate: "do not stop until done.txt exists", "until the test suite passes".

The danger is a condition the model cannot meet: no permission to write the file, a test that cannot pass. Two brakes exist:

  • stop_hook_active in the input is true when the model is already continuing because of a Stop hook. Check it and let the model stop on the second attempt.
  • Claude Code caps a run of consecutive Stop-hook continuations at 8 and then ends the turn anyway. The count resets every time the model calls a tool. CLAUDE_CODE_STOP_HOOK_BLOCK_CAP raises it.

Lab 4 measured what exit 2 on Stop does in a headless -p run, in three cases:

RunSetupStop hook runsnum_turnsOutcome
ALoop guard on, Write allowed24Model wrote done.txt; second run saw stop_hook_active=True done=True
BLoop guard on, no tools allowed23Write denied once; guard let it stop on the second run; file absent
CLoop guard off, no tools allowed16234 denied Write attempts reset the cap counter; ended by the cap with an empty result, subtype still success

So in headless mode exit 2 on Stop does keep the session going, the reason does reach the model (in run A it replied that it created the file "as the stop hook asked"), and the 8-in-a-row cap does end a runaway loop, but tool calls in between can stretch it well past 8. Run C cost about $0.009 at Haiku list price; on Opus the same loop would cost roughly 20 to 40 times that, depending on how much of it is cache reads. On a subscription the dollar figure is notional, but every one of those 23 turns draws on your window.

Every Stop gate checks stop_hook_active first, and its condition is something the model has the tools to satisfy.
A run ended by the cap still reports subtype: "success" and is_error: false. A pipeline that trusts those fields will treat an unfinished job as done. Check the condition itself (the file, the test result), not the exit status.

Offline first

A command hook is a program that reads stdin and writes stdout. Test it like one, with no model involved:

Get-Content samples\deny.json -Raw | powershell -NoProfile -ExecutionPolicy Bypass -File .claude\hooks\guard.ps1
$LASTEXITCODE

Where do samples come from? Record them. The Lab 1 logger saves each raw stdin to hook-data\stdin-<tool>.json, which gives you the exact shape Claude Code sends on your machine, including Windows paths and escaping. For edge cases, build the JSON with ConvertTo-Json from a table of commands so your test inputs are never hand-quoted. Lab 5's harness does that: 13 rows, each with an expected verdict, and a pass/fail count at the end. Add a row every time you find a new bypass.

Include a row of garbage input. Your guard should exit 2 on it. In Lab 2 it did: garbage exit=2 with guard: could not parse hook input, refusing on stderr.

Then one live run, with only that hook loaded

Offline tests prove the script. A live run proves the wiring: the matcher matches, the path resolves, the JSON is read. Keep it small and isolated:

  • Put the hook in a lab folder's .claude/settings.json, never in ~/.claude/settings.json while it is untested.
  • Run claude -p with --setting-sources project --strict-mcp-config so your personal hooks, settings and MCP servers stay out.
  • Grant exactly the tools the test needs with --allowedTools, cap --max-turns, and point any destructive test at a harmless target (a victim folder with one file in it).
  • Check three things: permission_denials in the JSON result lists the call, the side effect did not happen, and the guard's own log has the DENY line.

For details, --debug-file <path> writes a log with a Hooks: line per run, naming the event, the command, the exit status and the duration.

In -p mode a settings file that fails validation is silently ignored. A trailing comma in .claude/settings.json does not produce an error; it produces a session with no guard. The live run with a deliberately denied command is how you find out.

Hooks are code you run

A command hook runs with your full user rights, outside any sandbox. It can read your SSH keys, your cloud credentials and every repository you can reach. That applies to hooks you write and to hooks you install: a plugin's hooks/hooks.json merges with yours when the plugin is enabled and runs as you, and a repository's committed .claude/settings.json runs in any claude -p job you point at it. Read a plugin's hooks before enabling it, pin what you install, and treat a new hook in a pull request with the same suspicion as a new CI step. Plugins and marketplaces covers pinning and allowlists.

Review a hook like a cron job: it runs unattended, as you, every time.

You register a project-scoped PreToolUse hook that appends every tool call to a log and saves the raw stdin, and end up holding real input samples for the later labs.

Self-check

Which top-level fields does your stdin-Read.json contain? In the verified run: session_id, transcript_path, cwd, prompt_id, permission_mode, effort, hook_event_name, tool_name, tool_input, tool_use_id.

Is tool_input.file_path relative or absolute? Absolute, with backslashes. Claude Code expands paths before hooks run.

How long did each hook run take, and what would that cost across 50 tool calls? About 440 to 500 ms each here, so roughly 20 to 25 seconds of waiting over 50 calls. That is the argument for a narrow matcher.

Why does the logger exit 0 even if writing fails? It is observability, not enforcement. It must never block work.

You write a PreToolUse guard that denies any shell command mentioning prod, prove it on saved stdin samples, then watch it stop a live session, ending with a denial record and a file that was never created.

  1. Write the guard. It parses the input, fails closed on garbage, logs every decision and denies with JSON.

    New-Item -ItemType Directory -Force {{LAB}}/m5/lab2/.claude/hooks, {{LAB}}/m5/lab2/samples | Out-Null

What would run C cost on Opus 5.5 instead of Haiku 5.5?
