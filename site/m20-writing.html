An agent works from text: the prompt you typed, the instruction files that loaded, the brief another session wrote for it. It has no memory of your project and it cannot ask what you meant an hour ago. This module treats that text as engineering work. It covers what Anthropic's own guidance says about writing for current models, how to write a brief, a spec with a check, a CLAUDE.md and a handoff, and how to measure whether the text did its job.

After this module you can

  • Write a brief with a goal, context, constraints, a definition of done, a way to verify and a report format, and show with a scoring script that it beats the one-line version of the same request.
  • Turn a prose requirement into a spec with an acceptance check the agent runs itself, and grant exactly the one command the check needs.
  • Say which instruction files load in a session, in what order, and which load only on demand, and place a given instruction in CLAUDE.md, a path-scoped rule, a skill, a hook or the brief.
  • Test whether a CLAUDE.md rule is followed over several headless runs, and measure what a long file or a contradicting line does to it.
  • Write a handoff file that lets a fresh session finish a job, including the decisions that no file on disk records.
  • Write a skill, subagent or tool description that says what it does and when to use it, and a reply format a script can parse.

What the agent has when it starts

The memory page of the Claude Code docs opens with the fact that shapes everything else: "Each Claude Code session begins with a fresh context window." The model is capable. It reads code faster than you can describe it. What it lacks is everything that lives only in your head: why the task exists, what was tried last week, which of two reasonable approaches your team prefers, what finished looks like. A subagent is in the same position. The subagents page says it "doesn't see your conversation history, the skills you've already invoked, or the files Claude has already read"; it gets a delegation message and works from there.

Anthropic's prompting guidance uses the same picture. The prompting best practices page says to think of Claude as "a brilliant but new employee who lacks context on your norms and workflows", and gives a test you can apply to any text in this module: show it to a colleague with minimal context on the task and ask them to follow it. If they would be confused, the model will be too.

Current models take you at your word

The model pages describe a shift you need to write for. The Claude Sonnet 5 page says the model "interprets prompts literally and explicitly", that it "does not silently generalize an instruction from one item to another", and that to apply an instruction broadly you should state the scope: "Apply this formatting to every section, not just the first one". The best practices page gives the everyday case: ask "can you suggest some changes" and you may get suggestions, not edits. Ask for the change.

Two single runs made while building this module's labs show how literal that is on Haiku. Asked to run a check script that the permission rules blocked, the model tried to run it four different ways across two shell tools before reporting. Asked the same with the words "exactly this command and no other form", it made one attempt, was refused, and stopped to ask, saying it had not tried another route because the request named one form. Both are correct readings of what was written.

Emphasis written for older models now overshoots. The best practices page: where you once wrote "CRITICAL: You MUST use this tool when...", write "Use this tool when...". The Claude Code best practices page lists "Add IMPORTANT or ALL CAPS" among advice to drop, because piling on emphasis "mostly makes Claude over-apply the rule".

The right altitude

Anthropic's engineering article on context engineering names two ways instruction text fails. At one end, brittle if-else logic hardcoded into the prompt. At the other, guidance so high-level that it gives no concrete signal, or that "falsely assumes shared context". The target is between them: specific enough to guide, with heuristics the model can apply to cases you did not foresee. The same article is careful about length: aim for "the minimal set of information that fully outlines your expected behavior", and "minimal does not necessarily mean short".

The Claude Code best practices page turns that into a filter. Before you write something down for the agent, ask two questions: could it find this by reading the code, and would it go and look. If both are yes, leave it out. What remains is what only you know.

Write for a capable colleague who joined this morning: say what you want, why, what finished looks like, and nothing they could read off the repository themselves.

Advice you can retire

The Claude Code best practices page ends with a table headed "What you can stop doing". Three rows concern writing. Phrases such as think hard or be thorough are ordinary prompt text; the effort level is the control for depth. "Keep going, don't be lazy" lines are more likely to cause over-work than to fix a stall; a check to pass is the thing that still helps. A description of your architecture and file layout in CLAUDE.md is redundant, because the model reads the repository. One phrase the page keeps is be ambitious, because it tells the model about scope, which only you know.

An example in a brief is copied more faithfully than the prose around it. The guidance asks for examples that are "diverse" so the model does not "pick up unintended patterns". Label an example as an example, and use values that cannot be mistaken for the real data.

Writing it

  • Hand over the thing, not a description of it. The Claude Code best practices page: include a file with @ and its path, paste the screenshot, pipe the log in. A path is shorter and more exact than a paraphrase.
  • Name the file, the symptom and what fixed looks like. The page's own pair: instead of "fix the login bug", write "users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it".
  • State a preference between reasonable approaches. The model cannot read your preference from the code. "No new libraries" is a preference; so is "follow the pattern in" a named file.
  • Number steps only when order matters. The prompting page asks for sequential steps "when the order or completeness of steps matters". Elsewhere, state the outcome and let the model choose the route.
  • Give the agent a way to fail. A reply format with only a success line leaves no honest way to report a blocker. The BLOCKED line costs one sentence.
If the request has one right answer in your head, the brief must contain enough to pick that answer out. If any reasonable answer will do, a one-line prompt is fine, and the docs say so: for exploring, a vague prompt is "completely fine".

When you do not yet know what you want, the same page suggests having the model interview you: "Interview me until you could write the spec, then write it to SPEC.md", then start a fresh session from that file. The brief is still written down. You have only changed who typed it.

Why a check changes more than an adjective

"Robust", "careful" and "production quality" describe a feeling about the result. They give the agent nothing to compare its work against. The Claude Code best practices page states the mechanism plainly: "Claude stops when the work looks done. If it has nothing to run that tells it whether the work actually is done, 'looks done' is all it has to go on." A check that returns pass or fail gives it a second source of truth. It makes the change, runs the check, reads the failure and fixes it before it reports.

The page lists what can serve: a test file, a build's exit code, a linter, a script that diffs output against a fixture, a browser screenshot next to the mockup. The requirement is only that the agent can run it and read the result. If the repository already has such a command, the page calls it "the single most useful line in your CLAUDE.md".

Writing the check into the spec

Lab 2 gives Haiku the same prose spec for a small script twice. One version ends with the reply format. The other ends with this section, and has the check file in the folder:

## Check
check.ps1 in this folder tests size.ps1 against ten cases.
Run it in the PowerShell tool with exactly this command: .\check.ps1
It prints one line per failing case and then PASS 10/10 or FAIL n/10.
Fix size.ps1 and run the check again until it prints PASS 10/10. Do not edit check.ps1.
When you are finished, reply with one line: the last line check.ps1 printed.

Four details in that section are deliberate. It gives the exact command, so a permission rule can allow that command and nothing else (--allowedTools "PowerShell(.\check.ps1)"). It says what the output looks like, so the agent knows what passing is. It forbids editing the check. It asks for the last line of output as the reply, which is evidence, not a claim.

What the check does not cover

A check is also a target. The prompting best practices page warns that the model "can sometimes focus too heavily on making tests pass at the expense of more general solutions". Its counter-text says tests "verify correctness", they do not "define the solution", and asks the model to say so if a test is wrong instead of working around it. Keep the prose requirement in the spec next to the check, and tell the agent the check file is not to be edited.

The model pages add a caution for small models. The Claude Haiku 5.5 page says that at low and medium effort the model "sometimes reports a code change as done without running a check", and offers a paragraph for the system prompt that asks for "a real check that exercises the change before reporting it done". In Anthropic's testing the model checked more often with that text and performed better, at the cost of more tokens. A named check in the spec is the per-task form of the same instruction.

Before you add an adjective to a spec, try to replace it with a command that fails when the adjective is not true.

What the file is for

CLAUDE.md is the text Claude Code puts in front of the model at the start of every session. The memory page gives its purpose in one line: "the place you write down what you'd otherwise re-explain". It lists four moments to add a line: the model makes the same mistake a second time, a review catches something it should have known about this codebase, you type the same correction you typed last session, or a new teammate would need the same context.

Two properties decide how you write it. First, it is context and not configuration. The page says the content "is delivered as a user message after the system prompt, not as part of the system prompt itself", and that "there's no guarantee of strict compliance, especially for vague or conflicting instructions". Second, it is paid for on every request. The best practices page: every line "takes a little of Claude's attention on every task, whether it's relevant or not".

As soon as one of those exists, it is read instead, unless you change the Project instructions setting or import AGENTS.md from the CLAUDE.md with a line such as @AGENTS.md.

How they load

  • Walk up, concatenate. Claude Code loads CLAUDE.md and CLAUDE.local.md from the working directory and every directory above it. The files are concatenated, not overridden, ordered from the filesystem root down, so the file closest to where you launched is read last. Within one directory the local file comes after the shared one.
  • Subdirectories load on demand. A CLAUDE.md below the working directory is not loaded at launch. It loads once the model reads, writes or edits a file in that subdirectory.
  • Imports expand in place. @path/to/file pulls another file in, relative to the importing file, up to four hops deep. Imports inside code spans and code blocks are ignored, so wrap a path in backticks to mention it without importing it. An import that resolves outside the working directory needs a one-time approval. The page is explicit that imports organise a long file without reducing its context cost, because the imported file loads with the file that names it.
  • Rules files. Every .md under .claude/rules/ loads at launch with the same priority as .claude/CLAUDE.md, unless its frontmatter has a paths list of globs. Then it loads only when the model opens a matching file. paths is the only frontmatter field a rule reads. User rules load before project rules.
  • Comments are free. Block-level HTML comments are stripped before the content reaches the model, so notes for human maintainers cost no tokens.
  • Compaction. The project-root CLAUDE.md is re-read from disk after /compact. Nested files and path-scoped rules come back when a matching file is next touched. An instruction given only in conversation does not survive.
  • Scripts. Project rules are skipped when project is left out of --setting-sources, and CLAUDE.local.md when local is left out. The labs pass --setting-sources project so that only the lab folder's files apply.

Size

The memory page gives one number: "target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence." A file over 4 MiB is skipped. Files that load on demand (a subfolder CLAUDE.md, a path-scoped rule) are cut off at 40,000 characters on a 200K context window, with a note telling the model to read the rest. Claude Code warns at startup and in /status when a file is over the recommended length.

A brief written by the session that knows most

A handoff is the text a fresh session starts from when it continues someone else's work: yours after a break, another session's after it ran out of room, a headless job's after a slow step. It is a brief with one difference. The writer has been inside the task for an hour and has stopped noticing what it knows. The Orchestration module covers when to hand off and how a fleet passes the file along. This lesson is about what the file has to say.

What the disk already tells the successor

The prompting best practices page has a section on work that spans several context windows. It observes that current models "are extremely effective at discovering state from the local filesystem", and recommends structured files for state (its example is a tests.json with a status per test), free text for progress notes, and git as the log of what was done. It also says to be prescriptive about how the next window starts, with lines such as "Review progress.txt, tests.json, and the git logs."

That divides the work. Files, test results and commits record what exists. They do not record why it is that way, what was decided along the way, which finished pieces must be left alone, or what finished means. Those are the handoff's job.

A template

# Handoff: <the job in one line>

## Goal
<the whole job and who uses the result, in one or two sentences>

## State
<each finished step and the file it produced; what is not started>

## Decisions and reasons
<every choice made so far that the files do not explain, each with its reason>

## Next steps
<the exact remaining work, in order: input files, output file, format>

## How to verify
<the check that proves the whole job is finished: a command, or the exact expected content>

## Do not redo
<finished files that must not be changed or recomputed, and why>

## Open questions
<what is unknown or blocked, or "none">

Writing it for a cold reader

The Claude Fable 5.2 prompting page has a section on final reports and handoffs. Its starting point: the people who read the report "usually haven't seen the tool calls or files behind it, so the report needs to make sense on its own". The text it offers for a system prompt begins "Write for an intelligent but low-context reader" and includes a rule worth applying to any handoff, whoever writes it: "Do not use a term or abbreviation that you made up during the work." A session that has called something "the v2 path" for an hour will write "the v2 path" in its handoff, and the successor has no idea what that is.

  • Name files by path and state by fact: "open.csv holds 6 rows, sorted by id", not "the first part is done".
  • Put the reason on the same line as the decision.
  • Give the remaining format exactly, with an example line, as you would in a brief.
  • Have the session that did the work write the handoff while it still has the context, then read it yourself with the colleague test from the first lesson.
"Continue from where we left off", "as discussed" and "the usual format" point at a context the successor never had. It will not ask what they mean. It will pick a meaning.
A handoff carries what the disk does not: the purpose, the decisions with their reasons, what must be left alone, and how to tell when the job is finished.

Descriptions decide what gets picked

A skill, a subagent and a tool each have a short text the model reads to decide whether to use it. The body of a skill or the prompt of a subagent is not read at that point. If the description does not match the request in front of the model, the rest of your work is never loaded. A description is therefore a different kind of writing from a brief. It is not instructions. It is the answer to "when is this the right thing to reach for".

  1. Write the scoring script. Each number traces to a statement in the docs: the 200-line target, emphasis that current models over-apply, prohibitions with no alternative, wording too vague to verify, and backticked paths that do not exist.

    Set-Location {{LAB}}/m20

@'
param([string]$Path)
$dir = Split-Path -Parent (Resolve-Path $Path).Path
$t = @(Get-Content $Path); $all = $t -join "`n"
$emph = [regex]::Matches($all, '\b(IMPORTANT|CRITICAL|MUST|NEVER|ALWAYS)\b').Count
$neg = @($t | Where-Object { $_ -match "\b(never|don't|do not|avoid)\b" -and $_ -notmatch '\b(instead|because|use|so that)\b' }).Count
$vague = [regex]::Matches($all, '(?i)\b(properly|appropriately|as needed|when necessary|nicely|clean|best practices|good)\b').Count
$paths = @([regex]::Matches($all, '`([^`\s]+[/\\][^`\s]+|[^`\s]+\.(md|ps1|json|ya?ml|txt|csv|sh|py|js|ts))`') | ForEach-Object { $_.Groups[1].Value } | Select-Object -Unique)
$missing = @($paths | Where-Object { $_ -notmatch '[*<>{}$]' -and $_ -notmatch '^(~|/|[A-Za-z]:|https?:)' -and -not (Test-Path (Join-Path $dir $_)) })
[pscustomobject]@{ lines = $t.Count; emphasis = $emph; bare_prohibitions = $neg; vague = $vague; missing_paths = $missing.Count; missing = ($missing -join ' ') }
'@ | Set-Content -Encoding utf8 lab5/lint.ps1
