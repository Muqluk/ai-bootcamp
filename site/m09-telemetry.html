Claude Code already counts every token it sends and receives. This module shows you the four places those counts surface, how to switch on OpenTelemetry export and send it somewhere you control, and which handful of ratios tell you that a session, a team or a pipeline has started to waste money or plan allowance.

After this module you can

  • Pick the right source for a question: the -p result JSON, the stream-json event stream, OpenTelemetry export, or /usage.
  • Turn on OpenTelemetry with the console, OTLP or Prometheus exporter, tag the data with team and cost-centre attributes, and say exactly what leaves the machine by default.
  • Name the metrics and events that carry tokens and cost, with their attributes, and sum them correctly.
  • Compute cache hit ratio, cost per session, output share, subagent share, error rate and tokens per request, and set an alert threshold for each.
  • Explain what a cost figure means on a subscription plan and on an API key, and what a plan user watches instead.
  • Take one expensive session apart request by request and say where the money went.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). Labs were verified on 2.1.322.
  • Windows PowerShell 5.1 or PowerShell 7. No collector, container or backend is needed: the labs build a 25-line receiver.
  • A free local port, 4318, bound to 127.0.0.1 only.
  • About 20 small Haiku runs. On an API key the whole module costs well under a cent; on a plan it uses a sliver of your 5-hour window.

If you skipped the prerequisites

From Tokens and their price: every API response reports four token counts. input (input_tokens) is only the part after the last cache breakpoint; cache write (cache_creation_input_tokens) is prefix written to the prompt cache; cache read (cache_read_input_tokens) is prefix served from it; output (output_tokens) is what the model generated, thinking included. Total input is read plus write plus input. On the API a cache write costs 1.25 times the base input price with the 5-minute lifetime or 2 times with the 1-hour lifetime, a cache read costs 0.1 times (0.05 on Opus 5.5 and Sonnet 5.5), and output costs 5 times input on every current model. Haiku 5.5 is $0.10 in and $0.50 out per million tokens for prompts up to 100k tokens, and $0.50 and $2.50 above that. Claude Code re-sends the whole conversation on every request, so a healthy session is mostly cache reads. A subscription plan charges a flat fee and meters usage against a 5-hour window and weekly limits; an API key pays per token.

The same counts, four views

Every number in this module starts as the usage block on an API response. Claude Code adds them up and exposes them in four places. They differ in grain (per request, per run, per session, per fleet), in who can see them, and in whether they survive after the process exits.

Check the arithmetic once so you trust it: 2 × $0.10 + 4 × $0.50 + 14,517 × $0.01 + 7,206 × $0.20 (the 1-hour write rate), all per million, is $0.00158857. The figure is computed locally from a bundled price table. costBasis says list: list price, not your bill. modelUsage splits the run by model, which matters as soon as a subagent runs on a different model from the main loop.

stream-json

The stream emits one JSON object per line: a system/init line with the tools, model and apiKeySource, then assistant and user lines as the loop runs, and a final result line identical to the JSON above. Each assistant line carries message.id, request_id and message.usage. One API response can arrive as several lines (one per content block) with the same message.id, so you count usage once per id. On a plan login the stream also carries a rate_limit_event line; Lesson 5 reads it.

OpenTelemetry

This is the only source that covers interactive sessions without anyone pasting anything, and the only one that aggregates across machines. Lessons 2 and 3 cover it.

/usage

/usage (aliases /cost and /stats) shows a Session block with total cost, API and wall duration, code changes, tokens by model, and a Prompt cache (main) line with the request count, the share of input served from cache, misses and whether the cache is warm. On a Pro, Max, Ultra, Team or Enterprise plan it adds usage bars and a breakdown of what drew on your limits over the last 24 hours or 7 days, computed from this machine's local history only. It runs headless: claude -p "/usage" returned this on a plan login, with no API call and total_cost_usd 0:

The switches

Export is off until CLAUDE_CODE_ENABLE_TELEMETRY=1. Then you pick an exporter per signal. Metrics are counters exported on an interval; events (OpenTelemetry calls them logs) are one record per prompt, API request, tool call and so on.

A Prometheus exporter serves a scrape endpoint at http://localhost:9464/metrics instead of pushing.

Will it flush before a short run exits

Yes, in 2.1.322. A headless run that lasted under two seconds exported its metrics at exit even with the default 60-second interval left alone. The short interval matters for long interactive sessions, where you want to see numbers before the session ends. What did stop output was --output-format json: with the console exporter, the JSON run printed only its result object and no telemetry, while the same run in text mode printed about 600 lines of metric and event records to stdout. OTLP export is not affected, because it goes over the network.

Tagging: team and cost centre

$env:OTEL_RESOURCE_ATTRIBUTES = 'department=engineering,team.id=platform,cost_center=eng-123'

The keys go into the OTLP resource block and onto every metric datapoint and event, so a backend can group by them as ordinary labels. Format is strict: comma-separated key=value, no spaces, no quotes, commas, semicolons or backslashes in values. Percent-encode anything else. A value with a space silently drops every key and raises no error. Each key becomes a label on every series; if a value is high-cardinality, set OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES=false to keep it in the resource block only.

Who can turn it on

Claude Code ignores the OTel exporter variables in a repository's .claude/settings.json and .claude/settings.local.json, so a cloned repo cannot start exporting your work or capture content. A repository can only turn a signal off. Set the variables in your shell, in your user settings env block, or, for a team, in managed settings (next lessons). Claude Code also does not pass OTEL_* to the Bash tool, hooks or MCP servers.

Leave the content switches off unless the collector is approved to hold source code and prompts; the counters answer every cost question without them.
Setting OTEL_EXPORTER_OTLP_PROTOCOL is easy to forget because most SDKs default it. Claude Code has no default, so an otlp exporter without it sends nothing. Run with --debug-file <path> and look for [3P telemetry] lines; a good setup logs First metrics export: SUCCESS.

Delta, not running totals

The default temporality is delta: each export carries only what happened since the last one. The OTLP payload shows "aggregationTemporality":1 (delta). To get a run's total you sum every datapoint across every export. If you switch to cumulative, you take the last value per series instead. Summing cumulative points is the commonest way to report a cost ten times too high.

Two spellings of query_source

On the two counters it is a bounded category: main, subagent or auxiliary. On events it is the raw subsystem name: the same headless run showed main on its metrics and sdk on its api_request event; interactive sessions report names such as repl_main_thread or compact. Build subagent share from the metric, and use the event value to drill in.

Version 2.1.322 also attached anthropic.plan (pro on the test login) and anthropic.provider to every record. They are not in the documented attribute list, so treat them as handy but unstable.

Totals come from the counters, explanations come from the events; join the two on session.id.
request_id on api_request matches request_id on stream-json assistant lines and requestId in the local transcript. The transcript format is internal and changes between versions, so a pipeline that joins on it breaks without warning.

Why ratios

Raw token totals grow with adoption and tell you nothing. A ratio stays flat while usage is healthy and moves when someone's habits or a pipeline's design change. Six cover almost every cost incident.

Reading each one

Cache hit ratio

Claude Code re-sends the whole conversation, so after the first request almost everything should be a cache read. A low ratio means the prefix keeps changing (tool definitions, MCP servers connecting late, a model or effort switch) or the cache expired between turns. On a plan within its usage the main conversation gets a 1-hour cache lifetime; on an API key, usage credits or a cloud provider it gets 5 minutes. A person who pauses 10 minutes between prompts on an API key pays a cache write on every prompt.

Cost per session and per task

Sessions are the unit people control (/clear starts a new session.id). Tasks are the unit your business cares about. For pipelines, put a run id or job name in OTEL_RESOURCE_ATTRIBUTES so cost per run is a single group-by. Do not use a per-run id as a metric label on a busy system; keep it on events, or set OTEL_METRICS_INCLUDE_RESOURCE_ATTRIBUTES=false.

Output share

Output is 5 times input on every current model and includes thinking. Output share climbs when effort is raised, when a prompt asks for full files back instead of edits, or when a loop writes long reports nobody reads.

Subagent share

Each subagent starts a fresh context and pays its own cache write. A rising subagent share with flat task counts usually means a skill or agent definition started fanning out. agent.name tells you which one (real names need OTEL_LOG_TOOL_DETAILS=1).

Error and retry rate

Claude Code retries internally and logs api_error only when it gives up, so every error event is a request that failed for good. Group by status_code: 429 points at rate limits, 5xx at the service, connection errors at your proxy.

Tokens per request growth

The context only grows until compaction. Watch the ratio, not the absolute value: a session at 5 times its starting size is paying for history it probably no longer needs, and the person should /clear or /compact.

Set each threshold from two weeks of your own data, then alert on change against that baseline, not on a number from a slide.
Averages hide the problem. One runaway loop at $40 disappears in a team average of $3 per session; alert on per-session maxima and percentiles.

Turning it on for a team

Put the variables in the env block of managed settings, delivered through a managed-settings.json file in the system directory, MDM, or server-managed settings from the admin console:

{
  "env": {
    "CLAUDE_CODE_ENABLE_TELEMETRY": "1",
    "OTEL_METRICS_EXPORTER": "otlp",
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "grpc",
    "OTEL_EXPORTER_OTLP_ENDPOINT": "http://collector.example.com:4317",
    "OTEL_EXPORTER_OTLP_HEADERS": "Authorization=Bearer example-token",
    "OTEL_RESOURCE_ATTRIBUTES": "department=engineering,team.id=platform"

When managed settings set the endpoint, protocol or headers, Claude Code removes conflicting developer-set per-signal variables at startup, so nobody can point one signal elsewhere. The exporter selectors follow normal precedence: a developer can still set OTEL_LOGS_EXPORTER=none unless managed settings set it too. For API-key logins there is no account identity on the records (only user.id and session.id), so set an identity attribute per user in the managed file or a launch wrapper.

What the admin consoles add

OpenTelemetry gives you raw counts as they happen. The consoles give you the billing view and data you cannot compute locally.

  • Team and Enterprise plans (claude.ai admin): a Claude Code analytics dashboard with lines accepted, suggestion accept rate, daily active users and sessions, contribution metrics from merged PRs through a GitHub integration, a leaderboard, and a spend report CSV for usage-credit spend.   • API organizations (Claude Console): the Cost page, a dedicated workspace for Claude Code with spend and rate limits, a per-member dashboard of spend and lines accepted, and the Claude Code Analytics API for daily per-user metrics with an Admin API key.

The method

A dashboard tells you a session cost five times the norm. To say why, you need it request by request. For a headless run, capture stream-json. For an interactive session, use the api_request events filtered by its session.id (Claude Code also keeps a local transcript per session, but its format is internal). Then build one row per API request.

  1. One row per response. Keep the last assistant line per message.id; take input_tokens, cache_creation_input_tokens, cache_read_input_tokens.
  2. Price each row with the model's rates, or take cost_usd from the matching api_request event via request_id.
  3. Look at the shape, not the total. Four shapes explain most expensive sessions.
Shape in the rowsCauseFix
Large cache write on many rows, not just the firstCache misses: prefix changed or the cache expired between turnsStop switching model or tools mid-session; on an API key keep turns inside 5 minutes or ask for the 1-hour lifetime
Cache read climbing steadily into the hundreds of thousandsContext growth: big tool results kept in history/compact or /clear; narrower reads; check tool_result_size_bytes
Many rows, small growth eachA tool loop: retries, polling, one-file-at-a-time editsLower --max-turns, better instructions, batch the work
Few rows, high outputLong generations or high effortAsk for diffs, lower /effort

A real two-request run

A Haiku run that read a 30-line CSV and answered one question made two API requests. Lab 3's script printed:

req input cacheWrite cacheRead output hitPct  costUsd
--- ----- ---------- --------- ------ ------  -------
  1     2       4552     17191     16   79.1 0.001091
  2     2        500     21743      8   97.7 0.000322

requests:            2
cache hit ratio:     88.5%
computed cost:       0.001413 USD
result total_cost:   0.001481 USD
output, stream lines: 24
output, result:       161

Read it like this. Request 1 paid a 4,552-token cache write: part of the system prompt was not cached yet. Request 2 re-sent everything plus the tool result; only the new 500 tokens were written and the rest was read at a tenth of the price. Three-quarters of the run's cost sat in request 1. A second run minutes later showed 0 cache writes and 100% hit on both requests, at a third of the cost: the cache was warm.

The output gap

The computed total came out about 5% low. The output_tokens on stream-json assistant lines is the count when the message started streaming (16 and 8 here), not the final count; the result line's modelUsage had 161 output tokens, thinking included. Take input and cache figures per request from the stream, and output totals from the result line or from the api_request events.

Other clues in the stream

  • user lines hold the tool results the model saw; their size explains growth in the next row.
  • The result line's subagent_stats counts subagents spawned, completed and failed; modelUsage splits cost by model.
  • system lines with subtype thinking_tokens give a running estimate of thinking.
Explain a cost by its worst request and the reason for it, not by the session total.
Summing every assistant line double-counts responses that span several content blocks. Deduplicate on message.id first.

Run one headless prompt with the console exporter and pull the four token counts and the cost out of its output, then compare with /usage.

  1. Make the lab folder. Every headless run in this module carries --setting-sources project --strict-mcp-config: the first keeps your user settings and hooks out of the run, the second ignores every MCP server not passed on the command line. Together they make the numbers you measure reproducible and keep your personal tools out of them.

    New-Item -ItemType Directory -Force {{LAB}}/m9 | Out-Null
Set-Location {{LAB}}/m9

    Expected: no output; your prompt is in the lab folder.

  2. Turn telemetry on for this PowerShell window only, with the console exporter and short intervals.

    $env:CLAUDE_CODE_ENABLE_TELEMETRY = '1'
$env:OTEL_METRICS_EXPORTER = 'console'
$env:OTEL_LOGS_EXPORTER = 'console'
$env:OTEL_METRIC_EXPORT_INTERVAL = '1000'
$env:OTEL_LOGS_EXPORT_INTERVAL = '1000'

    Expected: no output.

  3. Run one prompt in text mode and send everything to a file.

    claude -p "Reply with the single word: ready" --model haiku --setting-sources project --strict-mcp-config --max-turns 1 > console.txt
(Get-Content console.txt).Count

    Expected: about 600 lines. The word ready is in there among JavaScript-style object dumps.

  4. List the metric and event names.

    Select-String -Path console.txt -Pattern 'name: "claude_code\.', 'body: "claude_code\.' | ForEach-Object { $_.Line.Trim() }

    Expected: events managed_settings_resolved, plugin_loaded (several), user_prompt, api_request, assistant_response; metrics session.count, cost.usage, token.usage, active_time.total.

  5. Pull out the four token types and the cost.

    Select-String -Path console.txt -Pattern 'type: "(input|output|cacheRead|cacheCreation)"' -Context 0,4 |
  ForEach-Object { '{0,-30} {1}' -f $_.Line.Trim(), ($_.Context.PostContext | Where-Object { $_ -match 'value:' }).Trim() }
Select-String -Path console.txt -Pattern 'cost_usd:' | ForEach-Object { $_.Line.Trim() }

    Expected: input 2, output 4, cacheRead about 17,000 to 22,000, cacheCreation 0 to about 7,000 depending on whether the cache was warm; cost_usd about 0.0002 warm or 0.001 to 0.0016 cold.

  6. Run the same prompt with --output-format json and count the telemetry lines.

    claude -p "Reply with the single word: ready" --model haiku --setting-sources project --strict-mcp-config --max-turns 1 --output-format json > console-json.txt
(Get-Content console-json.txt).Count
(Select-String -Path console-json.txt -Pattern 'claude_code\.').Count

    Expected: 1 line, 0 telemetry mentions. The JSON output mode keeps stdout clean and the console exporter prints nothing. Use text mode with the console exporter.

  7. Check /usage headless, then close this PowerShell window to drop the variables (or set each one to $null).

    claude -p "/usage" --model haiku --setting-sources project --strict-mcp-config --max-turns 1

    Expected: on a plan login, You are currently using your subscription…, then Current session: N% used and weekly lines with reset times, then the 24-hour and 7-day breakdown. It makes no API call.

Self-check

  1. Write the receiver. It accepts POSTs on /v1/metrics and /v1/logs, appends each body as one line to metrics.jsonl or logs.jsonl, and exits on a request to /stop.

    param([int]$Port = 4318, [string]$OutDir = '.')
$l = [System.Net.HttpListener]::new()
$l.Prefixes.Add("http://127.0.0.1:$Port/")
$l.Start()
while ($l.IsListening) {
  $ctx = $l.GetContext()
  $path = $ctx.Request.Url.AbsolutePath
  if ($path -eq '/stop') { $ctx.Response.StatusCode = 200; $ctx.Response.Close(); break }
  $reader = [IO.StreamReader]::new($ctx.Request.InputStream, [Text.Encoding]::UTF8)
  $body = $reader.ReadToEnd() -replace "`r?`n", ' '
  $file = switch ($path) { '/v1/metrics' { 'metrics.jsonl' } '/v1/logs' { 'logs.jsonl' } default { 'other.jsonl' } }
  Add-Content -Path (Join-Path $OutDir $file) -Value $body -Encoding utf8
  $bytes = [Text.Encoding]::UTF8.GetBytes('{}')
  $ctx.Response.StatusCode = 200
  $ctx.Response.ContentType = 'application/json'
  $ctx.Response.OutputStream.Write($bytes, 0, $bytes.Length)
  $ctx.Response.Close()
}
$l.Close()

  3. Write the analysis script. Rates default to Haiku 5.5 per million tokens; pass others for another model.

    param([string]$File = 'run.jsonl', [double]$In = 0.10, [double]$Out = 0.50, [double]$CacheWrite1h = 0.20, [double]$CacheWrite5m = 0.125, [double]$CacheRead = 0.01)
$seen = @{}; $rows = @(); $result = $null
foreach ($line in Get-Content $File) {
  $e = $line | ConvertFrom-Json
  if ($e.type -eq 'result') { $result = $e }
  if ($e.type -ne 'assistant') { continue }
  $id = $e.message.id
  if ($seen.ContainsKey($id)) { continue }   # one API response can arrive as several lines
  $seen[$id] = $true
  $u = $e.message.usage
  $cw1h = [double]$u.cache_creation.ephemeral_1h_input_tokens
  $cw5m = [double]$u.cache_creation.ephemeral_5m_input_tokens
  $allIn = $u.input_tokens + $u.cache_read_input_tokens + $u.cache_creation_input_tokens
  $cost = ($u.input_tokens * $In + $u.output_tokens * $Out + $cw1h * $CacheWrite1h + $cw5m * $CacheWrite5m + $u.cache_read_input_tokens * $CacheRead) / 1e6
  $rows += [pscustomobject]@{
    req = $rows.Count + 1; input = $u.input_tokens; cacheWrite = $u.cache_creation_input_tokens; cacheRead = $u.cache_read_input_tokens; output = $u.output_tokens
    hitPct = [math]::Round(100 * $u.cache_read_input_tokens / [math]::Max($allIn, 1), 1); costUsd = [math]::Round($cost, 6)
  }
}
$rows | Format-Table -AutoSize | Out-String -Width 200
$tin = ($rows | Measure-Object input -Sum).Sum; $tcw = ($rows | Measure-Object cacheWrite -Sum).Sum; $tcr = ($rows | Measure-Object cacheRead -Sum).Sum
'requests:            {0}' -f $rows.Count
'cache hit ratio:     {0:P1}' -f ($tcr / ($tin + $tcw + $tcr))
'computed cost:       {0:N6} USD' -f ($rows | Measure-Object costUsd -Sum).Sum
'result total_cost:   {0:N6} USD' -f $result.total_cost_usd
'cost per request:    {0:N6} USD' -f ($result.total_cost_usd / $rows.Count)
$mu = $result.modelUsage.PSObject.Properties | ForEach-Object { $_.Value }
'output, stream lines: {0}' -f ($rows | Measure-Object output -Sum).Sum
'output, result:       {0}' -f ($mu | Measure-Object outputTokens -Sum).Sum
foreach ($line in Get-Content $File) {
  $e = $line | ConvertFrom-Json
  if ($e.type -eq 'rate_limit_event' -and $e.rate_limit_info.unifiedWindows) {

    '5-hour window used: {0:P0}   7-day window used: {1:P0}' -f $w.five_hour.utilization, $w.seven_day.utilization

Measure per-session ratios from captured events, choose three thresholds from your own numbers, and end with a checker that exits 1 when any rule fires.

  1. Write a per-session measurement script over the api_request and api_error events in logs.jsonl (from Lab 4, or a capture of your own work with the Lab 2 receiver).

    param([string]$File = 'logs.jsonl')
function Get-Attr($rec) { $a = @{}; foreach ($kv in $rec.attributes) { $v = $kv.value; $a[$kv.key] = if ($null -ne $v.stringValue) { $v.stringValue } elseif ($null -ne $v.intValue) { [double]$v.intValue } elseif ($null -ne $v.doubleValue) { [double]$v.doubleValue } else { $v.boolValue } }; $a }
$s = @{}
foreach ($line in Get-Content $File) {
  foreach ($rec in ($line | ConvertFrom-Json).resourceLogs.scopeLogs.logRecords) {
    $name = $rec.body.stringValue
    if ($name -notin 'claude_code.api_request', 'claude_code.api_error') { continue }
    $a = Get-Attr $rec; $id = $a['session.id']
    if (-not $s[$id]) { $s[$id] = [ordered]@{ session = $id.Substring(0, 8); requests = 0; errors = 0; input = 0; cacheRead = 0; cacheWrite = 0; output = 0; costUsd = 0 } }
    if ($name -eq 'claude_code.api_error') { $s[$id].errors++ ; continue }
    $s[$id].requests++; $s[$id].input += $a.input_tokens; $s[$id].cacheRead += $a.cache_read_tokens
    $s[$id].cacheWrite += $a.cache_creation_tokens; $s[$id].output += $a.output_tokens; $s[$id].costUsd += $a.cost_usd
  }
}
foreach ($x in $s.Values) {
  $allIn = $x.input + $x.cacheRead + $x.cacheWrite
  [pscustomobject]@{
    session = $x.session; requests = $x.requests
    cacheHitRatio = [math]::Round($x.cacheRead / [math]::Max($allIn, 1), 3)
    costPerSession = [math]::Round($x.costUsd, 6)
    inputPerRequest = [math]::Round($allIn / [math]::Max($x.requests, 1))
    errorRate = [math]::Round($x.errors / [math]::Max($x.requests + $x.errors, 1), 3)
  }
}
