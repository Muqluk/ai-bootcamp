A skill is a folder with a SKILL.md file that Claude Code advertises to the model in one line and loads in full only when it is used. That makes it the cheapest place to keep procedures, runbooks and reference material that the model needs some of the time, and the wrong place for anything that must hold every time. This module shows how the loading works, what each layer costs, and how to make a skill fire when it should and stay quiet when it should not.

After this module you can

  • Write a project skill, prove from the headless init line that it is listed, and invoke it both by name and by letting the model choose.
  • Measure what a skill costs in context per request while it is only listed, and what it adds once invoked.
  • Write a description that triggers on the prompts you mean and not on neighbouring ones, and count hits to prove it.
  • Bundle a script with a skill so that the work runs outside the context window, and grant it the permissions it needs without a prompt.
  • Decide between a skill, a CLAUDE.md line, a hook and a subagent for a given requirement, and move a block out of CLAUDE.md with a measured saving.
  • Review a third-party skill for what it can run on your machine before you let it load.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The numbers here were taken on 2.1.322.
  • Windows PowerShell 5.1 or PowerShell 7. Every lab runs in its own folder under {{LAB}}/m3 and touches nothing outside it.
  • About 20 short Haiku runs across all labs. On an API key that is well under a dollar; on a plan it is a small draw on your 5-hour window.

If you skipped the prerequisites

From Context: the model has no memory between requests, so Claude Code re-sends the whole working context on every request: a system prompt, the tool definitions, your CLAUDE.md files, the skill listing, and the conversation so far. An agent turn can be several requests (one per tool call), and each one carries all of it. Anything that loads at session start is therefore paid on every request for the rest of the session, not once. Prompt caching makes the repeated part cheap (a cache read costs a tenth of fresh input or less) but not free, and it still occupies the context window. When the window fills, Claude Code compacts: it replaces the conversation with a summary and re-attaches selected material. /context shows the live breakdown by category, and claude -p "/context" prints it headless.

Three layers, loaded at three different times

A skill is a directory whose name is the skill's name, containing a SKILL.md file: YAML frontmatter between --- lines, then markdown instructions. Claude Code never puts the whole directory in front of the model at once. It discloses the skill in layers, and each layer has a different cost profile.

LayerWhat it isWhen it enters contextHow long it stays
ListingThe skill name plus description and when_to_use, capped at 1,536 characters per skillSession startEvery request of the session
BodyThe rendered markdown of SKILL.md, after argument substitution and shell injectionWhen you type /name or the model calls the Skill toolFrom then on, as one message in the conversation; Claude Code does not re-read the file
Supporting filesOther markdown files in the folder that SKILL.md links toWhen the model decides to read one with the Read toolLike any file read: in the conversation from then on
ScriptsPrograms in the folder that the body tells the model to run, or that shell injection runsNever. Only their output enters contextThe output stays like any tool result

This is the whole point of a skill.

A 30 KB runbook in CLAUDE.md costs its full size on every request. The same runbook as a skill costs one line until somebody needs it.

What that costs on a plan and on an API key

The listing is part of the stable prefix, so after the first request it is almost always a cache read. On an API key that is 0.1x the model's input price, or 0.05x on Opus 5.5 and Sonnet 5.5. A 300-token listing entry read 1,000 times on Opus 5.5 ($4 per million input) is 300,000 cache-read tokens at $0.20 per million: about six cents. Thirty such skills is about $1.80 per 1,000 requests, for skills that may never fire. On a subscription plan there is no per-token bill; the same tokens draw down your 5-hour window and weekly limits, and cached tokens count less against them than fresh ones. Either way, the tokens also sit in the context window.

The body is a different animal. Once invoked it stays in the conversation, so 11,000 tokens of body are re-sent on every later request until the session ends or compacts. The first request after invocation pays them as cache write (1.25x for a 5-minute cache, 2x for 1-hour), later ones as cache read.

Spend characters in the description only on words that change when the model picks the skill; spend lines in the body only on instructions the task needs every turn after it loads.

After compaction

When the conversation is compacted, Claude Code re-attaches the most recent invocation of each skill after the summary, keeping the first 5,000 tokens of each, inside a combined budget of 25,000 tokens filled from the most recently invoked skill backwards. A long body loses its tail; in a session that invoked many skills, older ones can drop out entirely.

A skill whose critical rule sits at line 400 of a long body works on the first turn and quietly stops working after the first compaction. Put the rules that must survive in the first screenful, and move long reference material into supporting files.

The file

Everything in the frontmatter is optional. Only description is recommended, and without it Claude Code uses the first non-empty line of the body. Field names are lowercase with hyphens, except when_to_use. A misspelt field is ignored without an error, and frontmatter that does not parse leaves the skill loaded with no fields set. The opening --- must be the first line of the file.

---
description: Formats an incident note for the ops ticket queue. Use when the user asks to log, file or write up an outage, alert or incident as a ticket.
---
Reply with exactly one line in this form and nothing else:

TICKET | <host> | <P1-P4> | <summary of at most ten words>

Severity: P1 service down, P2 degraded, P3 warning, P4 information.

That is a complete skill. The fields that change behaviour, grouped by what they control:

Seeing what loaded, headless

The first line of --output-format stream-json --verbose is the init event. Its skills array lists every skill the session can use (yours plus the bundled ones for your version), and slash_commands lists the names you can type. That is the scriptable proof that a skill loaded. Note that --setting-sources must include project for project skills to load, and that bare mode and --disable-slash-commands turn skills off.

How the model picks a skill

The model sees the skill listing as part of its context, next to the Skill tool. Picking a skill is an ordinary tool-choice decision: the model reads the user's request, compares it with the descriptions it can see, and calls the Skill tool with a skill name and arguments if one fits. There is no keyword matcher underneath. The description is the only evidence the model has, so its wording is the trigger.

When you type /ticket-note web-01 nginx down at the start of a message, there is no decision: Claude Code expands the body before the model sees the request. In the first lab that run takes one turn and no tool call. When the model chooses, the stream shows a tool_use block named Skill with input like {"skill":"ticket-note","args":"..."}. A /name later in a sentence does not run the skill; it counts as your permission for the model to run it in that message.

Writing the description

  • Lead with the use case. The combined description and when_to_use is cut at 1,536 characters in the listing (skillListingMaxDescChars changes the cap), and under budget pressure it may be dropped entirely. The first sentence must carry the decision.
  • Use the user's words, not yours. People say "bounce web-02" and "is the site up", not "execute node lifecycle procedure".
  • Name the near-misses. "Not for rotating or shipping logs" keeps a log-counting skill out of a logrotate request.
  • Put trigger phrases in when_to_use when you want them separate from the summary. They are appended to the description in the listing and share its cap.
  • Avoid angle brackets. They display as &lt; and &gt;; write [branch] or use argument-hint.

If the model tries to run a manual-only skill anyway, Claude Code blocks the call and tells it not to reproduce the steps another way. Without editing the file, the skillOverrides setting sets a skill to "on", "name-only" (listed without description), "user-invocable-only" or "off"; it does not apply to plugin skills.

The listing budget

The listing always contains every skill name, but the descriptions must fit a budget of 1% of the model's context window. When they do not, Claude Code drops descriptions starting with the skills you invoke least, and writes a warning to the debug log (--debug). A skill whose description was dropped is listed by name only, which leaves the model nothing but the name to match against. Raise the budget with skillListingBudgetFraction (for example 0.02) or a fixed character count in SLASH_COMMAND_TOOL_CHAR_BUDGET, or free it by setting rarely used skills to "name-only" or manual-only. /skill-doctor reports each skill's cost and how often it was used.

Test every description against two prompts that should fire it and two neighbours that should not, and keep the four as a regression set.
A skill that "stopped working" after you installed a plugin with forty skills has often lost its description to the listing budget. It still shows in the / menu, so nothing looks wrong until you check the debug log or /context.

Scripts are run, not loaded

A skill folder can carry anything: reference markdown, templates, scripts in any language. A script costs context only through its output. In the fourth lab a 110 KB log with 2,000 lines is counted by a three-line PowerShell script that prints ERRORS=37 RUN=8714; the whole session's total input stays at about 21,900 tokens, the same as an empty session. Had the model read the log instead, it would have added tens of thousands.

There are two ways to run a bundled script:

MechanismSyntax in the bodyWho runs itWhen
Shell injection!`command` at line start or after whitespace, or a fenced block opened with ```!Claude Code, before the model sees the bodyEvery invocation, while the body renders
Instruction"Run ${CLAUDE_SKILL_DIR}/scripts/x.ps1"The model, through the Bash or PowerShell toolWhen the model decides to

Injection is deterministic: the output replaces the placeholder and the model receives data, not a suggestion. A failing injected command (non-zero exit) aborts the whole invocation with Shell command failed for pattern "...", so append || true to checks that exit 1 on findings. Injected commands never prompt: each is checked against your permission rules and the skill's allowed-tools, and anything short of allow aborts the invocation. ${CLAUDE_SKILL_DIR} resolves to the skill's own folder wherever it is installed; use it rather than relative paths, because commands run in the session's current directory.

---
description: Counts ERROR lines in app.log with a bundled script. Use when the user asks how many errors app.log has.
allowed-tools: Bash(powershell *) PowerShell(powershell *)
---
Error count from the bundled script:

!`powershell -NoProfile -ExecutionPolicy Bypass -File "${CLAUDE_SKILL_DIR}/scripts/count.ps1" app.log`

Reply with that ERRORS= line exactly and nothing else. Do not open app.log yourself.

The allowed-tools line lists both shell tools because which one runs injected commands depends on the machine: the Bash tool when Git Bash is present, otherwise the PowerShell tool. shell: powershell forces the PowerShell tool when it is enabled.

allowed-tools grants, it does not restrict

The field pre-approves the listed tools for the turn that invokes the skill; the grant clears at your next message. It does not remove any other tool, and your deny and ask rules still win. Use disallowed-tools to take tools away while the skill is active.

One consequence shows up headless. A skill that carries allowed-tools is itself a permission decision, so when the model (not you) invokes it in default permission mode, the Skill call needs approval. In the fourth lab the model's call to log-count came back in permission_denials as Skill {"skill":"log-count"}, and the model fell back to counting the log with Grep. The plain ticket-note skill with no allowed-tools needed no grant. Adding --allowedTools "Skill(log-count)" fixed it: three turns, no denials, and the script's nonce in the answer.

A headless job that "works when I type /log-count" and does something else when the model picks the skill is often a denied Skill call. Read permission_denials in the JSON result before you blame the description.

Running a skill somewhere else: context: fork, agent, model

context: fork starts a new subagent and gives it the rendered body as its prompt. The subagent does not see your conversation, so the body must be a complete task, not guidelines; a fork of "use these API conventions" returns nothing useful. The agent field picks the subagent type: Explore and Plan start without CLAUDE.md and git status, general-purpose (the default) or a custom agent from .claude/agents/ loads CLAUDE.md. Only the subagent's final report comes back into your context, which is the point: a skill that reads forty files to answer one question should fork. Interactively a fork runs in the background unless you set background: false; under -p the caller always waits for it.

model sets the model for the rest of the current turn (the session model returns at your next prompt), or the forked subagent's model with context: fork. effort works the same way. Together they let a mechanical skill (formatting, counting, summarising a diff) run on haiku while the session stays on a larger model. On an API key that is a direct price cut, since Haiku 5.5 input is $0.10 per million against $4 for Opus 5.5. On a plan it spends less of your limits per task.

Fork a skill when its working material is large and its answer is small; keep it inline when the model needs it alongside the conversation.

Four mechanisms, four guarantees

These overlap in what they can express and differ sharply in when they load and whether the model can ignore them. Choose by the guarantee you need, not by convenience.

CLAUDE.mdSkillHookSubagent

EnforcedNo, it is adviceNo, it is adviceYes: can block a tool call or a promptNo; isolates work

Best forFacts every task needs: build command, layout, "never do X"Procedures and reference needed some of the timeRules that must hold every timeLarge reading or searching with a small answer

Decision rules

  • Must happen every time, or must never happen: a hook. A line in CLAUDE.md or a skill is a request. If a skill needs a hard rule while it is active, declare the hook in the skill's hooks frontmatter; it registers on invocation and stays for the session.
  • Needed on most tasks and short: CLAUDE.md. Keep the file under about 200 lines; anything that is a procedure rather than a fact belongs in a skill.
  • Needed on some tasks, or long: a skill. Leave a one-line pointer in CLAUDE.md ("For a release, use the release-runbook skill") if you want the model to think of it.
  • Lots of input, little output: a subagent, or a skill with context: fork when the task is reusable and you want /name to start it.
  • Has side effects: a skill with disable-model-invocation: true, so it runs only when you type /name.

What moving a block saves

The fifth lab takes a 126-line CLAUDE.md, moves the 120-line release runbook into a skill, and leaves 5 lines plus a pointer. Total input for a one-word reply falls from about 28,500 to about 22,000 tokens: about 6,500 tokens off every request. The skill's listing entry costs about 50 of those back. An agent turn with eight tool calls is eight requests, so that is roughly 52,000 fewer tokens per turn on work that never touches a release.

If a CLAUDE.md section is a procedure with numbered steps, it is a skill that has not been extracted yet.
Moving a hard rule ("never push to main") out of CLAUDE.md into a skill makes it weaker, not leaner: it is now absent until something invokes the skill. Hard rules go to hooks; short standing rules stay in CLAUDE.md.

Run tests in fresh sessions. The session you wrote the skill in already knows what you meant, which hides gaps in the written instructions. For plugin skills, claude plugin eval automates the with-and-without comparison and can gate CI; Plugins and marketplaces covers it. claude plugin validate .claude/skills finds SKILL.md files whose frontmatter does not parse, which otherwise fail silently (the skill loads with no description and never triggers).

Surviving long sessions

Two things make a skill fade during a session. First, the body enters the conversation once and is not re-read, so "Run the tests" is followed once while "Run the tests after every edit" stays a standing instruction. Write the body as standing rules. Second, compaction keeps only the first 5,000 tokens of each invoked skill, within 25,000 shared. If the model stops following a skill after a compaction, invoking it again restores the full body. To test this interactively, invoke the skill, run /compact, then ask for something only the tail of the body covers.

Maintenance

  • Treat the description like an interface. Changing it changes when the skill fires; re-run the trigger set after every edit.
  • Prune. Every listed skill costs its listing line on every request whether or not it is used. /skill-doctor flags skills that were never invoked, ordered by cost.
  • Keep SKILL.md under about 500 lines and push detail into linked supporting files, so the body that loads (and survives compaction) is the part that matters.

The trust question

A skill is code you run, not documentation you read. Before you let a third-party skill load, read it for these:

Look forWhy it matters
!`...` lines and ```! blocksRun on your machine every time the skill renders, before the model or you see anything
allowed-toolsPre-approves tools for that turn; applied to a project skill even in a -p run in a folder you never trusted
hooksRegister on first invocation and run for the rest of the session
Scripts in the folderRun with your rights when the body tells the model to run them
A broad description with no near-miss exclusionsFires on more of your work than you expect, carrying the above with it

Controls that help: "disableSkillShellExecution": true in settings replaces every injected command from user, project, plugin and added-directory skills with a placeholder (most useful in managed settings); Skill(name) deny rules in permissions block specific skills; disable-model-invocation: true or skillOverrides keep a skill manual-only. A cloned repository's .claude/skills/ is the same risk as its Makefile: read it before you run Claude Code there.

Read every ! line, every allowed-tools entry and every script before a third-party skill goes into a folder Claude Code will run in.

You write a one-file project skill, prove from the init event that it loaded, and run it once by name and once by letting the model choose it.

  1. Create the lab folder and the skill. A project skill lives in .claude/skills/<name>/SKILL.md under the folder you start Claude Code in.

Every headless run in this module uses --setting-sources project --strict-mcp-config: the first loads only this folder's settings and skills, not your personal ones, and the second ignores every MCP server you have configured. Together they keep your own setup out of the measurement. --model haiku keeps the runs cheap.

    $events = claude -p "Log this as a ticket: the disk on db-02 is at 91 percent" --model haiku --setting-sources project --strict-mcp-config --output-format stream-json --verbose --max-turns 3 | ForEach-Object { $_ | ConvertFrom-Json }
$events | Where-Object { $_.type -eq 'assistant' } | ForEach-Object { $_.message.content } | Where-Object { $_.type -eq 'tool_use' } | ForEach-Object { "tool_use: $($_.name) $($_.input | ConvertTo-Json -Compress)" }
($events | Where-Object { $_.type -eq 'result' }).result

    Expected: tool_use: Skill {"skill":"ticket-note","args":"Log a ticket: the disk on db-02 is at 91 percent"} (the args wording varies), then TICKET | db-02 | P3 | Disk on db-02 at 91 percent capacity.

Self-check

1. Why did step 3 take one turn while step 4 needed a tool call? Typing /ticket-note at the start of the prompt expands the body before the request goes out; in step 4 the model had only the description and had to call the Skill tool to load the body.

2. Which field in the init event would you check in a CI job to fail fast when a skill did not load? skills (or slash_commands for user-invocable ones).

3. Your own personal skills did not appear in the list. Why? --setting-sources project leaves out the user source, so ~/.claude/skills was not read.

  2. Define a helper that runs one prompt in one folder and returns total input tokens (input plus cache write plus cache read).
