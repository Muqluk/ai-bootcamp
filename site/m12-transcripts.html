Every Claude Code session writes a JSONL file: one JSON object per line, holding the conversation, the tool results, the token usage of each API call and a final cost record. It is the most complete record of what a session did and what it cost, and it sits on your disk in plain text. This module shows how to find it, read each line type, walk the message chain, add up usage without double counting, and where the format stops being trustworthy.

After this module you can

  • Locate the transcript of any session from its cwd and session id, and from a hook's transcript_path.
  • Name the line types in a transcript and the envelope fields shared by user, assistant and attachment lines.
  • Walk the parentUuid chain from the last line back to the first prompt.
  • Total a session's tokens by deduplicating on message.id, and reconcile the total against total_cost_usd.
  • Explain what resume, fork, compaction and subagents do to the files, and what each leaves out.
  • State what a transcript is good for, what it exposes about you, and why you must not build a long-lived tool on its format.

What you need

  • Claude Code 2.1 or later, signed in (subscription plan or API key). Measurements here were taken on Claude Code 2.1.322.
  • PowerShell 5.1 or later. The labs parse JSONL with ConvertFrom-Json.
  • A scratch folder, written {{LAB}}/m12.

If you skipped the prerequisites

Context: the model sees one growing message list per session, plus a system prompt and tool definitions that are resent with every request. Tokens: usage splits into four types, input (uncached), output, cache write and cache read. Cache reads are cheap, cache writes cost more than plain input (a 1-hour write costs twice the input price), and output is the most expensive per token. A tool-using turn makes several API calls, one per model step, and each call re-reads the whole prefix from cache. This is why a short task can show a large cache-read count and a tiny cost. A headless run with --output-format json returns a usage block and total_cost_usd for the whole run; the transcript holds the same numbers one request at a time.

The path

Claude Code stores each session as ~/.claude/projects/<project>/<session-id>.jsonl. The <project> folder name is the session's working directory with every non-alphanumeric character replaced by a hyphen. Observed on Claude Code 2.1.322: a session started in a folder ending ai-bootcamp-labs\m12 was stored under a folder name ending -ai-bootcamp-labs-m12. The docs add that names over 200 characters are truncated and given a hash suffix.

Two environment variables move things. CLAUDE_CONFIG_DIR relocates the whole ~/.claude tree, transcripts included. CLAUDE_CODE_PROJECT_DIR_NAME (2.1.234 and later, only together with CLAUDE_CONFIG_DIR) sets the project folder name yourself.

What lives next to the file

  • <session-id>/subagents/: one transcript per subagent run.
  • <session-id>/tool-results/: large tool outputs spilled out of the main file.
  • file-history/<session-id>/: the file snapshots used by checkpointing.

Retention

The setting cleanupPeriodDays defaults to 30 days and has a minimum of 1; 0 is rejected as a validation error. The sweep deletes the session file, its subagents and tool-results folders, any .orphaned-* or .superseded-* copies, and the matching file-history folder. If you want to keep transcripts for audit, copy them out before the sweep, or raise the setting.

A transcript is a file you can find without asking Claude Code: derive the path, or have a hook hand it to you.
Headless -p sessions write transcripts too, but they do not appear in the interactive resume picker. Missing from the picker does not mean missing from disk. --no-session-persistence (print mode only) is the flag that suppresses the file.

The docs say little, on purpose

The Claude Code docs state that the entry format is internal and changes between versions, and point you to /export and the script interfaces instead. Everything in this lesson about line types is therefore observed on Claude Code 2.1.322 on a subscription login, from lab sessions. Treat the names as a snapshot.

The envelope

User, assistant and attachment lines share these fields: parentUuid, isSidechain, type, uuid, timestamp, userType, entrypoint (sdk-cli for a headless run), cwd, sessionId, version and gitBranch. Outside a git repo, gitBranch read HEAD.

assistant.message

The message object mirrors an API response: model, id (msg_...), content, stop_reason and usage. The key observation: each assistant line carries exactly one content block, either thinking, text or tool_use. A response with a thinking block and a tool call becomes two lines that share one message.id and one identical usage object. Lesson 4 turns this into a trap.

Privacy

Two kinds of line hold identity. session-owner carries an account id and an organization id. A session_context attachment carried the signed-in email address in clear. Neither appears in this module; examples use 11111111-2222-... and user@example.com. The docs state transcripts are plaintext, not encrypted at rest, protected by operating system permissions only, and that they include file contents, command output, pasted text, the system prompt, tool definitions and CLAUDE.md. A credential printed by any tool lands in the file.

Redact before sharing a transcript: owner ids, email, anything a tool printed.
Do not paste a transcript, or a line of one, into a ticket or a chat. The first line you copy may be an identity line.

A linked list, not an array

Each conversation line has a uuid and a parentUuid. The first line has a null parent; every other line points at the line before it. File order is usually the same as chain order, but the file is an append-only log and the chain is the truth. A last-prompt line records leafUuid, the newest conversation line, so you can start there and walk backward to rebuild the exact message list.

$byId = @{}; foreach ($l in $lines) { if ($l.uuid) { $byId[$l.uuid] = $l } }
$cur = $byId[$leafUuid]
while ($cur) { $cur; $cur = $byId[$cur.parentUuid] }   # newest to oldest

Why the chain matters

  • Parallel tool calls: if the model emits two tool_use blocks in one response, they are two assistant lines. Observed: the tool-result user line for the first call sat between the two assistant lines in the parent chain. File order and chain order are both worth checking.
  • Tool results link back: a tool-result user line carries sourceToolAssistantUUID, the assistant line whose tool_use it answers.
  • Branches: a chain can fork when a conversation is rewound or resumed from an earlier point. The older branch stays in the file; only the branch ending at the leaf is what the model sees next.
  • isSidechain marks lines that belong to a side conversation such as a subagent rather than the main thread.

Outline view

For debugging, reduce each chain line to one row: timestamp, type, and the first 60 characters of text, the tool name, or the tool result summary. That is a faithful replay of a session in a screenful, and it is what lab 2 builds.

To reconstruct a session, start at the leaf and follow parentUuid; do not trust line order alone.
Counting lines is not counting turns. In the lab, num_turns was 6 while the file had 5 api-request lines and 9 assistant lines.

Where the numbers are

Every assistant line carries message.usage: input_tokens, output_tokens, cache_creation_input_tokens, cache_read_input_tokens, a cache_creation object splitting 1-hour and 5-minute writes, service_tier, and a few more fields. The last line of the file, cost-state, has the session's totalCostUSD and a modelUsage object per model.

The trap

The SDK cost-tracking doc says that assistant messages from one response share a message.id and identical usage, and that you must deduplicate by id. The transcript shows why. In a lab run with five API calls, three responses had a thinking block plus a tool call and one had two parallel tool calls, so there were nine assistant lines for five message ids.

ResponseBlocksOutputCache writeCache read
Atool_use, tool_use1707,23814,517
Bthinking, tool_use39830321,755
Cthinking, tool_use27944422,058
Dthinking, tool_use24138822,502
Etext11127122,890

Each response had 2 uncached input tokens. Summed once per message.id: input 10, output 1,199, cache write 8,644 (all 1-hour), cache read 103,722. Those four numbers matched result.usage from the headless JSON and the cost-state line exactly. Summing every assistant line instead counts responses A to D twice and overstates the session.

Reconciling the price

At the Haiku 5.5 list prices used in the lab, per million tokens ($0.10 input, $0.50 output, $0.20 for a 1-hour cache write, $0.01 for a cache read), the deduplicated totals price to $0.00336652, equal to the run's total_cost_usd. The price check works only with the right sum, which makes it a good test of your script.

The SDK doc also says per-step output_tokens can be a placeholder from the start of the stream. On Claude Code 2.1.322 the transcript values were final in this lab: the deduplicated output matched the final result. Verify on your version before relying on either behavior.

Subscription plans and API keys read the same transcript. On a plan the dollar figure is list-price equivalent, not a charge; the number that matters there is the share of your window the tokens consumed. The token counts are the same either way.

Resume and continue

--resume takes a session id, a name, or an absolute path to a .jsonl. --continue resumes the most recent session in the folder; headless runs are excluded from a plain --continue but included in claude -p --continue. --session-id lets you choose the uuid up front. Resuming appends to the same file, so two terminals resuming one id interleave their lines into one transcript.

--fork-session, used with resume, starts a new session id with a copy of the history, so the original file stays as it was.

Compaction

When context fills, or on /compact, the history is replaced by a summary in what the model sees. The transcript is a log, so the older lines are still in the file unless garbage collection removes them. CLAUDE_CODE_TRANSCRIPT_LOCAL_GC=1 (2.1.287 and later) makes a file over 5 MB drop pre-compaction history after a compaction. I did not observe a compaction marker line type in the lab runs, so the module does not name one. If you need to know, run a compaction on a throwaway session and diff the type counts.

Subagents

Each subagent run gets its own transcript at <session-id>/subagents/agent-<id>.jsonl, and the SubagentStop hook receives the path as agent_transcript_path. The cost-tracking doc says result.usage excludes subagent usage, while total_cost_usd and modelUsage include it. A total built only from the main file therefore undercounts a session that used subagents. Observed on 2.1.322 (lab 4): modelUsage equalled the main file plus the subagent file field for field, while the top-level result.usage matched neither.

Limits

  • The format is undocumented and internal. The docs say it changes between versions. The fields in this module are observed on Claude Code 2.1.322; write scripts that check for a field and fail loudly, not ones that assume it.
  • The transcript is written asynchronously. Inside a Stop hook, use last_assistant_message from the hook input; the file may not hold the last line yet.
  • Retention is 30 days by default.
  • Telemetry is the supported channel for continuous cost and usage metrics; the transcript is for after-the-fact forensics on one session.

Controls

claude purge <path> removes stored sessions (--dry-run to preview, --yes to skip the prompt). CLAUDE_CODE_SKIP_PROMPT_HISTORY=1 keeps prompts out of the history in any mode. If a credential has been printed in a session, rotate the credential; purging the file does not undo exposure.

Use transcripts to explain one session after the fact; use telemetry for ongoing numbers.
A parser built on the 2.1.322 line types will break silently on a version that renames them. Pin the version in the script's output and test on a fresh session after every upgrade.

}
"main  : $(Sum (Join-Path (Split-Path $sdir) "$($r.session_id).jsonl") | ConvertTo-Json -Compress)"

You write a small script that lists the most expensive API requests of a transcript, test it on a lab session, then run it on one of your own recent sessions.

  1. Save the script. It deduplicates by message.id, prices each request at the Haiku 5.5 list prices used earlier (change the four numbers for another model), and stops with an error if the transcript has no assistant lines.

    param([Parameter(Mandatory)][string]$Path)
$ErrorActionPreference = 'Stop'
$a = Get-Content $Path -Encoding UTF8 | ForEach-Object { $_ | ConvertFrom-Json } | Where-Object { $_.type -eq 'assistant' }
if (-not $a) { throw 'no assistant lines: format may have changed' }
$rows = $a | Group-Object { $_.message.id } | ForEach-Object {
  $u = $_.Group[0].message.usage
  [pscustomobject]@{
    id    = $_.Name.Substring(0, 12)
    model = $_.Group[0].message.model
    out   = $u.output_tokens
    cw    = $u.cache_creation_input_tokens
    cr    = $u.cache_read_input_tokens
    usd   = [math]::Round(($u.input_tokens * 0.10 + $u.output_tokens * 0.50 + $u.cache_creation_input_tokens * 0.20 + $u.cache_read_input_tokens * 0.01) / 1e6, 6)
  } }
$rows | Sort-Object usd -Descending | Select-Object -First 3 | Format-Table -AutoSize | Out-String
"requests: $(@($rows).Count)  total usd: $([math]::Round(($rows | Measure-Object usd -Sum).Sum, 6))"

  2. Test it on the lab 1 transcript, whose path you saved or can re-derive.

    Set-Location {{LAB}}/m12
powershell -NoProfile -File top-requests.ps1 -Path $t

    Expected: two requests ($t from lab 1; if you changed sessions, point it at lab 1's file), the first with about 4,500 cache-write tokens, and a total of about $0.0015, which equals lab 1's total_cost_usd (0.00148983).

  3. Now run it on one of your own recent sessions. List the newest transcripts of a project, read nothing but this script's summary, and do not paste the output anywhere with identity in it (it prints only message-id prefixes, models and numbers).

    Get-ChildItem ~/.claude/projects/*/*.jsonl | Sort-Object LastWriteTime -Descending | Select-Object -First 5 FullName, Length
powershell -NoProfile -File top-requests.ps1 -Path "<one of the paths above>"

    Expected: three rows. On a long interactive session the costliest request is usually one with a large cache write (a new file read, or the first request after a pause longer than the cache lifetime) rather than the longest answer.
