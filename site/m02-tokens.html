Every request to a Claude model is metered in four kinds of token, and their prices differ by a factor of up to 200 on the same model. The bill for an agent session is decided far more by the mix of those four than by the total count. This module teaches you to size text in tokens, read the meter on a real run, price it by hand, and see what makes the expensive kinds appear.

After this module you can

  • Estimate the token count of prose, JSON and log text from its size in bytes, with ratios you measured yourself.
  • Name the four token types, their usage fields and their price multipliers, and say which one dominates a given bill.
  • Price any claude -p result by hand from its usage block and match total_cost_usd to the last digit.
  • Predict whether a change to a prompt, a flag or a setting will cause a cache miss, and how much that miss costs.
  • Explain what total_cost_usd means on a subscription plan and on an API key, and where each kind of limit shows up.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key).
  • Windows PowerShell 5.1 or PowerShell 7.
  • About $0.02 of usage at Haiku prices for all five labs, or the equivalent share of a plan window.

The unit the model reads and writes

A model does not see characters or words. A tokenizer cuts the text into tokens: common words are one token, rare words split into pieces, and digits, punctuation, hex strings and identifiers break into many short tokens. Everything is counted in these units: the window size, the output limit, the rate limits and the price.

Current models have a 1M-token context window and a maximum output of 128k tokens per response. Both limits count tokens, so you need a way to turn "a 6 KB log excerpt" into a number before you paste it.

Sizing rules, measured

These ratios come from measurement, not from a rule of thumb: each sample was piped into a headless run and the growth of the prompt count was read from usage (you repeat this in the lab "Measure tokens per kilobyte"). Haiku 5.5 and Sonnet 5.5 gave identical counts for the same text.

ContentBytes per tokenTokens per KBWhy
English prose (runbook narrative)3.5about 296Common words are single tokens.
Compact JSON (records with ids, paths, numbers)2.0about 508Quotes, braces, keys repeated on every record, numbers split up.
Application log (timestamps, hosts, hex request ids)1.8about 567Timestamps and hex ids tokenize into many short pieces.

So a 100 KB log file is not "about 25k tokens" as a prose ratio would suggest. It is closer to 57k. Machine-generated text costs roughly twice what prose of the same size costs, both in window space and in money.

The fixed overhead of a session

Before your prompt arrives, Claude Code sends its own system prompt, tool definitions and an environment block (working directory, platform, shell, git status). A headless run with no MCP servers and no personal settings measured about 21,700 prompt tokens for a one-word answer. Each MCP server, skill description and CLAUDE.md line adds to that. You pay for this overhead on every request, which is why caching matters so much: in that run about 14,500 tokens were already cached and only the rest was new.

input_tokens                : 2
cache_creation_input_tokens : 7206
cache_read_input_tokens     : 14517
output_tokens               : 4

The answer was four output tokens. The prompt side was over 21,000. For short tasks the overhead is the cost.

Counting before you send

The API offers a token counting endpoint. It is free and its result is an estimate. In Claude Code the practical counter is the run itself: the sum of input_tokens, cache_creation_input_tokens and cache_read_input_tokens is the full prompt the model read. Subtract a baseline run and you have the cost of whatever you added.

Size machine output at about 2 bytes per token and prose at about 3.5, then measure when the number decides something.
Estimating a log or a JSON dump with the prose ratio underestimates it by about half. The window fills, or the bill grows, at twice the rate you planned.

Four meters, not one

Every response carries a usage block with four counts. Each is billed at its own rate, expressed as a multiple of the model's base input price.

TypeWhat it countsUsage fieldPrice vs base input
inputPrompt tokens after the last cache breakpoint: neither read from nor written to the cache.input_tokens1x
cache writePrompt tokens processed and stored so a later request can reuse them. Split by lifetime in cache_creation.ephemeral_5m_input_tokens and cache_creation.ephemeral_1h_input_tokens.cache_creation_input_tokens1.25x (5 min) or 2x (1 hour)
cache readPrompt tokens served from the cache.cache_read_input_tokens0.1x; 0.05x on Opus 5.5 and Sonnet 5.5; 0.025x on Fable 5.2
outputEverything the model generates, thinking included. The thinking share is in output_tokens_details.thinking_tokens.output_tokens5x

The full prompt the model read is input_tokens + cache_creation_input_tokens + cache_read_input_tokens. The input_tokens field alone is not the prompt size. In Claude Code it is usually a single-digit number, because Claude Code places a cache breakpoint at the end of the conversation and almost nothing sits after it.

Thinking is output

Extended thinking tokens are billed as output and count toward the context window. In a measured run that asked Haiku for a 400-word explanation, output_tokens was 1,121 and output_tokens_details.thinking_tokens was 302. The cost matched only when all 1,121 were priced as output, so the thinking share is inside the output count, not on top of it.

Why the mix matters more than the total

An agent re-sends its whole conversation on every turn. Take one turn at a 150,000-token context on Opus 5.5 (input $4, output $20, 5-minute write $5, read $0.20 per million), adding 2,000 new tokens and writing a 1,500-token answer. The token total is the same in both columns. The bill is not.

TokensWarm cacheCostCold cache (expired)Cost
cache read150,000$0.0300$0
cache write2,000$0.010152,000$0.760
output1,500$0.0301,500$0.030
Total153,500$0.070153,500$0.790

The same turn costs about eleven times more when the cache has expired. In a healthy long session, cache read is the largest type by volume, often above 90 percent, while cost is spread across cache read, cache write and output. A session where cache write stays large turn after turn is a session where something keeps changing the prefix.

The Haiku 5.5 step at 100k

Haiku 5.5 is the only current model with a long-context price. When a request's prompt passes 100,000 tokens, every rate for that request steps up fivefold, output included. The prompt length that decides it counts cache reads and cache writes, not just input_tokens. A warm turn at 99,000 tokens of cache read costs about $0.001; the same turn at 101,000 costs about $0.005. A Haiku agent in a 1M window that drifts past 100k pays the higher rate on every turn until the context shrinks again.

The model choice multiplies everything. A cheap model running an expensive pattern can still cost less than an expensive model running a good one, which is why the module "Cutting cost" treats model choice and cache hygiene together.

Batch: half price for work that can wait

The Message Batches API takes up to 100,000 requests or 256 MB per batch, returns results within 24 hours, and bills input and output at 50 percent off. The discount stacks with the cache multipliers and with the Haiku step. Batch is an API feature for jobs you submit yourself, such as classifying a ticket backlog overnight. It is not a Claude Code flag, and whether Claude Code itself can use it is not documented.

Other things that change the rate

  • Thinking: billed as output at the output rate, as shown in the previous lesson.
  • Data residency: Claude Code multiplies the list price by 1.1 when a response reports usage.inference_geo as "us". A normal run reports "global".
  • Contracted rates: Claude Code computes every figure at list price unless the managed setting modelPricing carries your rates. modelUsage.<model>.costBasis reads "list" on a default install.
  • API rate limits: cache_read_input_tokens do not count toward the input-tokens-per-minute limit, so caching also buys throughput on an API key.
Look up four numbers for your model before you estimate anything: input, write, read and output. Input alone predicts nothing about an agent.

A prefix, matched exactly

The API caches a request by its prefix. The prefix is assembled in a fixed order: tools, then system, then messages. A cache entry is a hash of everything up to a breakpoint, so the match is exact: one changed character at position N recomputes everything after N. There is no per-file or per-section caching.

Claude Code builds each request so the parts that rarely change come first:

LayerContentChanges when
System promptCore instructions, tool definitionsThe set of loaded tool definitions changes
Project contextCLAUDE.md, auto memory, unscoped rulesSession start, /clear, /compact
ConversationMessages, responses, tool resultsEvery turn (appended at the end)

Breakpoints

  • A breakpoint is a cache_control marker on a content block. A request can carry at most 4. Breakpoints themselves cost nothing.
  • A cache write happens only at a breakpoint. On a read, the API checks the hash at the breakpoint and then walks back up to 20 blocks looking for an entry an earlier request wrote.
  • Automatic caching (one top-level cache_control) puts the breakpoint on the last cacheable block and moves it forward as the conversation grows. It uses one of the 4 slots.
  • A breakpoint on a block that changes every request (a timestamp, a request id) never hits: every request writes, none reads. Put the breakpoint on the last block that stays identical.

Lifetimes and their prices

A cache hit refreshes the lifetime at no extra cost, so a session that keeps working stays warm indefinitely. The lifetime runs from the start of the request that wrote or read the entry, not from the end of the response: a response that streams for 4 minutes leaves about 1 minute of a 5-minute entry.

In Claude Code terms, these cause a full or partial re-read: switching models (each model has its own cache), changing effort on older models (Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 or later keep the cache on an API key or subscription), turning fast mode on or off, adding or removing tools when tool search is off, /compact (the conversation layer), and the first session after a Claude Code upgrade. Editing files, editing CLAUDE.md mid-session, changing permission mode, invoking skills and spawning a subagent keep the parent's cache.

The cache is effectively scoped to one machine and one directory, because the system prompt carries memory paths and the first message carries the working directory and git status. In the lab runs, about 14,500 tokens of tools and core instructions were shared across directories and the remaining 7,200 were written fresh in each new folder.

Minimum size

The minimum cacheable prompt is 512 tokens on current models. A shorter prefix is processed uncached with no error: both cache counts read zero. Claude Code's overhead is far above this, so the minimum only bites when you call the API directly with short prompts.

The fields that carry cost

claude -p "…" --output-format json prints one JSON object. Three of its fields carry token and cost data, and they do not cover the same scope.

The resume behaviour was measured: a task run cost $0.00210; resuming it with one more question gave a usage block for the new call alone (about 300 written, 22,100 read, 65 output) while total_cost_usd read $0.00242, the sum of both. Use modelUsage or total_cost_usd for accounting, and usage for "what did this call do".

The cost meter

Paste a claude -p JSON result or just its usage block below and pick the model. The meter shows the four token types by volume and by cost, and what the same run would cost with and without caching.

Estimates, not invoices

total_cost_usd and costUSD are computed on your machine from a price table bundled with Claude Code. They drift from the real bill when prices change, when the installed version does not know a model, or when billing rules apply that the client cannot model. Use them for development insight and budgeting; the authoritative figure is the Console on an API key and the plan usage page on a subscription.

Price a run by hand once per model you use; after that, trust the meter and check its split.
Summing total_cost_usd across a script that resumes the same session. Each resumed result already contains the earlier spend, so the sum counts it again.

The tokens are identical, the bill is not

The model, the tokenizer and the four token types are the same whichever way you sign in. What changes is what a token costs you and which limit stops you.

Windows instead of dollars

On a plan, there is no published exchange rate between tokens and window percent. What is documented: usage depends on model, context length, features and effort; cached content counts less; the session and weekly limits span all models, so switching models does not escape them. Claude.ai, the desktop app, IDE extensions and Claude Code all draw on one pool.

/usage works headless and costs nothing: the run reports num_turns 0 and total_cost_usd 0. On a subscription its result starts with the window state:

You are currently using your subscription to power your Claude Code usage

Current session: 12% used · resets Nov 11, 6:30pm
Current week (all models): 40% used · resets Nov 12, 1am

It goes on to list what contributed to usage on this machine (sessions run at once, context size, subagents, MCP servers), each with a share.

Which lifetime you observe

The cache_creation split tells you which regime a run was billed under. Every run in this module's labs, on a subscription login, wrote only ephemeral_1h_input_tokens. On an API key the same run writes ephemeral_5m_input_tokens unless you set promptCacheTtl to 1h. That changes the arithmetic: a 1-hour write is 2x input against 1.25x for 5 minutes, so the same cold run shows a higher notional cost on a plan than it would bill on a key, and a resumed session after a 20-minute break is warm on the plan and cold on the key.

Which one a run used

  • With -p, an API key in the environment is always used when present, and the run is billed as API usage even if you also have a plan. Interactive sessions ask once.
  • The stream-json init line reports apiKeySource; on a subscription login it reads "none".
  • /status shows the account and login method.
On a plan, budget in window percent and watch /usage; on a key, budget in dollars and reconcile against the Console.
A stray ANTHROPIC_API_KEY in a CI runner or a shell profile turns every headless run into paid API usage, silently, while you believe the plan covers it.

Run one headless prompt, find the four token counts, and reproduce total_cost_usd from the price table.

  1. Make the lab folder and move into it.

    New-Item -ItemType Directory -Force {{LAB}}/m2 | Out-Null
Set-Location {{LAB}}/m2

  2. Run one prompt and keep the JSON result. Every headless run in this module carries --setting-sources project and --strict-mcp-config: the first keeps your personal settings and hooks out, the second loads no MCP servers. Without them your own configuration would change the token counts you measure.

    claude -p "Reply with the single word OK." --model haiku --setting-sources project --strict-mcp-config --output-format json | Set-Content -Encoding utf8 run1.json

    Expected: no screen output; run1.json holds one JSON object.

  3. Print the four counts, the cache lifetime split and the meter.

    $r = Get-Content run1.json -Raw | ConvertFrom-Json
$r.usage | Select-Object input_tokens, cache_creation_input_tokens, cache_read_input_tokens, output_tokens
$r.usage.cache_creation
$r.total_cost_usd

    Expected: input_tokens 2, cache_creation_input_tokens about 7,200, cache_read_input_tokens about 14,500, output_tokens 4. The split between write and read depends on what was already warm; the sum stays about 21,700.

  4. Price it by hand with the Haiku 5.5 rates (dollars per million, prompt under 100k).

    $in = 0.10; $out = 0.50; $w5 = 0.125; $w1 = 0.20; $rd = 0.01
$u = $r.usage
$cost = ($u.input_tokens * $in + $u.output_tokens * $out + $u.cache_creation.ephemeral_5m_input_tokens * $w5 + $u.cache_creation.ephemeral_1h_input_tokens * $w1 + $u.cache_read_input_tokens * $rd) / 1e6
"by hand: {0:N8}" -f $cost
"meter:   {0:N8}" -f $r.total_cost_usd

    Expected: two identical lines, for example by hand: 0.00158857 and meter: 0.00158857.

Self-check
  • Which token type is the largest share of the cost? Cache write: about 91 percent on a subscription (1-hour writes at $0.20 per million). A one-word answer cost almost nothing to generate.
  • What is the full prompt size? input_tokens + cache_creation_input_tokens + cache_read_input_tokens, about 21,700. Not 2.
  • What would the same counts cost on Sonnet 5.5? Write 7,206 x $4 + read 14,517 x $0.10 + output 4 x $10, per million: about $0.030, roughly 19 times the Haiku figure.

    Expected: the same figure as the long run's cost, about 0.00164. Adding the thinking tokens a second time would overshoot.

Self-check
  • What would the long run's output alone cost on Opus 5.5? 1,121 x $20 per million, about $0.022: more than thirteen times the whole Haiku run.
  • Which lever cuts this run's cost most on Haiku: shorter answer or no cache write? The cache write (about 55 percent) edges out output (about 34 percent) here. In a warm multi-turn session the write disappears and output becomes the main lever.

Build three samples (prose, JSON, log), pipe each into a run, and compute tokens per KB from the growth of the prompt count.

  1. Make a subfolder and write the prose sample. The samples are plain ASCII on purpose: Windows PowerShell 5.1 pipes text to a native program as ASCII by default, so other characters would arrive as question marks.

    New-Item -ItemType Directory -Force {{LAB}}/m2/sizing | Out-Null
Set-Location {{LAB}}/m2/sizing
$prose = @'
When the change window opened, the team drained traffic from the first web node and watched the error rate. Nothing moved for ten minutes, so they patched the kernel, rebooted, and let the load balancer bring the node back once its health check passed. The second node took longer: a stale mount held the shutdown for almost four minutes, which nobody had seen in the test environment. The runbook now says to unmount the archive share before the reboot, and to check for open handles first. By the end of the night all six nodes were on the new build, the dashboards were quiet, and the only open item was a ticket to find out why the mount had hung in the first place.
Capacity planning works the same way every quarter. Someone pulls the peak numbers, someone else argues that last quarter was unusual, and the group settles on a figure that leaves a little headroom without buying hardware nobody will use. The useful part is not the number itself but the list of assumptions written next to it, because that list is what you check when the forecast turns out wrong.
'@
($prose + "`n") * 6 | Set-Content -Encoding ascii prose.txt

    Expected: prose.txt of 6,428 bytes. Repeating the passage does not change the ratio: a tokenizer does not compress repeats.

  2. Write a JSON sample and a log sample. The fixed seed makes your files match the ones measured here.

    Get-Random -SetSeed 42 | Out-Null
$rows = 1..60 | ForEach-Object { [ordered]@{ id = 1000 + $_; host = "web-0$($_ % 6 + 1)"; status = (200, 200, 200, 404, 500)[(Get-Random -Maximum 5)]; latency_ms = (Get-Random -Minimum 5 -Maximum 900); path = "/api/orders/$(Get-Random -Minimum 10000 -Maximum 99999)"; tags = @('prod', 'eu-west') } }
$rows | ConvertTo-Json -Compress | Set-Content -Encoding ascii data.json
$levels = 'INFO', 'INFO', 'INFO', 'WARN', 'ERROR'
$t = [datetime]'2026-11-11T08:00:00'
$lines = 1..90 | ForEach-Object { $t = $t.AddMilliseconds((Get-Random -Maximum 4000)); '{0:yyyy-MM-ddTHH:mm:ss.fffZ} {1,-5} web-0{2} GET /api/orders/{3} status={4} dur={5}ms req={6:x10}' -f $t, $levels[(Get-Random -Maximum 5)], (Get-Random -Minimum 1 -Maximum 7), (Get-Random -Minimum 10000 -Maximum 99999), (200, 200, 404, 500)[(Get-Random -Maximum 4)], (Get-Random -Minimum 3 -Maximum 900), (Get-Random -Maximum 2147483647) }
$lines | Set-Content -Encoding ascii app.log
Get-ChildItem prose.txt, data.json, app.log | Select-Object Name, Length

    Expected: data.json about 6,650 bytes and app.log about 8,700 bytes.

  3. Run a baseline, then pipe each sample into the same prompt and compute the difference.

    function Get-PromptTokens($file) { $u = (Get-Content $file -Raw | ConvertFrom-Json).usage; $u.input_tokens + $u.cache_creation_input_tokens + $u.cache_read_input_tokens }
claude -p "Reply with the single word OK." --model haiku --setting-sources project --strict-mcp-config --output-format json | Set-Content -Encoding utf8 base.json
$base = Get-PromptTokens base.json
'prose.txt', 'data.json', 'app.log' | ForEach-Object {
  $f = $_
  Get-Content $f -Raw | claude -p "Reply with the single word OK." --model haiku --setting-sources project --strict-mcp-config --output-format json | Set-Content -Encoding utf8 "$f.result.json"
  $bytes = (Get-Item $f).Length; $delta = (Get-PromptTokens "$f.result.json") - $base
  [pscustomobject]@{ file = $f; bytes = $bytes; tokens = $delta; tokens_per_KB = [math]::Round($delta / ($bytes / 1024)); bytes_per_token = [math]::Round($bytes / $delta, 1) }
} | Format-Table -AutoSize

    Expected: close to this (observed):

    file      bytes tokens tokens_per_KB bytes_per_token
----      ----- ------ ------------- ---------------
prose.txt  6428   1856           296             3.5
data.json  6651   3299           508               2
app.log    8718   4827           567             1.8

    The baseline drifts by up to about 10 tokens between runs, which is noise against differences in the thousands. Piping adds no measurable wrapper: a one-character stdin moved the count by less than that noise.

Self-check
  • How many tokens would a 200 KB log of this shape add to a prompt? About 200 x 567, so roughly 113,000. On Haiku 5.5 that alone crosses the 100k step.
  • Why does the log cost more per byte than the JSON, though both are machine text? Timestamps with milliseconds and 10-digit hex request ids break into many short tokens; the JSON has more repeated keys, which tokenize well.
  • Does piping the file make it cheaper than pasting it into the prompt? No. Piped stdin becomes part of the prompt and is counted the same way.
