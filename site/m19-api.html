Claude Code is one program built on the Messages API, and everything it does is a request body and a response body. Once you can read those two, tool use, structured output, image and PDF input, citations, batch jobs and computer use stop being separate products and become fields on the same request. This module walks each building block from the official docs, runs the parts that need no API key through Claude Code itself, and gives you complete, validated request bodies for the parts that do.

After this module you can

  • Read a Messages API request and response field by field, including stop_reason and usage, and say which of them you control.
  • Write a tool definition, run the tool_use and tool_result loop by hand, and explain what tool_choice and parallel calls change.
  • Say where each kind of tool runs (your code, Anthropic's servers, or a desktop you provide) and what that implies for risk and for who writes the loop.
  • Pick between output_config.format, strict tool use and Claude Code's --json-schema, and name the schema features and limits that make a request fail.
  • Estimate the input tokens of an image or a PDF from its size before sending it, then check the estimate against a measured run.
  • Price a bulk job as synchronous, batch, and batch with caching, and retrieve batch results by custom_id.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The measured labs were run on 2.1.322 on a subscription login.
  • Windows PowerShell 5.1 or PowerShell 7. Lab 3 uses System.Drawing, which is part of Windows PowerShell 5.1.
  • An API key from the Claude Console for the "send it" steps of Lab 4. Those steps are marked not run in this build: the course machine has no API key, so the request bodies are validated as JSON and the loop is exercised against canned replies, but nothing was sent to the API. Every other step needs no key.
  • About $0.03 of Haiku usage at API list price for Labs 1, 2, 3 and 5, or the same share of a subscription's 5-hour window.

If you skipped the prerequisites

Everything the model reads is counted in tokens, and every token is billed. There are four kinds on the bill: input, output, cache write and cache read. The API reports them in a usage object on every response. Output tokens cost five times what input tokens cost on every current model. A cache read costs a small fraction of normal input (0.1 times on Haiku 5.5, 0.05 times on Opus 5.5 and Sonnet 5.5), and a cache write costs 1.25 times (5-minute tier) or 2 times (1-hour tier). Prices per million input and output tokens are $4 and $20 for Opus 5.5, $2 and $10 for Sonnet 5.5, and $0.10 and $0.50 for Haiku 5.5 on prompts up to 100,000 tokens. On a subscription the same tokens draw down a 5-hour window and weekly limits instead of producing a bill. The module Tokens and their price covers all of this in depth.

What you send

The Messages API is a single HTTPS endpoint, POST https://api.anthropic.com/v1/messages. Every example in the docs sends three headers: x-api-key (your Console key), anthropic-version (the docs examples use 2026-10-21) and content-type: application/json. The body carries the whole conversation, because the API keeps no state between calls: you always send the full history, and earlier assistant turns do not have to have come from Claude.

{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "messages": [
    {"role": "user", "content": "Hello, Claude"}
  ]
}

That is the minimal body from the docs. The fields you will meet in this module:

FieldWhat it doesWhere it is taught
modelModel id, for example claude-haiku-5-5, claude-sonnet-5-5, claude-opus-5-5This lesson
max_tokensUpper bound on output tokens for this response. Required. A response cut off here has stop_reason: "max_tokens"This lesson
messagesThe history: objects with role (user or assistant) and content (a string, or an array of typed blocks)This lesson
systemTop-level system prompt; applies from the first turnThis lesson
tools, tool_choiceTool definitions and the rule for using themLessons 2 and 3
output_config.formatA JSON schema the output must matchLesson 4
Block types in content: image, documentImage and PDF input, with optional citationsLesson 5

content as a plain string is shorthand for one text block. The moment you send an image, a document or a tool result, content becomes an array of blocks, and the order of blocks is part of the request: the docs recommend PDFs before the question text, and tool results before any text in the same user message.

What comes back

  "type": "message",

This is the docs' own example output. content is an array of blocks again, and its types grow with the features you enable: text, tool_use, server_tool_use and others. usage carries the token counts that the module Tokens and their price taught you to price, with the cache fields added when caching is in play.

stop_reason is a branch, not decoration

Every successful response says why the model stopped. Your code must branch on it, because only one value means "the answer is complete".

stop_reasonMeaningWhat your code does

Parameters that no longer exist

Two older habits fail on current models, and the docs say so plainly. temperature, top_p and top_k are not supported on Claude 4.7 and later models, or on any model starting with API version 2026-10-21. Prefilling the assistant turn (starting Claude's answer for it) returns a 400 error on Claude 4.6 and later; the docs point to structured outputs or system prompt instructions instead. If you port a script written for an older model, these two are the first things to remove.

Subscription and API key

This endpoint is the API-key side of the house: a Console key, pay per token, no 5-hour window. A subscription login does not give you a key, so no request in this module can be sent from a subscription alone. Claude Code on a subscription makes the same calls on your behalf, which is why the measured labs here run through claude -p and read the same usage fields.

Branch on stop_reason every time. A response with max_tokens or refusal looks like success until the downstream parser breaks.
Writing a loop that only checks for tool_use and treats everything else as the final answer. A max_tokens cut-off or a pause_turn then ships half an answer as if it were whole.

The contract

The docs put it as a contract between your application and the model. You declare which operations exist and what shape their inputs take. Claude decides when and how to call them. The model never runs anything: it emits a structured request, your code runs the operation, and the result goes back into the conversation. If you are writing a regex to pull a decision out of free text, the docs say that decision should have been a tool call.

Defining a tool

A client tool is an entry in the top-level tools array with three required parts.

FieldRule from the docs
nameMust match ^[a-zA-Z0-9_-]{1,128}$
descriptionA detailed plain-text account of what the tool does, when to use it and how it behaves. This is the main lever on whether Claude calls it correctly
input_schemaA JSON Schema object for the parameters
input_examples (optional)Example input objects that show Claude how to use the tool
{
  "name": "get_ticket_count",
  "description": "Return the number of open tickets in a support queue. Use it whenever the user asks how many tickets are open.",
  "input_schema": {
    "type": "object",
    "properties": {
      "queue": { "type": "string", "description": "Queue name, for example web-01" }
    },
    "required": ["queue"]
  }
}

Other per-tool properties exist (cache_control, strict, defer_loading, allowed_callers); this module uses strict in Lesson 4. Tool definitions are input tokens, billed on every request, and the API adds its own tool-use system prompt on top: 286 tokens for Opus 5.5, Sonnet 5.5 and Haiku 5.5 when tool_choice is auto or none. A change to the tool list also invalidates the prompt cache that follows it, which is why stable tool lists matter.

The loop

Client tools make your application drive a loop. The canonical shape is a while keyed on stop_reason:

  1. Send the request with your tools and the user message.
  2. Claude answers with stop_reason: "tool_use" and one or more tool_use blocks, each with an id, a name and an input object that matches the schema.
  3. Run each tool and wrap its output in a tool_result block with the same id in tool_use_id.
  4. Send a new request: the original messages, Claude's response as an assistant message, and a user message holding the tool_result blocks.
  5. Repeat while stop_reason is "tool_use". Any other value ends the loop.
{
  "stop_reason": "tool_use",
  "content": [
    {"type": "text", "text": "I'll check the current weather in San Francisco for you."},
    {"type": "tool_use", "id": "toolu_01A09q90qw90lq917835lq9", "name": "get_weather",
     "input": {"location": "San Francisco, CA", "unit": "celsius"}}
  ]
}
{
  "role": "user",
  "content": [
    {"type": "tool_result", "tool_use_id": "toolu_01A09q90qw90lq917835lq9", "content": "15 degrees"}
  ]
}

Formatting rules that cause real errors

  • The tool_result message must come immediately after the assistant message that holds the tool_use. Nothing may sit between them.
  • In the user message, tool_result blocks come first; any text goes after all of them.
  • content in a result can be a string or a list of blocks (text, image, document), so a tool can return a screenshot.
  • Set "is_error": true when the tool failed. Write a message that says what went wrong and what to try next, because Claude reads it and adapts. If an input is invalid, Claude retries two or three times with corrections before apologising.
  • The error text "tool_use ids were found without tool_result blocks immediately after" means you broke one of the first two rules.
Tool results routinely carry content you do not control: web pages, inbound mail, uploaded files, third-party APIs. The docs warn that this is the route for indirect prompt injection. Keep such content inside tool_result blocks, not in the system prompt or a plain user text block.

tool_choice

tool_choiceEffect
{"type": "auto"}Default when tools are present. Claude decides whether to call any tool
{"type": "any"}Claude must call one of the tools
{"type": "tool", "name": "..."}Claude must call that tool
{"type": "none"}No tool calls. Default when there are no tools

Forcing has costs. With any or tool the API prefills the assistant turn, so there is no natural-language text before the tool_use block and no thinking block. A change to tool_choice invalidates the cached message blocks (tool definitions and system prompt stay cached). Check the model before relying on it: the docs say any and tool return a 400 error on Fable 5.2, Mythos 5.2, Opus 5.5, Sonnet 5.5, Fable 5.1 and Mythos 5.1, and on any model with manual extended thinking enabled. On those models use auto together with strict tool use (Lesson 4). Haiku 5.5 is not on that list.

Return exactly one tool_result per tool_use, matched by id, tool results first. If the loop is stuck, print the message array before you blame the model.

Parallel tool calls

Claude 4 and later models may return several tool_use blocks in one response when a request benefits from it. How you run them is your decision: concurrently, in order, or mixed. The API only asks that you return one tool_result for every tool_use, all together in the next user message, with every result before any text. If you skip a call because an earlier one failed, still return a result for it with is_error: true and a one-line reason such as "Not executed: the preceding write_file call failed."

Parallel use is on by default. To turn it off, set disable_parallel_tool_use: true inside the tool_choice object; it is not a top-level request parameter. With auto, Claude then calls at most one tool per response and can still answer in plain text. Run read-only calls in parallel for latency and run calls with side effects or ordering needs one at a time.

Where a tool runs

The primary axis the docs use is where the code executes, and it decides what you are responsible for.

KindExamplesWho runs itYou build a tool_result?
User-defined client toolYour get_ticket_countYour codeYes
Anthropic-schema client toolmemory, bash, text_editor, computerYour code; Anthropic publishes the schema, trained into the modelYes
Server toolweb_search, web_fetch, code_execution, tool_searchAnthropic's serversNo

A server tool appears as a server_tool_use block whose id starts with srvtoolu_, followed by its result block in the same assistant turn. You enable the tool and read the answer. Two cases bring you back into the loop. A server-side loop has an iteration limit, and when it is hit the response has stop_reason: "pause_turn": send the conversation back, including the paused response, and the model continues. And when Claude calls a server tool and a client tool in the same group, the response comes back as tool_use with the server call still unresolved; the API runs it after you return the client results, and that user message must hold only tool_result blocks. Server tools can add usage-based charges on top of tokens, for example web search per search.

Computer use

Computer use is an Anthropic-schema client tool. One entry, {"type": "computer_toolset_20260801"}, in tools gives Claude 17 member tools such as screenshot, left_click, type and zoom. Your application executes every call in an environment you control. The toolset needs no beta header, and the docs list Fable 5.2, Mythos 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5 as supporting it.

The loop is the one you already know, with two additions. Member calls arrive as tool_use blocks whose name is the member and which carry "toolset_name": "computer", and your tool_result must echo the same toolset_name or it is rejected. A turn can hold several member calls (a batch action); run them in order and stop at the first failure. Return an image for screenshot and zoom, and a short text such as OK for the rest. Claude takes a screenshot, decides, clicks or types, takes another, and continues until it answers in text.

What it costs: declaring the default toolset adds about 4,500 input tokens to a request, and every screenshot or zoom returned in a result is billed as image input (Lesson 5 gives the formula). What it risks: the docs call the risks distinct from other API features and ask for four precautions.

  1. Use a dedicated virtual machine or container with minimal privileges.
  2. Keep sensitive data, such as account logins, out of the model's reach.
  3. Limit internet access to an allowlist of domains.
  4. Have a human confirm decisions with real-world consequences, and anything needing affirmative consent such as accepting cookies, completing financial transactions or agreeing to terms of service.

The docs add that Claude sometimes follows instructions found in screenshots or web pages even when they conflict with yours, that Anthropic runs classifiers over what the tool returns to flag likely injections, and that the precautions above remain necessary even with those classifiers. Limitations listed include latency too slow for human-paced interaction, unreliable coordinates, and weaker reliability on niche or multi-application tasks. The reference implementation runs inside a Docker container. For tasks that stay inside web pages, the docs point to the separate browser use tool instead.

Treat a computer use agent as an untrusted user at a keyboard: give it a disposable machine, an allowlist and a human approval step before anything irreversible.
Giving the agent your own logged-in desktop because it is convenient. Any text on screen, including a web page or an image, can carry instructions the model may follow.

Two features, one grammar

The docs describe structured outputs as two complementary features that you can use alone or together. JSON outputs constrain the reply text to a schema through output_config.format. Strict tool use sets strict: true on a tool definition so the tool name and inputs are guaranteed to match the schema. Both compile the schema into a grammar and constrain sampling, so a schema violation cannot be sampled. That replaces the retry-and-reparse loop most scripts grow around "answer as JSON".

{
  "model": "claude-opus-5-5",
  "max_tokens": 1024,
  "messages": [
    {"role": "user", "content": "Extract the key information from this email: John Smith (john@example.com) is interested in our Enterprise plan and wants to schedule a demo for next Tuesday at 2pm."}
  ],
  "output_config": {
    "format": {
      "type": "json_schema",
      "schema": {
        "type": "object",
        "properties": {
          "name": {"type": "string"},
          "email": {"type": "string"},
          "plan_interest": {"type": "string"},
          "demo_requested": {"type": "boolean"}
        },
        "required": ["name", "email", "plan_interest", "demo_requested"],
        "additionalProperties": false
      }
    }
  }
}

The reply is JSON in the response's text content block. The older output_format parameter and its beta header are deprecated; the current field is output_config.format, and structured outputs are available on every model.

What a schema may contain

SupportedNot supported (400 error)
object, array, string, integer, number, boolean, nullRecursive schemas
enum (strings, numbers, booleans, nulls), constNumeric constraints: minimum, maximum, multipleOf
anyOf, allOf (not with $ref), $ref and definitions (not external)String constraints: minLength, maxLength
required; additionalProperties set to falseadditionalProperties set to anything but false
String formats such as date-time, date, email, uri, uuidArray constraints beyond minItems of 0 or 1
Simple regex in patternRegex backreferences, lookahead or lookbehind, \b

Complexity is limited too. Per request: 20 strict tools, 24 optional parameters in total across all strict schemas and JSON output schemas, and 16 parameters that use union types (anyOf or type arrays such as ["string","null"]). Beyond those explicit limits the API can still reject a schema with "Schema is too complex for compilation", and compilation has a 180-second timeout. The docs' advice, in order: make only critical tools strict, make parameters required, flatten nesting, split the request.

Costs and side effects

  • The first request with a new schema pays extra latency for grammar compilation. Compiled grammars are cached for 24 hours from last use; renaming a property is cheap, but changing the structure, or the tool set when both features are on, recompiles.
  • Claude receives an extra system prompt describing the format, so input tokens run slightly higher, and changing output_config.format invalidates the prompt cache for that conversation.
  • Required properties are emitted before optional ones, whatever order the schema lists them.

When the output still does not match

The guarantee has documented exceptions. A refusal returns 200 with stop_reason: "refusal" and text that may not match the schema. A max_tokens cut-off leaves JSON incomplete, so retry with a larger limit. String enum and const values can come back with different capitalisation than the schema, with no error, so compare case-insensitively and do not define values that differ only in case. A property that asks for the model's step-by-step reasoning can trigger a reasoning_extraction refusal; ask for a short explanation instead.

Two incompatibilities matter when you combine features: citations (Lesson 5) return a 400 if enabled together with output_config.format, and prefilling is not supported with JSON outputs. Structured outputs do work with batch processing, token counting and streaming.

Strict tools and forced calls

With strict: true a tool's inputs always match its input_schema, which removes the missing-parameter and wrong-type retries from Lesson 2. On models that support forced tool use, tool_choice: {"type": "any"} plus strict tools guarantees both that a tool is called and that its input is valid. On Opus 5.5 and Sonnet 5.5, where forcing returns 400, use auto with strict tools.

The Claude Code route: --json-schema

In headless mode, claude -p takes --json-schema together with --output-format json. The parsed object arrives in the structured_output field of the result; the result field holds the same data as text. If a run ends without valid structured output, for example because Claude declined, the field is absent, so test for it before use. The page says the flag exits with an error when the value is not a valid JSON Schema, and that the format keyword is accepted but treated as an annotation, not enforced. Lab 1 runs this.

The Claude Code docs describe the flag and the field and do not say that the API's grammar-constrained decoding is what enforces it, so do not carry the API-level guarantee over without testing. In Lab 1 a one-shot extraction took 3 turns, so budget for more than one model call.

Ask for a schema, not for "JSON". A prompt that says "answer as JSON" gets a code fence and keys of the model's choosing; a schema gets your keys.
Putting minimum, maxLength or a recursive $ref in a schema because the validator you use elsewhere accepts it. The API rejects it with a 400, and the fix is to validate those limits in your code after parsing.

Sending an image

An image is a content block with a source of type base64, url or file (a Files API id). Supported media types are JPEG, PNG, GIF and WebP; an animated GIF contributes its first frame only.

LimitValue
Images per request on the API100 on models with a 200k-token window; 600 on all others
Largest image8000 x 8000 px; 10 MB base64-encoded on the Claude API
Whole request128 MB on the first-party API; with more than 20 images a stricter per-image size applies

What an image costs

Claude processes an image in 28 x 28 pixel patches, each one a visual token. An image costs ceil(width / 28) x ceil(height / 28) tokens, until it exceeds the model's native resolution and is downscaled first. Claude 4.7 and later models are high resolution (long edge up to 2,576 px, at most 4,784 tokens); other models cap at 1,568 px and 1,568 tokens.

Image sizeStandard tier tokensHigh-resolution tier tokens
200 x 2006464
1000 x 10001,2961,296

The cost is billed as input at the model's rate, so the 3840 x 2160 image costs about $19 per thousand images at Opus 5.5's $4 per million, as the docs compute. High-resolution tiers can use roughly three times the tokens of a standard tier for the same image, so downsample when fine detail does not matter. The docs' accuracy cautions are worth repeating to a platform audience: text must be legible after any resize, counting is approximate, coordinates are approximate, and Claude cannot tell you whether an image is AI-generated. Lab 3 measures three sizes through Claude Code.

PDFs

A document block carries a PDF the same three ways (base64, URL, file id). Each page is converted to an image and its text is extracted and supplied alongside, so Claude sees both the words and the charts or diagrams. Requirements: a standard PDF with no password or encryption; 600 pages per request (100 when the request's context window is under 1M tokens); 128 MB per request. The docs give the text cost as typically 1,500 to 3,000 tokens per page depending on density, with no extra PDF fee, plus the image cost of each page from the table above. Put the PDF before your question, and use the token counting endpoint for an estimate on your real documents. A dense PDF can fill the context window before the page limit.

The Files API

Uploading the same 40-page PDF with every request is wasteful. The Files API stores it once: POST /v1/files with a multipart file field returns an id, and you reference it as {"type": "file", "file_id": "..."} in the source of a document or image block.

FactValue from the docs
Maximum file size500 MB each; 1 TB total per organization

Treating the Files API as per-user storage. The docs warn that files are visible to the whole workspace; a multitenant product needs a workspace per tenant, and a file id from an untrusted source must never be accepted.

Citations

Citations make the model point at the exact passage behind each claim. You set "citations": {"enabled": true} on a document block; citations must be enabled on all documents in a request or none. Plain text and PDF documents are chunked into sentences automatically. A custom content document uses your own blocks as-is, which is the way to control granularity for bullet points, transcripts or retrieval chunks.

The response then splits into several text blocks, and a block that makes a claim carries a citations array. The location type depends on the source.

SourceCitation typePosition fieldsIndexing
Plain textchar_locationstart_char_index, end_char_index0-based, end exclusive
PDFpage_locationstart_page_number, end_page_number1-based, end exclusive
Custom contentcontent_block_locationstart_block_index, end_block_index0-based, end exclusive

Every citation also has cited_text, document_index (0-based over all document blocks in the request) and document_title. The cited_text field does not count toward output tokens, and does not count as input when you send it back in a later turn. Enabling citations adds a small amount of input from the system prompt additions and chunking. Only text is citable; images inside PDFs cannot be cited. Citations conflict with structured outputs (400 error). To get a citation per extracted value, ask for one line per field and parse the lines; a prompt such as "return only a JSON object" gets few or no citations.

Cost an image or page before you send hundreds: compute the patches, or count tokens once on a sample and multiply.

The Message Batches API

A batch is a list of Messages requests processed asynchronously at 50 percent of the standard price, both input and output. You post {"requests": [...]} to /v1/messages/batches. Each element has a custom_id (1 to 64 characters, letters, digits, hyphen and underscore, unique) and a params object that is a normal Messages body.

Retrieving results

Poll GET /v1/messages/batches/{id} and read processing_status and request_counts. When it is ended, the results_url field points at a .jsonl file, one result per line; GET /v1/messages/batches/{id}/results streams it, and the docs recommend streaming over downloading everything. Each line has the custom_id and a result whose type is one of four values.

Result typeMeaning and billing
succeededHolds the full message. Billed
erroredInvalid request or server error; no message. Fix the body for a validation error, retry directly for a server error. Not billed
canceledCancelled before it was sent to the model. Not billed
expiredThe 24 hours ran out first. Not billed
Reading the results file in order. Results can come back in any order. Match every line to its request by custom_id, and use meaningful ids such as a ticket number. Validation of params also happens asynchronously, so errors show up in the results, not at creation: send one request through the synchronous endpoint first.

Where prompt caching fits

Batch and caching discounts stack, but cache hits inside a batch are best-effort because requests run concurrently and in any order; the docs quote hit rates anywhere from 30 to 98 percent. To raise them: put identical cache_control blocks on every request, keep requests flowing, share as much prefix as you can, and use the 1-hour cache tier, because a batch can take longer than the 5-minute default lifetime. Remember the prefix order is tools, then system, then messages; a stable tool list and system prompt at the front of every request is what makes a shared cache possible. The module Cutting cost covers the price arithmetic.

  1. Run one classification, then price its usage block with Haiku 5.5 list prices: $0.10 in and $0.50 out per million tokens, cache read at 0.1 times input, a 5-minute cache write at 1.25 times and a 1-hour cache write at 2 times.

    New-Item -ItemType Directory -Force {{LAB}}/m19/lab5 | Out-Null
Set-Location {{LAB}}/m19/lab5
$raw = claude -p "Classify this ticket as hardware, software or network: printer shows paper jam. One word." --model haiku --setting-sources project --strict-mcp-config --output-format json --max-turns 1
$r = $raw | ConvertFrom-Json
$u = $r.usage
$in = 0.10; $out = 0.50
$cw5 = [double]$u.cache_creation.ephemeral_5m_input_tokens
$cw1 = [double]$u.cache_creation.ephemeral_1h_input_tokens
$cost = ($u.input_tokens * $in + $cw5 * $in * 1.25 + $cw1 * $in * 2 + $u.cache_read_input_tokens * $in * 0.1 + $u.output_tokens * $out) / 1e6
"usage: input={0} cache_write_5m={1} cache_write_1h={2} cache_read={3} output={4}" -f $u.input_tokens, $cw5, $cw1, $u.cache_read_input_tokens, $u.output_tokens
"computed cost : {0:N6}" -f $cost
"reported cost : {0:N6}" -f $r.total_cost_usd
"difference    : {0:P1}" -f (($cost - $r.total_cost_usd) / $r.total_cost_usd)

    Expected: a usage line close to input=2 cache_write_5m=0 cache_write_1h=7232 cache_read=14517 output=6 (the cache figures depend on your Claude Code version and how warm the cache is), a computed cost near $0.0016 that equals the reported cost to six places, and difference : 0.0%. On a subscription the dollar figure is what the same tokens would cost at list price, not a charge.

  2. Project a bulk job. The API-shaped part of a classification request is far smaller than Claude Code's, which carries its own system prompt and tools, so set the sizes to what your own request would be on the raw API: the prompt tokens you send and the tokens you get back.

    $n = 10000; $inTok = 150; $outTok = 4
$sync = $n * ($inTok * $in + $outTok * $out) / 1e6
"{0:N0} requests of {1} in / {2} out on Haiku 5.5: synchronous {3:N4} USD, batch {4:N4} USD" -f $n, $inTok, $outTok, $sync, ($sync / 2)

    Expected: 10,000 requests of 150 in / 4 out on Haiku 5.5: synchronous 0.1700 USD, batch 0.0850 USD. Batch is exactly half because the 50 percent discount applies to input and output alike.

  3. Now do it on your own workload. Pick a job you really run on a loop (classify tickets, summarise logs, extract fields). Measure one request's input and output tokens, set $n, $inTok, $outTok and the model's prices from the lesson tables, and decide: synchronous, batch, or batch with a shared cached prefix.

    Done when you have a one-line decision with three numbers (synchronous cost, batch cost, and the deadline that justifies the choice), and your hand-priced one-request figure matched the reported cost within 1 percent.

Self-check

When is batch the wrong choice even at half price? Answer: When someone is waiting. A batch can take up to 24 hours before it expires, and results arrive as a file you poll for.

What would change in your projection if the 150-token prefix were identical across all 10,000 requests? Answer: You could cache it: cache reads cost a fraction of input, and the batch and caching discounts stack, though hits in a batch are best-effort (the docs quote 30 to 98 percent).

What did the match in step 1 prove? Answer: That you can reconstruct the bill from the four usage fields, which is the skill every cost figure in this course rests on.
