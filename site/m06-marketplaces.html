A plugin is a folder that carries skills, hooks, agents and MCP servers as one installable, versioned unit; a marketplace is a JSON catalogue in a git repository that tells Claude Code where to fetch each plugin. Together they are how a team ships its Claude Code setup the way it ships any other tool: reviewed, pinned to a commit, enabled per repository, and removable. They are also a supply chain, because whatever a plugin runs, it runs as you.

After this module you can

  • Turn a skill and a hook you already have into a plugin, validate it, load it with --plugin-dir and prove its skill is listed as /plugin-name:skill.
  • Build a marketplace from scratch, add it, install from it at project scope, update, uninstall and remove it, and say what each step wrote and where.
  • Pin a catalogue entry to a full commit sha, publish a new version, and predict whether claude plugin update moves.
  • Make a repository bring its own plugins through extraKnownMarketplaces and enabledPlugins, and let one teammate opt out locally.
  • Say which controls only managed settings can enforce (strictKnownMarketplaces, blockedMarketplaces, allowManagedHooksOnly) and show that the same keys in project settings do nothing.
  • Read a plugin's always-on context cost with claude plugin details and confirm it against a real run.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The labs were run on 2.1.322.
  • Windows PowerShell 5.1 or later, and git on the PATH (labs 3 and 4).
  • About $0.02 of API usage for all labs, or a very small share of a plan's 5-hour window. Most steps are claude plugin … commands, which do not call the model.
  • One skill or hook of your own for the last lab.

If you skipped the prerequisites

This module leans on Skills and Hooks. A skill is a folder with a SKILL.md file: YAML frontmatter (name, description and optional fields such as allowed-tools or disable-model-invocation) followed by instructions. The skill's name and description sit in the context of every session so Claude knows the skill exists; the body loads only when the skill runs, and every skill can be called as /name. A hook is a command Claude Code runs at a lifecycle event such as SessionStart, PreToolUse or PostToolUse. Hooks are configured as hooks > event > a list of {matcher, hooks:[{type, command, …}]} objects; on a blockable event, exit code 2 blocks the action and stderr becomes the reason. Hooks are ordinary processes: they run with your user rights, they cost no model tokens, and they run whether or not the model agrees. Hooks from every source (user, project, local, managed, plugin) merge, and matching hooks run in parallel.

A plugin is a directory that Claude Code loads as one unit. Inside it, each kind of component sits in a fixed place under the plugin root, and an optional manifest at .claude-plugin/plugin.json gives the plugin its name. Nothing in the folder is new: the skills, hooks and agents are the same files you already write under .claude/. What the plugin adds is packaging. It has a name, a version, an install and uninstall path, a namespace for its skills, and a place in a catalogue that other people can install from.

The manifest

Only name is required. It must be kebab-case, and it becomes the prefix on every skill and agent the plugin provides. claude plugin validate warns when version, description or author is missing; it does not fail on them.

{
  "name": "acme-tools",
  "description": "Team helpers: a standup skill and a session log hook",
  "version": "1.0.0",
  "author": { "name": "Acme Platform Team" }
}

version matters more than it looks. When it is set, it is the version Claude Code uses to decide whether an update exists. Lesson 3 covers what that means for your release flow.

Namespacing

A skill called standup inside the plugin acme-tools is invoked as /acme-tools:standup. Two plugins can therefore each ship a review skill without colliding, and a plugin copy of a skill can sit next to your original .claude/skills/standup without either hiding the other. Hooks have no namespace. If the same hook is in your settings file and in a plugin, it runs twice.

Two path variables

You do not know where a plugin will be installed, so it refers to its own files through variables. Both are substituted in skill, agent and command text, in hook commands and in MCP server configuration, and both are exported to hook and MCP processes.

VariablePoints atUse it for
${CLAUDE_PLUGIN_ROOT}The plugin's install directory. For an installed plugin that is a per-version cache folder, so it changes on every update.Reading the plugin's own scripts and files. Never write state here.
${CLAUDE_PLUGIN_DATA}~/.claude/plugins/data/<id>/, where <id> is the plugin id with every character other than letters, digits, _ and - replaced by -Caches, virtual environments, node_modules, anything that must survive an update.

In lab 1 a SessionStart hook in a plugin loaded with --plugin-dir logged both values:

session start; root=C:\Users\you\bootcamp-labs\m6\lab1\acme-tools; data=C:\Users\you\.claude\plugins\data\acme-tools-inline

The root is the source folder itself, because --plugin-dir loads a plugin in place. The data id is acme-tools-inline: inline is the name Claude Code uses in place of a marketplace for session-only plugins. The data folder existed after the run even though the hook only read the variable.

When a plugin is the wrong tool

Everything in a plugin also works on its own. A skill in ~/.claude/skills/ serves every project on your machine; a hook in .claude/settings.json serves everyone in one repository. Keep that standalone setup while it serves one project or one person. Make a plugin when you want to hand the same setup to several repositories or several people, install and remove it as a unit, and ship versioned releases.

A plugin is packaging, not a new capability: make one when you need a name, a version and an uninstall, not before.
An enabled plugin is part of every session, not only the sessions that use it. Its skill and agent descriptions are in context on every turn, its MCP servers start, and its hooks fire at their events.

The shortest path to a working plugin is to copy parts you already have into the layout, validate it, and load it for one session with --plugin-dir. No marketplace and no install are involved until you want to share it.

From parts you already have

Copy each .claude/ folder you use to the plugin root, then move the hooks object from your settings file into hooks/hooks.json under a top-level "hooks" key. The shape is identical. In lab 1 the plugin has one skill and one hook:

{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "shell": "powershell",
            "command": "Add-Content -Path \"$env:CLAUDE_PROJECT_DIR/plugin-hook.log\" -Value \"session start; root=$env:CLAUDE_PLUGIN_ROOT; data=$env:CLAUDE_PLUGIN_DATA\""
          }
        ]
      }
    ]
  }
}

While the originals still sit in .claude/, skills and agents do not collide (the plugin copies carry the prefix), but a hook that is in both places runs twice. Delete the originals once the plugin works.

Or scaffold one: claude plugin init

claude plugin init <name> (alias new) writes a starter plugin into your personal skills directory, ~/.claude/skills/<name>/, with a manifest and a root SKILL.md. --with skills also creates skills/example/; other --with values are agents, hooks, mcp, lsp, output-style and channel. A folder in a skills directory that contains .claude-plugin/plugin.json is a skills-directory plugin: it loads in every session with no install step, under the id <name>@skills-dir. On 2.1.322 the command printed:

✔ Created plugin "acme-scratch" at C:\Users\you\.claude\skills\acme-scratch
  It will auto-load next session as acme-scratch@skills-dir. Run /reload-plugins to load it now.
  Disable: claude plugin disable acme-scratch@skills-dir. Remove: delete the directory.

The root SKILL.md of a skills-directory plugin is invoked as /acme-scratch, not /acme-scratch:acme-scratch; skills under its skills/ get the prefix. Because init writes into your user profile, the labs build plugins by hand inside the lab folder instead.

Validate

claude plugin validate <path> checks the manifest, hooks/hooks.json and the frontmatter of every skill, agent and command. It exits 0 on ✔ Validation passed and 1 on failure; --strict turns warnings into errors for CI, and --json prints a machine-readable report with the same exit codes. On 2.1.322 it also prints "plugin directory checks" (missing README.md, missing LICENSE or license, no icon). Those are what Anthropic's public directory would refuse; they do not change the result unless you add --profile directory.

Windows PowerShell 5.1 writes a byte-order mark with Set-Content -Encoding utf8. A hooks.json with a BOM fails validation (Invalid JSON syntax: JSON Parse error: Unrecognized token, and the directory check names it: UTF-8 BOM at start of file), and at runtime it breaks the whole plugin load: claude plugin list showed Status: ✘ loaded with errors and Hook load failed. The labs write files with [IO.File]::WriteAllText, which writes UTF-8 without a BOM.

Load it for one session: --plugin-dir

claude --plugin-dir ./acme-tools loads the folder for that session only, in place, without installing anything. Repeat the flag for several plugins, or pass a folder of plugin folders. The flag also works in front of plugin subcommands, which is how you inspect a plugin without a session:

claude --plugin-dir ./acme-tools plugin details acme-tools
claude --plugin-dir ./acme-tools plugin list
Session-only plugins (--plugin-dir / --plugin-url):

  ❯ acme-tools@inline
    Version: 1.0.0
    Path: C:\Users\you\bootcamp-labs\m6\lab1\acme-tools
    Status: ✔ loaded

To prove the skill is registered under its namespaced name, read the first line of a stream-json run, the system/init message. Its skills and slash_commands arrays both contained acme-tools:standup, and its plugins array listed {"name":"acme-tools","source":"acme-tools@inline","version":"1.0.0"}. Invoking it headless works the same as typing it:

claude -p "/acme-tools:standup fixed the backup job, next is the DNS cutover, waiting on the change window" --model haiku --setting-sources project --strict-mcp-config --plugin-dir ./acme-tools --max-turns 2
Done: fixed the backup job
Next: DNS cutover
Blocked: waiting on the change window

In a live session, run /reload-plugins after you edit the plugin's files; a --plugin-dir plugin picks up the change without a restart. Common load failures: --plugin-dir pointed at a marketplace root instead of a plugin folder (nothing loads, no error), or skills/ placed inside .claude-plugin/ (the plugin loads with no skills).

Validate, then plugin details with --plugin-dir, then one headless run that reads the init line: three checks, no install.

A marketplace is a directory or repository with a .claude-plugin/marketplace.json file that lists plugins and says where to fetch each one. It is a catalogue, not a store: nothing is hosted, and each entry can point at a folder next to the catalogue or at a different repository. The directory that contains .claude-plugin/ is the marketplace root, and relative sources resolve from it.

The file

{
  "name": "acme-marketplace",
  "description": "Internal Claude Code plugins for the Acme platform team",
  "owner": { "name": "Acme Platform Team" },
  "plugins": [
    {
      "name": "acme-tools",
      "source": "./plugins/acme-tools",
      "description": "Standup skill and a session log hook",
      "category": "productivity"
    }
  ]
}

Pinning: ref and sha

For the three git sources, ref is a branch or tag (default: the repository's default branch) and sha is a full 40-character lowercase commit. When both are set, Claude Code checks out sha. A ref is a moving label that whoever controls the repository can repoint; a sha is the exact tree you reviewed.

{
  "name": "acme-tools",
  "source": {
    "source": "url",
    "url": "https://git.example.com/acme/acme-tools.git",
    "sha": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0"
  }
}

How Claude Code decides an update exists

Every installed plugin has a computed version, and claude plugin update only replaces the cached copy when that version changes. The order is: version in plugin.json, then version in the catalogue entry, then a value from the source (a 12-character commit sha for git sources; unknown for a local folder outside git and for npm). The version also names the cache folder, ~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/.

Lab 3 runs the cases against a local repository standing in for a git host:

Catalogue entryUpstream changeResult of claude plugin update
sha = commit of 1.0.01.1.0 committed, pin not moved✔ acme-tools is already at the latest version (1.0.0).
sha moved to the 1.1.0 commitcatalogue commit pulled✔ Plugin "acme-tools" updated from 1.0.0 to 1.1.0 …; cache now holds 1.0.0 and 1.1.0
ref: "main"a new commit, version still 1.1.0✔ acme-tools is already at the latest version (1.1.0).

The third row is the trap in the version rule. A pinned "version" string holds every user on their cached copy however many commits you push. Either bump version on every release, or leave it out of both plugin.json and the entry so the commit sha becomes the version. Do not set it in both: plugin.json wins and validate reports the mismatch.

A relative-path plugin in a marketplace you added from a local folder is the exception: it is read in place, and your edits show up at the next session start or /reload-plugins whatever the version says. That is convenient while you develop the catalogue and surprising if you expected versioned releases.

Getting updates to users

Auto-update is on by default only for Anthropic's official marketplaces; for yours it is off until a user turns it on in /plugin or an administrator sets "autoUpdate": true on the extraKnownMarketplaces entry in managed settings. Without it, users run claude plugin marketplace update <name> to refresh the catalogue and claude plugin update <plugin>@<name> to move the plugin. An update prints Restart to apply changes; a running session keeps the version it loaded until /reload-plugins or a restart. Old version folders get an .orphaned_at marker and are swept 14 days later.

claude plugin tag <path> creates a <name>--v<version> git tag after checking that plugin.json and any enclosing catalogue entry agree; --dry-run shows the tag without creating it (lab 3 printed Tag: acme-tools--v1.0.0).

Pin third-party entries to a full sha, and move the pin only after you have read the diff between the two commits.

A repository that brings its plugins

Commit .claude/settings.json with both keys, and the repository declares its catalogue and the plugins it expects. What a teammate gets depends on the surface:

  • In an interactive session, extraKnownMarketplaces applies only after the teammate trusts the folder; then Claude Code offers to register the marketplace. A plugin enabled in project settings still has to be installed on each machine; until it is, /plugin shows Plugin "<name>" is enabled in project settings but isn't installed here.
  • From the shell, in lab 4, a fresh plugin store did not pick the marketplace up from the committed file. claude plugin install acme-tools@acme-marketplace --scope project failed with Plugin "acme-tools" not found in marketplace "acme-marketplace"; after claude plugin marketplace add <source> --scope project the same install succeeded.

A teammate who does not want a project plugin sets it to false at local scope, which outranks project scope: claude plugin disable acme-tools@acme-marketplace --scope local writes .claude/settings.local.json and claude plugin list shows Status: ✘ disabled. Make sure .claude/settings.local.json is ignored by git in your repositories (git check-ignore -v .claude/settings.local.json).

The CLI rewrites .claude/settings.json whenever it adds, installs or removes. In lab 4 a teammate's add only reordered the keys, but it still showed as M .claude/settings.json; and claude plugin marketplace remove emptied both keys in the committed file. Review git diff .claude/settings.json before every commit. Also note the absolute path a directory source records: it is meaningless on a teammate's machine, so commit git-sourced marketplaces, not local folders.

Review and release flow

  1. A plugin change lands in the catalogue repository (or the plugin's own repository) through a normal pull request with a named reviewer.
  2. CI runs claude plugin validate <plugin> --strict and claude plugin validate <marketplace-root>; both must exit 0.
  3. The reviewer reads every hook command, .mcp.json and every file in bin/ in full, and records the always-on cost from claude --plugin-dir <path> plugin details <name>.
  4. On merge, bump version (or rely on the commit sha), tag with claude plugin tag, and move the catalogue entry's sha in a separate, reviewed commit.
  5. Users run claude plugin marketplace update and claude plugin update, or get it from auto-update if an administrator turned that on.

Private repositories

Claude Code has no git token of its own and marketplace.json has no field for one. It runs git on the user's machine with prompts turned off and uses whatever credentials are already stored. For SSH, the key must work without a passphrase prompt (loaded in an agent) and the host must be in known_hosts. For HTTPS, a credential the helper already stores works; one it would have to ask for fails. For owner/repo, Claude Code tries SSH first; users without a GitHub SSH key set CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1. A token in GITHUB_TOKEN alone does not authenticate; it takes effect through a credential helper.

The repository says which plugins it wants; each machine still installs them; managed settings are the only place that can force them.

What a plugin can do to your machine

A plugin runs code with your user rights. Claude Code's permission rules and sandbox cover the tool calls Claude makes, not the code a plugin runs by itself.

ComponentRuns asCovered by permissions and sandbox
Hooks (and monitors)Shell commands at lifecycle events, with your full user rightsNo. They run outside the sandbox.
MCP and LSP serversProcesses Claude Code starts for every session the plugin is enabled inThe server process: no. Claude's calls to its tools: yes.
bin/ executablesCommands on the Bash tool's PATHYes, when Claude runs them as a tool call.
Skills, agents, commandsInstructions in Claude's contextThey steer what Claude does with tools it already has.
UpdatesNew files on disk, from auto-update if it is onThe files you reviewed can change.

So the review that matters happens before install: read hooks/hooks.json, .mcp.json and every file in bin/, then pin the entry to the commit you read. claude plugin marketplace list shows where each marketplace came from. claude --plugin-dir <folder> plugin details <name> lists the components of a plugin you have cloned, without starting a session; after install, claude plugin details <name> does the same for the cached copy.

To remove a plugin you no longer trust: claude plugin uninstall <plugin> --scope <scope> (it deletes ${CLAUDE_PLUGIN_DATA} unless you pass --keep-data), and claude plugin marketplace remove <name> if you distrust the owner too, which uninstalls every plugin from it. The cached files stay under ~/.claude/plugins/cache/ for 14 days; delete the folder yourself to remove them now.

What only managed settings can enforce

The plugin policy keys are managed settings. Put them in a project's settings file and they do nothing, which lab 4 shows: with "strictKnownMarketplaces": [] in .claude/settings.json, adding another marketplace still printed ✔ Successfully added marketplace, and with "allowManagedHooksOnly": true there, the plugin's hook still ran.

KeyEffectDoes not
strictKnownMarketplacesAllowlist of marketplace sources, checked before any download and again at session start. [] blocks every source, the official one included.Register anything, restrict entries inside an allowed marketplace, or block --plugin-dir.

An allowlist without a {"source": "skills-dir"} entry also stops skills-directory plugins from loading. Allowlist matching is exact for github and git entries: repo or url, ref and path must all match, so an entry without ref does not cover a source added with #main. On Windows the managed file lives at C:\Program Files\ClaudeCode\managed-settings.json, which takes administrator rights to write. A policy that allows only your organisation's catalogue, registers it, force-enables one plugin and closes the side doors:

{
  "strictKnownMarketplaces": [
    { "source": "github", "repo": "acme/*" },
    { "source": "skills-dir" }
  ],
  "blockedMarketplaces": [
    { "source": "github", "repo": "untrusted-org/*" }
  ],
  "extraKnownMarketplaces": {
    "acme-marketplace": {
      "source": { "source": "github", "repo": "acme/acme-marketplace" },
      "autoUpdate": false
    }
  },
  "enabledPlugins": { "acme-tools@acme-marketplace": true },
  "allowManagedHooksOnly": true,
  "disableSideloadFlags": true
}

What a project can do for itself is narrower. "disableAllHooks": true in project settings stopped the plugin's hook in lab 4, and a project or local enabledPlugins entry of false turns a plugin off for that repository.

A non-official marketplace can still look official. Claude Code reserves Anthropic's marketplace names and refuses look-alikes, but a third-party catalogue with a reassuring name is still third-party. Trust comes from the source repository and the commit you pinned, not from the name.

What a plugin costs in context

Every enabled plugin's skill, agent and command names and descriptions are in Claude's context on every turn, used or not. Bodies load only when a component runs. Hooks cost no context at all. MCP servers add what MCP tool search lets through (by default, tool names and server instructions, with definitions deferred). claude plugin details estimates the first two:

Component inventory
  Skills (1)  standup
  Agents (0)
  Hooks (1)  SessionStart  (harness-only — no model context cost)
  MCP servers (0)
  LSP servers (0)

Projected token cost
  Always-on:   ~32 tok   added to every session

Per-component (rounded)
  component  always-on  on-invoke
  standup          ~30        ~30

A real run agrees to within the noise. The same one-line Haiku prompt showed about 21,730 total input tokens without the plugin and about 21,780 with it (input + cache write + cache read), a difference of about 50. For MCP servers, details gives no estimate; run /context in a session with the plugin enabled and read the MCP tools category. The always-on figure is what every user carries, so it is the number to cut: shorter descriptions, disable-model-invocation: true on skills only people call, or a split into smaller plugins.

How you pay changes what that number means. On an API key, the always-on tokens are billed on every request, mostly at the cache-read rate once the prefix is cached. On a subscription plan they draw down the 5-hour window and the weekly limit instead; cached content counts less against those limits, but it still counts. A dozen plugins at a few hundred tokens each is a few thousand tokens on every turn of every session.

Before you approve a plugin, write down three things: the commit you read, the always-on token figure, and every process it starts.
