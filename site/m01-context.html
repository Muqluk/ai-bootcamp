The model keeps no memory between requests. Everything it knows about your session is the text Claude Code sends with each request, and every token of that text is paid for again each turn. This module shows you what is in that text, how to measure it, and how to make sure the part that matters is the part the model actually reads.

After this module you can

  • Name the layers Claude Code puts in the context window, in order, and read their sizes from /context, the stream-json init line and the usage block.
  • Measure what a CLAUDE.md file adds to every request, and cut it with path-scoped rules, skills and HTML comments.
  • Predict how a session grows turn by turn, and choose between /compact with instructions, /clear and a fresh session, knowing what each one loses.
  • Explain why a bigger context can make answers worse, and place instructions so they hold.
  • Make the model read the source before it answers, ask for file:line evidence, and check that evidence.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key).
  • Windows PowerShell 5.1 or PowerShell 7 for the lab commands.
  • A project of your own with a CLAUDE.md or AGENTS.md, for the last lab.
  • About $0.10 of API usage for all five labs on Haiku, or a small slice of a plan's 5-hour window.

A stateless function with a long argument

A language model is a function. It takes a sequence of tokens and returns a continuation. It holds nothing from one call to the next: no session, no scratchpad, no memory of what it said a minute ago. What looks like a conversation is the client sending the whole conversation again, with the new message appended, on every request.

Claude Code is that client. When you type a prompt, it builds one request that contains its own system prompt, the definitions of every tool the model may call, your instruction files, the conversation so far, every tool result so far, and your new message. The model answers. If the answer is a tool call, Claude Code runs the tool, appends the result, and sends the whole thing again. One prompt from you can be ten requests, and each of the ten carries everything before it.

This has three consequences you will use for the rest of the module.

ConsequenceWhat it means in practice
The model knows only what is in the request.A file it has not read, a rule that is not in an instruction file, a decision from yesterday's session: none of it exists for the model. It will not say "I don't know" reliably. It will often fill the gap with something plausible.
Every token is re-sent every request.A 10,000-token file read on turn 3 is in the prompt of turn 4, 5 and 40. Its cost is paid per request, not once.
Order and position are under the client's control.Claude Code decides what goes first and what goes last. You influence it through instruction files, skills, the prompt itself and when you compact or clear.

Why re-sending is affordable: the prompt cache

Re-sending 50,000 tokens forty times would be expensive at full input price. The API caches the start of a request: if a new request begins with exactly the same tokens as a recent one, that prefix is served from cache. The usage block on every result splits the prompt side into three counts:

FieldMeaningAPI price vs base input
input_tokensTokens after the last cache breakpoint, read fresh.1x
cache_creation_input_tokensTokens written to the cache on this request.1.25x (5 min) or 2x (1 hour)
cache_read_input_tokensTokens served from the cache.0.1x, or less on some models
output_tokensWhat the model wrote, thinking included.5x

The sum of the first three is the real size of the prompt the model saw. Call it the prompt side. It is the number to watch in this module, because it is what fills the window. Which of the three buckets a token lands in decides its price, and the module Tokens and their price covers that in depth.

Here is the result of the smallest possible run: a one-word reply on Haiku in an empty folder.

input_tokens                : 2
cache_creation_input_tokens : 7214
cache_read_input_tokens     : 14517
output_tokens               : 4

Four tokens of answer, about 21,700 tokens of prompt. None of that prompt was yours. It is the fixed cost of being a Claude Code session, and Lab 1 has you measure it on your machine.

Three slots, filled by the client

The API orders a request as tools, then system, then messages. The cache works on that order: a change in an early slot invalidates the cache for everything after it. A change to the tool definitions invalidates all three; a new message only adds to the end. Claude Code fills the slots with these layers.

LayerWhat it isSize, empty sessionChanges when
System promptClaude Code's own instructions, environment facts, git status snapshot, plus anything from --append-system-prompt or an output style.about 3,400Rarely within a session.
Tool definitionsName, description and JSON schema of each built-in tool (Read, Edit, Bash, PowerShell, Grep and the rest).about 11,600You change --tools, --allowedTools or permission settings.
Deferred toolsMCP tools and some built-ins are deferred: only their names and server instructions load. The full schema loads when the model searches for the tool.names onlyYou add or remove an MCP server.
Instruction filesCLAUDE.md, CLAUDE.local.md, unscoped .claude/rules/ files, and the first 200 lines or 25KB of auto memory's MEMORY.md. Delivered as a user message after the system prompt.0 in an empty folderYou edit the files; on demand when Claude reads a file in a subdirectory that has its own.
Skills listingName and description of each skill the model may invoke. Bodies load only on invocation.about 2,200You add a skill or plugin.
MessagesYour prompts, the model's replies, and system reminders Claude Code adds (a file changed on disk, attribution lines).10Every turn.
Tool resultsEverything a tool returned: file contents, command output, search hits.0Every tool call. Usually the largest layer by far.

The sizes are from an empty folder on Claude Code 2.1.322 with no MCP servers, measured with the three instruments below. Your numbers will differ with version, platform, plugins and servers. That is the point of measuring.

/context prints the window by category. It works in a live session and also headless, as claude -p "/context". /context all expands the per-file lists. Output from the empty folder:

The billed prompt side on the same session was about 21,700. Use /context to see which category is large, and the usage block for the number.

Instrument 2: the stream-json init line

Run headless with --output-format stream-json --verbose and the first line is a JSON object with type "system" and subtype "init". It lists what loaded, not how big it is: tools, mcp_servers, model, permissionMode, slash_commands, skills, plugins, agents, memory_paths, apiKeySource and more. In the empty folder it showed 26 tools, 17 skills, no MCP servers, and a memory_paths object with only the auto memory folder. Use it to answer "did that server, skill or file load at all" in a script.

Instrument 3: the usage block

Every --output-format json result, and the last line of a stream-json run, carries usage. Prompt side = input_tokens + cache_creation_input_tokens + cache_read_input_tokens. For a run that made several model calls, the three counts are summed across the calls, so a turn with one tool call counts the prefix twice. That is real cost, but it is not the window size. For window size, compare single-call runs, or read the last entry of usage.iterations.

One more detail from the lab runs: the very first run in an empty folder already showed about 14,500 tokens of cache read. The cache matches on identical prefixes, not on sessions, so the system prompt and tool definitions written by an earlier session on the same account are reused. The part that is new to each session (its working folder, its first message) is written fresh.

Use /context to find the big category, the init line to prove what loaded, and the usage block for the number you pay for.

Where they live and how they stack

CLAUDE.md files do not override each other. Every file that applies is concatenated into context, broadest first, so the more specific file is read last.

If a repository has an AGENTS.md and no CLAUDE.md or CLAUDE.local.md in the working folder or above it, Claude Code reads AGENTS.md instead. A CLAUDE.md containing the line @AGENTS.md loads both tools' instructions from one file.

Imports and comments

A line such as See @docs/style.md imports that file. Relative paths resolve from the importing file; imports nest up to four hops; a path inside backticks is not imported. An import that resolves outside the project asks for approval the first time.

Imports organise a file. They do not make it cheaper. Lab 2 measured it: 300 rules inline in CLAUDE.md added about 13,900 tokens per request; the same 300 rules moved to an imported file added about 14,000. /context all lists the imported file as its own memory file.

Block-level HTML comments are stripped before injection. The same 300 rules wrapped in <!-- --> added about 160 tokens, the cost of the heading and one remaining line. Comments are the right place for maintainer notes: owner, review date, why a rule exists.

What belongs in CLAUDE.md, and what does not

CLAUDE.md is paid on every request of every session. It earns its place only with facts the model needs in every session and cannot discover cheaply.

ContentWhere it goesWhy
Build and test commands, branch rules, "never do X"CLAUDE.mdNeeded every session; short.
A multi-step procedure (release, migration, incident triage)A skillOnly the description is in context until it is used. See the module Skills.
Rules for one part of the tree (src/api/**)A rule with paths:Loads only when Claude touches a matching file.
Directory layouts, dependency lists, architecture toursNowhereThe model can read the tree when it needs to. A stale copy is worse than none.
Something that must happen every time (format on save, block a command)A hookInstructions are context, not enforcement. See the module Hooks.
Personal URLs, test accounts, preferencesCLAUDE.local.md or ~/.claude/CLAUDE.mdNot the team's business; not in git.

The documentation sets a target of under 200 lines per CLAUDE.md file. Longer files cost more context and reduce adherence, and Claude Code warns at startup and in /status when a file is over the recommended length. Write rules concrete enough to check ("Run make test before committing", not "test your changes"), group them under headings, and remove contradictions: when two files disagree, the model may pick either one.

CLAUDE.md is delivered as a user message after the system prompt, so it is strong guidance, not configuration. When you need system-prompt weight in a script, --append-system-prompt puts text there. In a session, /memory lists and opens the files, and /doctor prompt-audit reviews them for stale or conflicting content without changing anything until you ask.

Every line in CLAUDE.md is a line you pay for on every request. Keep the ones the model needs every time and cannot find on its own.
Splitting a 600-line CLAUDE.md into six imported files and believing it shrank. The window sees all 600 lines. Use path-scoped rules or skills to make content load less often.

How a session grows

The prompt side of each request is the fixed overhead plus everything said and returned so far. Lab 4 measured a resumed session in which each turn read one 150-line log file (about 13KB):

TurnWhat happenedPrompt side of the last call
0One-word reply, Read as the only tool4,813
1Read app-1.log, reply with one number11,636
2Read app-2.log18,516
3Read app-3.log25,335
4Read app-4.log32,140
5After /compact, one question6,398

Each file added about 6,800 tokens and stayed. The answers were one number each; the cost came from what the model read, not what it wrote. Per-turn cost rose in step: turn 4 cost about four times turn 1, for the same work. Tool results dominate growth in real sessions too. A test log, a git diff of a lockfile or a directory listing does the same thing.

Note also the overhead of turn 0: 4,813 tokens with only the Read tool, against about 21,700 with the default tool set. Restricting --tools in a headless job is one of the largest savings available.

Auto-compaction

When the window approaches its limit, Claude Code compacts on its own: it replaces the conversation with a structured summary and carries on. On the 1M-token models the default trigger is about 967K; /context shows the reserve as "Autocompact buffer". You can move the trigger with /autocompact 500k, the --autocompact flag, the autoCompactWindow setting or CLAUDE_CODE_AUTO_COMPACT_WINDOW (100K to 1M). If a single output is so large that the window refills right after each summary, Claude Code stops after a few attempts and shows an error instead of looping.

Your three manual levers

CommandWhat it doesWhat you keepWhat you lose
/compact [instructions]Summarises the conversation now. Instructions steer the summary: /compact keep the failing test names and the fix plan.Same session. System prompt, project-root CLAUDE.md, unscoped rules, auto memory and skill descriptions are re-injected from disk. Up to five recently edited files are re-read. Invoked skill bodies come back capped at 5,000 tokens each.Exact wording of earlier turns, tool output details, path-scoped rules and subfolder CLAUDE.md files (they reload only when a matching file is touched again), and anything the summary judged unimportant.
/clear [name]Starts a new conversation with empty context. The old one stays in the /resume picker.Instruction files and memory, loaded fresh.The whole conversation.
New session or subagentA separate context window from the start.Instruction files.Everything in your current conversation, unless you write it into the prompt.

/compact also works headless on a resumed session: claude -p "/compact ..." --resume <id> returns a result with local_command "compact" and a zero usage block. In Lab 4 it took the window from about 32,000 to about 6,400 tokens, and the next turn still listed all four files and their values, because the compact instructions asked for exactly that.

A CLAUDE.md section titled "Compact Instructions" steers every automatic compaction the same way. Rules that must survive compaction belong in the project-root CLAUDE.md or an unscoped rule, never only in the conversation.

Clear between unrelated tasks; compact with instructions inside one long task; never rely on the conversation to hold a rule.
Telling the model a constraint in turn 2 ("don't touch the prod config") and finding it ignored after an auto-compaction in turn 80. The summary kept the task and dropped the aside.

A big window is not a good memory

A 1M-token window means the request is accepted, not that every token gets equal attention. The model weighs everything in the prompt against everything else. Three effects follow, and all three get worse as the context grows.

EffectMechanismWhat you see
PositionModels attend most reliably to the start and the end of a long prompt. Material in the middle of a long run of tool output is the most likely to be missed.A rule from the middle of a 900-line instruction file is ignored; the detail from the third of eight file reads is misquoted.
DilutionEvery irrelevant token competes with the relevant ones. Thirty near-identical rules make each one weaker.Adherence falls as CLAUDE.md grows. The documentation's 200-line guidance exists because of this.
Stale contentOld instructions, old file contents and abandoned plans stay in the window and look exactly as authoritative as new ones.The model edits code against the version of a file it read an hour ago, or follows a plan you rejected.

Claude Code mitigates the stale-file case with a system reminder when a file it read changes on disk. It cannot know that the plan you discussed at turn 10 was replaced verbally at turn 30.

Placing what matters

  • The task goes last and is specific. Your prompt is the end of the request. Name the file, the function, the acceptance test. "Fix the timeout in gate/upstream.go so TestBillingRetry passes" beats "fix the bug we talked about".
  • Standing rules go in instruction files, at the top. Put the few rules that cause damage when missed at the start of CLAUDE.md, under a clear heading. The same applies to SKILL.md: after compaction a skill body is cut to its first 5,000 tokens.
  • Restate a constraint when it matters. Repeating "read-only: do not modify files" in the prompt that needs it costs a dozen tokens and puts the rule at the end of the window.
  • Keep bulk out. Ask for head, a filtered search, or a summary instead of a full log. Send a large investigation to a subagent: it reads in its own window and returns only its report. The module Headless runs and subagents covers how.
  • Reset when the topic changes. A fresh window with a two-line handoff note outperforms a long window full of the previous task.
Put the instruction where the model looks: the top of an instruction file for standing rules, the end of the prompt for this task.
Answering "the model ignored my rule" by adding the rule again in a second place in CLAUDE.md. That makes the file longer and the rule no stronger. Shorten the file, make the rule concrete, or turn it into a hook.

The confident wrong answer

Ask a model about a file it cannot see and it rarely says "I cannot see it". It produces the most likely text. Lab 3 asks Haiku about a small proxy config, acme-gate.conf, in which /invoice/ routes to a billing upstream with read_timeout = 180s and retries = 0. With no tools at all (--tools=), these were real answers across the lab runs:

RunWhat came backWhy it is wrong
No tools"I couldn't find acme-gate.conf in this workspace, C:\..., or your user profile."It searched nothing. The result showed num_turns 1 and the init line listed 0 tools. The claim of a search was invented.
No toolsText shaped like a tool call (Glob with **/acme-gate.conf) followed by a made-up "No files found" result.A transcript of work that never happened, printed as the answer.
Read allowed, stale notes in the prompt, evidence required"Read timeout is 180s (acme-gate.conf:13), and retries are 0 (acme-gate.conf:14). The notes saying 60s and 3 are out of date."Correct, and checkable in five seconds.

The failure is not that the model lies. It is that a fluent answer and a grounded answer look the same on the screen. Your defence is to make grounding the default and to make the evidence visible.

Read on demand versus stuffing

There are two ways to put source material in front of the model.

Stuff it in up frontLet the model read on demand
HowPaste files into the prompt, import them in CLAUDE.md, pipe them on stdin.Grant Read, Grep and Glob; ask a question; the model searches and reads what it needs.
CostEvery token on every request, relevant or not.Only what was read, from the turn it was read.

RiskDilution; stale copies.The model skips the read and answers from prior. Counter it with the prompt below.

Claude Code is built for the second way. Its tools are a search engine over your files, used at the moment of need.

Retrieval and RAG, honestly

Retrieval-augmented generation is the same idea run by a program instead of the model: split documents into chunks, index them (often by embedding similarity), fetch the top matches for a question, and paste them into the prompt. It is the right tool when the corpus is too large to search with grep, lives outside the file system, or the caller is not an agent with tools. Its weaknesses are the chunker and the ranker: the passage that answers the question can be split across chunks or ranked eleventh, and the model then answers from what it was given, confidently. In an agent session with file tools, the model's own Grep and Read are a retrieval system whose queries you can see and whose results you can check. Prefer them until the corpus forces you elsewhere. MCP servers that expose a search tool are the usual bridge to corpora that are not files.

Asking for evidence

Three sentences turn an answer you have to trust into one you can check:

Read the file first. Cite file:line for each value you report.
If the file does not say, answer "not in the file".

Then check a citation. Select-String -Path acme-gate.conf -Pattern read_timeout printed line 13 as read_timeout = 180s, matching the claim. A citation that points at the wrong line is your signal that the rest needs checking too. For anything that matters (a firewall rule, a retention setting, a version pin) make "evidence or it did not happen" the rule, and put that rule in CLAUDE.md.

No read, no answer: require file:line evidence for any claim about your systems, and spot-check one citation.
Removing tools to make a run "safe" and then trusting its answer. A model with no tools has nothing but its prior. It will still answer, and it may tell you it looked.

Self-check
  • Which single category is largest in your /context output? On a default install it is System tools, about two thirds of the total.
  • Add the non-deferred categories. Do they equal the total? They should: deferred tools are listed but not counted.
  • Why is the usage prompt side (about 21,700) larger than /context (about 17.2k)? /context is an estimate by category; usage is what the API counted, including per-session text such as environment details.
  • Why did run 2 still write some cache? The part of the prefix unique to each new session (its first message, environment details) is new every time. Only the shared part is read.

Ask the same question about a made-up config file with no tools and then with Read allowed and evidence required, and check both answers against the file.

  1. Make the folder and write the config.

    New-Item -ItemType Directory -Force {{LAB}}/m1/lab3 | Out-Null; cd {{LAB}}/m1/lab3
Set-Content -Encoding utf8 acme-gate.conf -Value @'
# acme-gate: edge proxy for the acme web tier
[listen]
port = 8443
tls_profile = modern

[upstream web]
servers = web-01:9080, web-02:9080
read_timeout = 47s
retries = 2

[upstream billing]
servers = bill-01:7311
read_timeout = 180s
retries = 0

[routes]
/api/      -> web
/billing/  -> billing
/invoice/  -> billing

[limits]
max_body = 12m
idle_close = 75s
'@
$q = 'Our edge proxy config is acme-gate.conf. What read timeout and how many retries apply to requests for /invoice/? Answer in two short lines.'
$notes = 'Notes from last month: the billing upstream in acme-gate.conf has read_timeout = 60s and retries = 3.'

  2. Ask with no tools at all. Write --tools= with the equals sign: Windows PowerShell 5.1 drops an empty "" argument, so --tools "" does not reach Claude Code intact.

    claude -p $q --model haiku --setting-sources project --strict-mcp-config --tools= --max-turns 1 --output-format json > a.json
$r = Get-Content a.json -Raw | ConvertFrom-Json; $r.result; "turns: $($r.num_turns)"

    Expected: turns: 1 and no correct values. In the lab runs the result was either text shaped like a tool call (Glob for **/acme-gate.conf) with no real answer, or a statement that the file could not be found in the workspace or the user profile. No search happened: there were no tools.

  3. Add stale notes to the prompt, still with no tools.

    claude -p "$notes $q" --model haiku --setting-sources project --strict-mcp-config --tools= --max-turns 1 --output-format json > b.json
$r = Get-Content b.json -Raw | ConvertFrom-Json; $r.result

    Expected: no correct values. Depending on the run, the model repeats the notes (60s and 3), prints a fake Grep call as text, or declines. Whatever it says, it has not seen the file.

  4. Same prompt with the notes, Read allowed, and evidence required.

    claude -p "$notes $q Read the file first and cite file:line for each value." --model haiku --setting-sources project --strict-mcp-config --tools "Read" --allowedTools "Read" --max-turns 3 --output-format json > c.json
$r = Get-Content c.json -Raw | ConvertFrom-Json; $r.result; "turns: $($r.num_turns)"

    Expected: turns: 2 (one Read, one answer). "Read timeout is 180s (acme-gate.conf:13), and retries are 0 (acme-gate.conf:14)", with a note that the 60s and 3 in the notes are out of date and that /invoice/ routes to billing at line 19.

  5. Check the citations against the file.

    Select-String -Path acme-gate.conf -Pattern 'read_timeout|retries|/invoice/' | ForEach-Object { "$($_.LineNumber): $($_.Line)" }

    Expected: lines 8 and 9 (web: 47s, 2), 13 and 14 (billing: 180s, 0), and 19 (/invoice/ -> billing). The grounded answer's line numbers match.

Self-check
  • What proves run A did not look at the file? num_turns 1 and --tools=: there was no tool to look with. Any claim of a search is invented.
  • A confident answer of "47s and 2" would have been plausible. Why? Those are real values in the file, for the wrong upstream. A model guessing from a partial view, or an earlier read of only the top of the file, produces exactly this kind of wrong answer.
  • Which part of the prompt in run C made the answer checkable? "cite file:line for each value". Without it you get the values but no way to verify them except reading the file yourself.

Resume one headless session for four turns that each read a log file, tabulate the prompt side per turn, compact with instructions, and measure the drop.

  1. Make the folder and four 150-line log files.

foreach ($n in 1..4) {
  $lines = foreach ($i in 1..150) { "2026-11-0{0} 10:{1:D2}:{2:D2} web-0{0} INFO request id={3} path=/api/orders status=200 ms={4}" -f $n, ($i % 60), (($i * 7) % 60), (100000 + $n * 1000 + $i), (20 + ($i * 13) % 400) }
  Set-Content -Encoding utf8 "app-$n.log" -Value $lines

    Expected: four files of about 12.9KB each.

  2. Define a helper that turns one result into a table row. prompt is the size of the last model call in the turn, which is the window size at the end of that turn.

    function Row($turn, $file) {
  $r = Get-Content $file -Raw | ConvertFrom-Json; $u = $r.usage; $last = $u.iterations[-1]
  [pscustomobject]@{ turn = $turn
    prompt = $last.input_tokens + $last.cache_creation_input_tokens + $last.cache_read_input_tokens
    cache_write = $u.cache_creation_input_tokens; cache_read = $u.cache_read_input_tokens
    output = $u.output_tokens; cost = [math]::Round($r.total_cost_usd, 4) }
}

  3. Start a session with Read as the only tool, and keep its id.

    claude -p "Reply with the single word OK." --model haiku --setting-sources project --strict-mcp-config --tools "Read" --allowedTools "Read" --output-format json > t0.json
$sid = (Get-Content t0.json -Raw | ConvertFrom-Json).session_id
$rows = @(Row 0 t0.json)

    Expected: a session id (a UUID). Turn 0's prompt is about 4,800 tokens, far below Lab 1's 21,700, because only one tool definition is loaded.

  4. Resume it four times, reading one file per turn.

    foreach ($n in 1..4) {

$rows | Format-Table -AutoSize

Self-check
  • What is the slope of your prompt column, in tokens per turn? About 6,800: the size of one log file as tokens. The answers added almost nothing.
  • If this session went on reading one such file per turn, roughly when would it reach the default auto-compact trigger of about 967K? After about 140 turns (967,000 / 6,800). Long before that, every turn would carry tens of thousands of tokens of logs it no longer needs.
  • What did compaction lose? The log contents and the exact wording of every turn. Ask a question about a specific line of app-2.log and the model has to read the file again.

Run a measuring script against a project of your own, read its numbers against a checklist, and change the instruction files until the checklist passes.

  1. Save the audit script in the lab folder. It lists every CLAUDE.md, CLAUDE.local.md, AGENTS.md and .claude/rules file under the project with line count, size, imports, HTML comments and backticked file references that do not exist, then asks /context all (from inside the project, project settings only) for the token cost of each file that loads at launch. It writes audit.txt in the lab folder and changes nothing in the project.

    param([Parameter(Mandatory)][string]$Project)
$Project = (Resolve-Path $Project).Path
$out = New-Object System.Collections.Generic.List[string]
$files = @(Get-ChildItem -Path $Project -Recurse -File -Force -Include CLAUDE.md, CLAUDE.local.md, AGENTS.md -ErrorAction SilentlyContinue | Where-Object { $_.FullName -notmatch '\\(node_modules|\.git)\\' })
$rules = Join-Path $Project '.claude\rules'
if (Test-Path $rules) { $files += @(Get-ChildItem $rules -Recurse -File -Filter *.md) }
$out.Add("FILES")
foreach ($f in $files) {
  $text = Get-Content $f.FullName
  $imports = @($text | Select-String -Pattern '(^|\s)@[\w./~\\-]+' -AllMatches).Count
  $comments = @($text | Select-String -Pattern '<!--').Count
  $missing = @()
  foreach ($m in ($text | Select-String -Pattern '`([\w./-]+\.(md|ps1|sh|json|yml|yaml|txt))`' -AllMatches)) {
    foreach ($g in $m.Matches) { $p = Join-Path $Project $g.Groups[1].Value; if (-not (Test-Path $p)) { $missing += $g.Groups[1].Value } }
  }
  $flag = if ($text.Count -gt 200) { 'OVER 200' } else { 'ok' }
  $out.Add(("{0}  lines={1} ({2})  bytes={3}  imports={4}  html-comments={5}  missing-refs={6}" -f $f.FullName.Substring($Project.Length), $text.Count, $flag, $f.Length, $imports, $comments, ($missing -join ',')))
}
Push-Location $Project
$ctx = claude -p "/context all" --model haiku --setting-sources project --strict-mcp-config
Pop-Location
$out.Add("CONTEXT")
$ctx | Where-Object { $_ -match 'Memory files|^\| (Project|Local|User|Managed)|System prompt \||System tools \|' } | ForEach-Object { $out.Add($_) }
$out | Set-Content -Encoding utf8 audit.txt
$out

    Save it with your editor, or paste it into Set-Content -Encoding utf8 {{LAB}}/m1/audit.ps1 -Value @' ... '@.

    1LengthEvery file is 200 lines or fewer.

Self-check
  • Your Memory files total went from A to B tokens. Over a day of 200 model calls, how many prompt tokens is that? 200 x (A - B). On an API key multiply by your model's cache-read price; on a plan it is window share you get back.
  • You moved a 40-line release procedure into a skill. What is still in context every session? Its name and description in the skills listing. The 40 lines load only when the skill is invoked.
  • The audit shows an AGENTS.md but /context does not list it. Why? A CLAUDE.md or CLAUDE.local.md on the path takes precedence, so AGENTS.md is not read. Import it with @AGENTS.md from the CLAUDE.md, or merge them.

Flag or commandEffect

Failure modes

SymptomCauseFix
The model ignores a CLAUDE.md rule.File too long, rule vague, contradicted elsewhere, or file not loaded.Check /context all Memory files; shorten; make the rule concrete; remove the conflict; use a hook if it must always happen.
A rule worked early and stopped later.It was only in the conversation, or in a path-scoped rule, and compaction summarised it away.Move it to the project-root CLAUDE.md or an unscoped rule; add Compact Instructions.
Confident answer about a file that is wrong.The model did not read the file, or read an old version earlier in the session.Require a read and file:line evidence; check one citation.
A run with no tools says it searched.Fabricated action; it had nothing to search with.Trust num_turns and the init line, not the prose.
Every turn gets slower and dearer.Tool results piling up in the window./compact with instructions, /clear between tasks, filtered reads, subagents for bulk.
Splitting CLAUDE.md into imports did not reduce cost.Imports load with the importing file.Path-scoped rules or skills.
AGENTS.md is not read.A CLAUDE.md or CLAUDE.local.md exists on the path.Add @AGENTS.md to the CLAUDE.md.
Headless overhead is large for a tiny job.Default tool set and skills listing in every request.Pass --tools with only what the job needs.
