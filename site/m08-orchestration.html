Orchestration is running more than one model session on one job: a lead and its subagents, a set of workers fed from a queue, a pipeline of stages, a writer and a reviewer. It is distributed systems work with an unreliable, very fluent worker in every slot, so the old rules apply: define the interface, keep state outside the process, make steps idempotent, verify independently and cap everything. This module covers the shapes, the brief that sits between them, and the ways a fleet fails in practice.

After this module you can

  • Pick an orchestration shape for a job, estimate what it adds in tokens and coordination, and say when one session is the better answer.
  • Write a brief with a goal, a done-test a script can check, a scope fence, inputs by path, a return contract and a blocked rule, and grade a worker's run against it.
  • Keep a job's state in files and a queue rather than in a conversation, and make each step safe to run twice.
  • Write a handoff file a cold session can finish from, and decide when to park a session instead of keeping it warm.
  • Add a reviewer stage that returns PASS or FAIL with evidence as validated JSON, and gate on it with a script.
  • Name the common fleet failures by symptom, and set concurrency, turn and budget caps plus a kill switch.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key).
  • Windows PowerShell 5.1 or later. The labs use background jobs (Start-Job) for parallel workers.
  • About $0.05 of API spend, or a small share of a plan's 5-hour window. Every run uses Haiku.
  • The module "Headless runs and subagents", or the recap below.

If you skipped the prerequisites

claude -p "prompt" runs one headless session and exits. With --output-format json it prints one JSON object with result (the final text), session_id, num_turns, total_cost_usd, usage (the four token counts), is_error, subtype (success or an error such as error_max_turns) and permission_denials. --allowedTools "Read,Write" grants tools without a prompt; in a headless run anything that would need a prompt is denied, and the run carries on. --max-turns caps the agent loop and --max-budget-usd caps estimated spend. A subagent is a second context window the main session starts with the Agent tool: it gets its own system prompt and tools, does its work, and only its final report comes back to the parent. Every fresh session or subagent pays a fixed prompt overhead before it does anything: on this course's test machine a one-word Haiku reply carried about 21,700 prompt tokens (system prompt and tool definitions), mostly as cache write and cache read. On an API key you pay per token; on a subscription plan the same tokens draw down a 5-hour window and weekly limits, and total_cost_usd is a list-price estimate, not a charge.

Four shapes

Almost every multi-agent setup is one of four shapes, or two of them nested. They differ in where the context lives, who decides what happens next, and how results travel back.

What each shape costs

There are two bills. The token bill is what the sessions consume. The coordination bill is the work you do to define interfaces, carry state between sessions and debug a run where three processes each did something plausible.

The token bill starts with the fixed overhead. Every new session and every subagent re-sends its own system prompt and tool definitions before it reads a word of your task. In the recap's measurement that was about 21,700 prompt tokens for a one-word answer. Ten workers pay it ten times, and a worker that is restarted pays it again. Caching softens it: identical prefixes are read back at a tenth of the input price or less. It does not remove it, because each new session writes its own conversation into the cache.

On top of the overhead, every handoff moves text. A subagent's report becomes input to the parent. A pipeline stage re-reads the files the last stage wrote. A reviewer reads the whole product and the source it was built from. In this module's labs, on Haiku, a worker that counted eight CSV rows cost about $0.004, and the reviewer that checked its output cost about $0.005 to $0.006. Checking carefully costs about as much as doing.

When not to orchestrate

A single session with a clear prompt beats a fleet whenever the job fits comfortably in one context, has one done-test, and gains nothing from parallel work or an independent check. Orchestration earns its cost for four reasons only:

  • Parallelism. The items are independent and wall-clock time matters.
  • Context limits. The work would push one session into compaction, or the detail of one part would crowd out the rest.
  • Independent verification. A second context that did not write the product is the check you want.
  • Different permissions. One stage may read production, another may only write a report. Separate sessions get separate tool grants.

If none of these applies, the coordination bill buys nothing. Most "multi-agent" failures in this module start with a job that did not need more than one agent.

Orchestrate for parallelism, context limits, independent checking or separate permissions, and for nothing else.
Fan-out feels free because each worker's cost is small. Ten workers each paying a 20,000-token overhead, retrying twice, and handing a 3,000-token report to a parent cost more than the single session would have, and finish no sooner if the parent then reads every report in series.

Why the brief carries the whole job

A worker starts with no memory of your conversation, your intent or the last attempt. Its context is its system prompt, whatever project instructions load, and the brief. Everything you meant but did not write is filled in by the model's best guess, and the guess is fluent enough to look like understanding. Treat the brief the way you treat an API contract between two services: it states inputs, outputs and error behaviour, and anything outside it is undefined.

Six parts

PartWhat it saysTest that it is good
GoalOne or two sentences: the outcome and who uses it.A stranger could explain why the task exists.
Done-testA numbered list of checks that decide finished or not finished.A script, or a reviewer with no other context, could apply every item.
Scope fenceWhat the worker may create or change, and what it must not touch.The grader can check it: a file list, a hash, a path rule.

The last part matters more than it looks. A model with no permitted failure path completes the task anyway, by assumption. Giving it a cheap, explicit way out (BLOCKED <reason>) turns silent guesses into reports you can act on.

A bad brief and its repair

The bad brief below is typical of a request typed into a chat: clear to the writer, empty for a cold worker.

Have a look at the services file and tidy up a list of the ports that matter. Make it neat.
# Brief: list the ports of running services

## Goal
List the TCP ports of the services that are running, for a firewall review.

## Done when (grade.ps1 checks exactly this)
1. open-ports.txt exists in this folder.
2. It holds one port number per line, digits only, sorted from low to high, nothing else.
3. The ports are exactly those of rows in services.csv whose state is running.
4. services.csv is unchanged and no other file is created.

## Scope
Create open-ports.txt only. Do not edit services.csv. No scripts, notes or backups.

## Inputs
- services.csv (columns: name,port,state)

## Return
One line: DONE <number of ports>, or BLOCKED <one-sentence reason>.

## If blocked
If a state value is not one of running, stopped, disabled, return BLOCKED and name it. Do not guess.

The contract said "one line"; it did not say "and nothing else". The lab 1 brief does say so, and its worker complied. Write the contract as tightly as the parser that reads it.

Writing the done-test first

Write the done-test before the rest of the brief, and write the grading script from it at the same time. If you cannot write the script, the done-test is not concrete yet. A done-test that only a person can apply ("the summary is clear") is fine for a reviewer session, provided it is numbered so the reviewer can cite which item failed.

If you cannot write the grading script, you have not finished writing the brief.
A brief that refers to "what we discussed" or "the earlier approach" points at a context the worker never had. It gets a guess, delivered with the same confidence as a fact.

The system of record

A model's context window is process memory: large, fast, and gone when the process ends, compacts or is replaced. A fleet needs a system of record that survives all three. Use a tracker or a queue for the state of each work item (open, claimed by whom, done, blocked) and files for the content that moves between sessions (briefs, products, handoffs, verdicts).

WhatWhere it livesWhy
Item stateTracker or queue directoryOne place answers "who has this and is it done". Survives any session.
Who holds an itemA claim record, created atomicallyTwo workers cannot both hold it.
The taskA brief fileRe-readable by a retry, a reviewer or a successor.
The productOutput files at agreed pathsA grader checks files, not claims.
Progress mid-taskA handoff fileA cold session can continue from it.

Why chat is not a record

A message between agents, or a line in a session's transcript, is not state. It cannot be queried, it is not ordered against other agents' messages, and the receiver may compact it away. "I told the worker in the chat" means the instruction exists in one context window, for as long as that window lasts. When you need to know what happened, read the files and the tracker. When something must happen, write it there.

Idempotent steps

Workers crash, time out and get retried. A step is safe to retry when running it twice has the same effect as running it once. Three habits get you there:

  • Check before doing. If done\job2.txt exists, skip job 2. Lab 4's worker does this before it claims.
  • Write whole outputs. Produce a complete file (write to a temporary name, then rename) rather than appending to one, so a retry replaces instead of duplicating.
  • Claim atomically. Create the claim with an operation that fails if it already exists. In .NET that is [IO.File]::Open($path, 'CreateNew', 'Write'). A check-then-create (if (-not (Test-Path ...))) has a gap two workers can both pass through.

When to hand off

Hand off when a session has done a clean unit of work and the rest needs a context it does not have room for, when it is about to wait for something slow (a person, a nightly job, another team), or when its context has grown large enough that every turn re-reads a long history. Each turn re-sends the whole conversation, so a session at 300,000 tokens pays for 300,000 prompt tokens on every turn, mostly as cache read. A successor that starts from a 2,000-token handoff file pays the fixed overhead and the handoff, and nothing else.

What a handoff file must contain

SectionContent
GoalThe whole job in one sentence, not just the remaining step.
Done-testHow the successor proves the whole job is finished. Copy it from the brief.
Done so farEach finished step and the file it produced.
Next stepThe exact next action: input file, output file, format rule.
Do not redoFinished files that must not be rewritten.
Open questions or blockersOr "none". A successor that finds a blocker here asks instead of guessing.

In lab 3 a session finished two of three steps and wrote a handoff from this template. A cold session with no --resume and the plan file hidden finished step three correctly and left both finished files byte-for-byte unchanged. The handoff it read included the expected final line, the exact format rule, and a "Do not redo" list naming both files.

Parked waits, not warm idle sessions

A session that waits with its context loaded costs nothing while idle, but its cache entry expires. Claude Code's main conversation uses a 1-hour cache lifetime on a subscription within plan usage, and 5 minutes on an API key, on usage credits and on cloud providers. When the session resumes after that, the first turn writes the whole context back into the cache at the write price (1.25 times input for the 5-minute lifetime, 2 times for 1 hour). A 300,000-token session woken after a long wait pays to write 300,000 tokens before it does anything.

Parking means: write the handoff, record the wait in the tracker (what is awaited, from whom, and how to resume), and end the session. When the answer arrives, start a cold session from the handoff. You pay the fixed overhead and a small file, not a large rewrite, and the wait is visible in the tracker rather than hidden in an idle process.

If a fact lives only in a context window, the fleet does not know it.
A handoff that lists only the next step, without the goal and the done-test, gets a successor that does the step and reports the whole job done.

Why the author cannot be the check

A session that wrote a product has its own reasoning in context. Asked "is this right", it re-reads that reasoning and agrees with it. Its final message reports what it intended, which may differ from what is on disk. Both effects are strongest exactly when the output is wrong in a way the author did not notice. So the check is a separate stage, run by something that did not write the product: a script, a reviewer session with a different prompt, or both.

Structured verdicts

--json-schema makes a headless run return its answer as JSON that matches a schema, in the structured_output field of the result. A verdict schema with an enum for the verdict means a gate script never parses prose:

{"type":"object","properties":{"verdict":{"type":"string","enum":["PASS","FAIL"]},"failed_checks":{"type":"array","items":{"type":"integer"}},"evidence":{"type":"array","items":{"type":"string"}}},"required":["verdict","failed_checks","evidence"]}

In lab 2 the reviewer was given the worker's real output and a copy with one planted defect (closed,5 instead of closed,4). It passed the first and failed the second, citing check 4 with the four ticket ids that have status closed. It also failed check 2 on the defective copy for a reason nobody planted: the copy had been written with Set-Content -Encoding utf8, which in Windows PowerShell 5.1 adds a byte-order mark, so the first line was no longer exactly status,count. The script grader in lab 1 reads the file with Get-Content, which hides the mark, and would have passed it. A script and a reviewer catch different things; use both where it matters.

defect : exit 0 verdict=FAIL failed=2,4 cost=0.0045
   evidence: Check 2 fails: defect/status-counts.csv begins with a UTF-8 BOM (EF BB BF), so its first line is ?status,count rather than exactly status,count. ...
   evidence: Check 4 fails: defect/status-counts.csv lists closed,5, but tickets.csv has 4 rows with status closed (ids 102, 105, 106, 108). ...
GATE OK: reviewer passed the good file and failed the planted defect

Gates in hooks

A gate that depends on the model choosing to run it is a suggestion. Hooks run whether the model wants them or not (see the module "Hooks"). PreToolUse can deny a write outside the scope fence before it happens. Stop, SubagentStop and TaskCompleted are blockable events, so a hook there can run the done-test script and refuse to let the session or subagent finish while it fails. Test the exact blocking behaviour on your version before you rely on it. In a pipeline you control from a script, the gate is simpler still: the next stage does not start unless the verdict file says PASS.

The thing that decides "done" must be something other than the thing that did the work.
A reviewer given the author's transcript, or asked "does this look right", inherits the author's framing and approves it. Give it the brief, the product and the source of truth, and nothing else.

Each failure below has turned up in real fleets. They share a cause: the worker produced fluent text where the system needed a checked fact. Each countermeasure moves a decision from the model's prose into a file, a script or a hook.

The confident wrong answer, and the confident retraction

Symptom: a worker reports a finding as fact ("the rule is missing on web-01"). Challenged, it reverses just as firmly ("you're right, the rule is present"), and neither statement was checked. Cause: the model produces the most plausible text for the context; a challenge changes the context, so it changes the answer. Neither is evidence. Countermeasure: require evidence with every claim (the command and its output, the quoted line), and answer a challenge by re-running the check, not by asking again.

Stopping short and reporting done

Symptom: DONE, but two of five items were skipped, or a test was "verified" by reading the code. Cause: the brief had no checkable done-test, or the worker graded itself. Countermeasure: a numbered done-test, a grading script or reviewer stage that runs after the worker, and a gate that ignores the worker's own verdict.

Scope creep

Symptom: the worker fixed the task and also "tidied" three other files, or edited the input. In lab 5 the bad brief's worker rewrote services.csv in place on two of three runs. Cause: no scope fence, or a fence the worker could not see. Countermeasure: list what may be created or changed; check it in the grader (hashes, file list); deny writes outside it with a PreToolUse hook or a narrow --allowedTools.

A lost or duplicated message between agents

Symptom: a worker never received an instruction, or acted on it twice. Cause: the message lived in transport only (a chat line, a pipe, a relay) with no acknowledgement and no record. Countermeasure: put the instruction in the tracker or a file, give it an id, and make acting on it idempotent, so a duplicate is a no-op and a missing one is visible as an item that never changed state.

Two agents editing the same files

Symptom: changes disappear, or a file holds a mix of two edits. In lab 4, two workers without claims each processed all three jobs: six model calls for three jobs. Cause: no ownership. Each worker read the same queue and acted. Countermeasure: an atomic claim per item, one owner per file or folder, and separate working copies (a git worktree per worker) where work overlaps.

A worker waiting on a human who was never asked

Symptom: a worker reports "I need approval to write that file" or "please confirm", and the run ends. Nobody saw it. Cause: a headless run cannot show a permission prompt, so the tool call is denied and the model writes a polite request into its final message. The run still ends with subtype success and exit code 0. Countermeasure: grant exactly the tools the brief needs, read permission_denials in every result and treat a non-empty list as a failure, and route real questions to a tracker field a person watches. With --permission-prompts none the denial is explicit.

"subtype":"success","is_error":false,
"permission_denials":[{"tool_name":"Write","tool_input":{"file_path":"...\\b.txt","content":"hi"}}],
"result":"The file was not created. When I called the Write tool ... the harness denied permission. ..."

Runaway fan-out and cost

Symptom: a lead spawns a worker per file, each spawns helpers, retries multiply, and the bill or the plan window is gone by mid-morning. Cause: no cap on concurrency, depth, turns or spend, and a retry policy with no limit. Countermeasure: the caps in the next lesson, set before the first run, and a kill switch that stops new work without killing finished work.

Every failure here is fixed by moving a decision out of the model's prose and into a file, a script or a hook.
Exit code 0 and "subtype":"success" mean the session ended normally. They say nothing about whether the task was done or whether a tool was denied.

Four caps

The budget cap is checked after spending, so it can be overshot by up to one response. In lab 4 a run with a cap of $0.0001 stopped with error_max_budget_usd after spending about $0.0002, and on a run with a cold cache about $0.0016. Set the cap with headroom, and treat it as a fuse, not a forecast.

A kill switch should stop new work, not destroy work in progress. A worker that checks for STOP before each claim leaves no half-claimed items. A hard process kill is the second line, for a worker that hangs; pair it with idempotent steps so the killed item can be retried cleanly.

Sizing a fleet

Estimate per-item cost from a real run, not a guess: run one item, read total_cost_usd and usage, and multiply by items and by your expected retry rate. Then choose the model per stage. Opus 5.5 lists input and output at 40 times the Haiku 5.5 rate for prompts under 100,000 tokens. A reviewer that checks a count needs Haiku; a worker that designs a firewall change may need more. Every worker should log its session_id, cost and turns next to its item, so a bad night can be traced to the item and the stage that caused it.

Set concurrency, turn, spend and time caps before the first fleet run, and log cost per item from the start.
A budget cap per run does not cap a fleet. Fifty runs under a $0.50 cap can spend $25, and a retry loop can start the fifty-first.

@'

  2. Write the brief.

    @'
# Brief: count tickets by status

## Goal
Produce a count of tickets per status from tickets.csv.

## Done when (the grader checks exactly this)
1. status-counts.csv exists in this folder.
2. Its first line is exactly: status,count
3. It has one row per distinct status in tickets.csv, sorted by status name A to Z.
4. Each count equals the number of rows in tickets.csv with that status.

## Scope
- You may create status-counts.csv. Nothing else.
- Do not edit tickets.csv. Do not create helper scripts or notes.

## Inputs
- tickets.csv (columns: id,status,owner)

## Return
Your final message is one line and nothing else:
DONE status-counts.csv <number of data rows>
or, if you cannot meet the done-test:
BLOCKED <one-sentence reason>

## If blocked
Do not guess and do not write a partial file. Return BLOCKED.
'@ | Set-Content -Encoding utf8 brief.md

  3. Write the grader from the done-test, and record the input's hash so the grader can check the scope fence.

    @'
# Grades a run against brief.md. Exit 0 = PASS.
param([string]$Result = 'worker.json')
$fail = 0
function Check($name, $ok) { if ($ok) { "PASS  $name" } else { "FAIL  $name"; $script:fail++ } }
$expected = Import-Csv tickets.csv | Group-Object status | Sort-Object Name | ForEach-Object { "$($_.Name),$($_.Count)" }
$exists = Test-Path status-counts.csv
Check 'status-counts.csv exists' $exists
if ($exists) {
  $lines = @(Get-Content status-counts.csv | Where-Object { $_.Trim() -ne '' })
  Check 'header is status,count' ($lines[0] -eq 'status,count')
  Check 'rows match tickets.csv, sorted' ((($lines | Select-Object -Skip 1) -join ';') -eq ($expected -join ';'))
}
Check 'tickets.csv unchanged' ((Get-FileHash tickets.csv).Hash -eq (Get-Content tickets.sha256))
$extra = Get-ChildItem -File | Where-Object { $_.Name -notin 'tickets.csv','brief.md','grade.ps1','tickets.sha256','status-counts.csv','worker.json' }
Check 'no files outside scope' (-not $extra)
$r = Get-Content $Result -Raw | ConvertFrom-Json
Check 'return line matches contract' ($r.result.Trim() -match '^DONE status-counts\.csv \d+$')
"cost_usd=$([math]::Round($r.total_cost_usd,4)) turns=$($r.num_turns) denials=$(@($r.permission_denials).Count)"
exit $fail
'@ | Set-Content -Encoding utf8 grade.ps1
(Get-FileHash tickets.csv).Hash | Set-Content tickets.sha256

  4. Run the worker. --setting-sources project loads only this folder's settings, and --strict-mcp-config loads no MCP servers, so your personal settings, hooks and MCP servers stay out of the run and out of the measurement. Every headless run in this module uses both. --allowedTools "Read,Write" grants exactly what the brief needs.

    claude -p "Do the task in brief.md exactly." --model haiku --setting-sources project --strict-mcp-config --allowedTools "Read,Write" --max-turns 8 --output-format json > worker.json
(Get-Content worker.json -Raw | ConvertFrom-Json).result
Get-Content status-counts.csv

    Expected: the result is the single line DONE status-counts.csv 3, and the file holds status,count, closed,4, open,3, pending,1.

  5. Grade the run.

    .\grade.ps1; "grade exit $LASTEXITCODE"

    Expected: six PASS lines, then something like cost_usd=0.0037 turns=6 denials=1 and grade exit 0. The one denial on the test run was the worker trying to use Bash to write and check the file; Bash was not granted, the call was denied, and the worker used Write instead.

Self-check

  2. Make two candidates: the worker's output, and a copy with one planted defect.

  3. Write the verdict schema. Windows PowerShell 5.1 strips bare double quotes from arguments passed to a program, so the schema's quotes are escaped as \" when it is passed on the command line. Without the escape, claude stops with --json-schema is not valid JSON. The flag takes the JSON text itself, not a file path.

    @'
{"type":"object","properties":{"verdict":{"type":"string","enum":["PASS","FAIL"]},"failed_checks":{"type":"array","items":{"type":"integer"}},"evidence":{"type":"array","items":{"type":"string"}}},"required":["verdict","failed_checks","evidence"]}
'@ | Set-Content -Encoding ascii verdict.schema.json
$schema = (Get-Content verdict.schema.json -Raw).Trim() -replace '"', '\"'

  4. Run the reviewer on each candidate. It gets a reviewer's prompt, only the Read tool, and the source of truth.

    $review = 'You are a reviewer, not the author. Check {0}\status-counts.csv against the numbered "Done when" list in brief.md, using tickets.csv as the source of truth. Count the rows yourself. Do not fix anything. For each failed check give its number and quote the line that proves it.'
foreach ($c in 'good', 'defect') {
  claude -p ($review -f $c) --model haiku --setting-sources project --strict-mcp-config --allowedTools "Read" --max-turns 6 --output-format json --json-schema $schema > "review-$c.json"
  $r = Get-Content "review-$c.json" -Raw | ConvertFrom-Json
  "$c : verdict=$($r.structured_output.verdict) failed=$($r.structured_output.failed_checks -join ',') cost=$([math]::Round($r.total_cost_usd,4))"
  $r.structured_output.evidence | ForEach-Object { "   evidence: $_" }
}

    Expected: good : verdict=PASS failed= cost=0.0062 with one evidence line per check (the test run listed the ticket ids behind each count), and defect : verdict=FAIL failed=2,4 at about $0.005. Check 4 fails on closed,5. Check 2 also failed on the test run: Set-Content -Encoding utf8 in Windows PowerShell 5.1 writes a byte-order mark, so the defective copy's first line is not exactly status,count. The reviewer found a second defect nobody planted.

  5. Gate on the verdicts with a script.

    Expected: GATE OK.

Run two parallel workers over a three-job file queue, watch them double-process every job, prevent it with atomic claim files, then stop the fleet with a kill switch and trip a budget cap.

  1. Write the worker. It skips finished jobs, optionally claims each job with a file that only one process can create, and stops before a new job if a STOP file exists. The claim path is absolute: .NET file calls resolve relative paths against the process directory, not PowerShell's current location, and a relative claim path fails in a background job.

    mkdir {{LAB}}/m8/lab4 -Force; cd {{LAB}}/m8/lab4
@'
param([string]$Dir, [string]$Worker, [int]$Claims = 0)
Set-Location $Dir
foreach ($job in Get-ChildItem queue\*.txt | Sort-Object Name) {
  if (Test-Path STOP) { "$Worker saw STOP"; break }
  $id = $job.BaseName
  if (Test-Path "done\$id.txt") { "$Worker skip $id (done)"; continue }
  if ($Claims) {
    $claim = Join-Path $Dir "claims\$id.claim"
    try { $f = [IO.File]::Open($claim, 'CreateNew', 'Write'); $w = New-Object IO.StreamWriter($f); $w.Write("$Worker $(Get-Date -Format o)"); $w.Close() }
    catch { "$Worker skip $id (claimed)"; continue }
  }
  $word = (Get-Content $job.FullName -Raw).Trim()
  $out = claude -p "Reply with only this word in capital letters: $word" --model haiku --setting-sources project --strict-mcp-config --tools "" --max-turns 1 --max-budget-usd 0.05 --output-format json | ConvertFrom-Json
  Add-Content -Encoding ascii runs.log "$id $Worker $($out.result) $([math]::Round($out.total_cost_usd,5))"
  Set-Content -Encoding ascii "done\$id.txt" $out.result
  "$Worker did $id"
}
'@ | Set-Content -Encoding utf8 worker.ps1

  2. Define two helpers: one resets the queue to three jobs, one starts two workers as background jobs and waits for them.

    function Reset-Queue {
  Remove-Item queue, claims, done, runs.log, STOP -Recurse -Force -ErrorAction SilentlyContinue
  New-Item -ItemType Directory queue, claims, done | Out-Null
  'alpha' | Set-Content -Encoding ascii queue\job1.txt
  'bravo' | Set-Content -Encoding ascii queue\job2.txt
  'charlie' | Set-Content -Encoding ascii queue\job3.txt
}
function Start-Workers([int]$Claims) {
  $here = (Get-Location).Path
  $jobs = 'w1', 'w2' | ForEach-Object { Start-Job -FilePath .\worker.ps1 -ArgumentList $here, $_, $Claims }
  $jobs | Wait-Job -Timeout 240 | Receive-Job
  $jobs | Remove-Job -Force
}

  3. Run A: no claims.

    Reset-Queue; Start-Workers 0
Get-Content runs.log
"calls: $((Get-Content runs.log).Count) for 3 jobs"

    Expected: both workers report did job1, did job2, did job3, and calls: 6 for 3 jobs. Each line in runs.log costs about $0.00004 (no tools, so a tiny prompt). The "done" check did not help: both workers checked before either had finished.

  4. Run B: a claim file per job.

    Reset-Queue; Start-Workers 1
Get-Content runs.log
"calls: $((Get-Content runs.log).Count) for 3 jobs"
Get-ChildItem claims | ForEach-Object { "$($_.Name): $(Get-Content $_.FullName)" }

    Expected: lines such as w2 skip job1 (claimed), calls: 3 for 3 jobs, and three claim files each naming one worker and a timestamp. Which worker gets which job varies by run.

  5. Run C: the kill switch.

    Reset-Queue; New-Item STOP -ItemType File | Out-Null; Start-Workers 1
"calls: $(@(Get-Content runs.log -ErrorAction SilentlyContinue).Count)"

    Expected: w1 saw STOP, w2 saw STOP, calls: 0.

  6. Run D: a per-run budget too small to finish. This run keeps the default tools, so its prompt is the normal size.

    claude -p "Reply with only the word OK." --model haiku --setting-sources project --strict-mcp-config --max-budget-usd 0.0001 --output-format json > budget.json
"exit $LASTEXITCODE"
$b = Get-Content budget.json -Raw | ConvertFrom-Json
"subtype=$($b.subtype) terminal_reason=$($b.terminal_reason) is_error=$($b.is_error) cost=$([math]::Round($b.total_cost_usd,4))"

    Expected: exit 1 and subtype=error_max_budget_usd terminal_reason=budget_exhausted is_error=True, with a cost above the cap: about $0.0002 with a warm cache, about $0.0016 cold.

Self-check
  • Why does CreateNew prevent the double pick-up when Test-Path on the done file did not? Creating the file and checking that it did not exist are one operation in the file system, so exactly one worker succeeds. A check followed by a separate action leaves a window that both workers pass through.
  • A worker crashes after creating its claim but before writing done\. What happens to that job, and what would you add? It stays claimed and is never done. Add a lease: a timestamp in the claim (already there) and a sweeper that releases claims older than a time limit, plus idempotent work so the retry is safe.
  • Run D spent more than its cap. What does that tell you about setting --max-budget-usd for a fleet? The cap is checked after spending, so it can be overshot by up to one response. Leave headroom, and cap the fleet separately (worker count, item count, kill switch).
