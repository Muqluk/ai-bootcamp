Most of what people run around Claude Code was not written by Anthropic: terminal multiplexers that keep a dozen agent sessions alive, skill collections published from somebody's own working directory, plugin marketplaces, MCP servers, and lists that point at all of them. Each one is a dependency that ends up holding some of your privileges. This module maps what exists, shows how to read a third-party item before it touches your machine, and how to adopt it at a fixed commit so that it only changes when you say so.

After this module you can

  • Sort a third-party item into its kind (multiplexer, skill collection, plugin, MCP server, installer, list) and say what that kind can do on your machine once adopted.
  • Tell Anthropic's own repositories and marketplaces from community work by name, and explain why a listing in an official marketplace is not a review of the code.
  • Compare tmux and herdr on platform, agent awareness, scripting interface and maturity, and script a pane from the documented commands.
  • Vet a skill repository at a pinned commit with git and PowerShell: file inventory, scripts, frontmatter fields, injected commands, hooks, licence, maintenance signals.
  • Vendor one reviewed skill into a project, record its provenance, and prove from the init line of a headless run that it loaded.
  • Review the diff between your pinned commit and a newer one before updating, and decide when writing your own short skill beats taking the dependency.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The labs were run on 2.1.322.
  • Windows PowerShell 5.1 or PowerShell 7, and git. Nothing else is installed by the labs: no multiplexer, no package, no plugin.
  • Network access to github.com for one clone of a public repository (about 180 files).
  • About $0.02 of Haiku usage at API list price for the six headless runs, or the same share of a subscription's 5-hour window.

If you skipped the prerequisites

From Skills: a skill is a folder that holds a SKILL.md file (YAML frontmatter, then a Markdown body) and, optionally, supporting files and scripts. It loads in layers. The description from the frontmatter sits in the context of every session so the model can decide when the skill applies; the body is loaded only when the skill is invoked, by you typing /name or by the model; supporting files are read when the body points at them; scripts are run through a tool, never loaded as text. Skills live in ~/.claude/skills/<name>/ (personal, all your projects), .claude/skills/<name>/ (project, committed with the repository), a managed location (enterprise) or a plugin's skills/ folder, where they are named /plugin-name:skill-name. On a name clash enterprise beats personal beats project. Frontmatter can do more than describe: allowed-tools pre-approves tools for the invoking turn, hooks registers hooks, and disable-model-invocation: true makes the skill run only when you type its name. The first line of claude -p … --output-format stream-json --verbose is an init event whose skills array is the scriptable proof of what loaded, and project skills only load when --setting-sources includes project.

The problem they solve

An interactive Claude Code session is a terminal program. Close the window or drop the SSH connection and the session's process dies with it. One session is easy to keep an eye on; eight are not, and eight windows give a script nothing to hold on to. A terminal multiplexer puts a server between you and the terminals. The server owns the terminal processes, you attach a client to look at them and detach without stopping them, and a command-line interface lets a script create a pane, type into it and read what is on its screen.

tmux

tmux describes itself as a terminal multiplexer that lets a number of terminals be created, accessed and controlled from a single screen, and be detached and later reattached. Its model has four nouns. The server is one background process that holds all state and exits when nothing is left running. A pane holds one terminal and the program in it. A window groups panes that are visible together. A session groups windows, and a client attaches a session to the terminal you are sitting at. Client and server talk over a socket file in /tmp.

tmux knows nothing about agents. To a script, an agent pane is a grid of characters: you find out whether Claude is working, finished or waiting for an approval by capturing the pane and matching text. That is workable and it is brittle, because the text you match is another program's user interface.

What Claude Code itself does with tmux

Claude Code uses tmux in two documented places. Agent teams can show each teammate in its own pane: the teammateMode setting (or the --teammate-mode flag, which the docs call experimental and which is absent from claude --help) takes in-process (the default), auto, tmux or iterm2. Split-pane mode needs tmux or iTerm2, and the docs state that it is not supported in VS Code's integrated terminal, Windows Terminal or Ghostty, and that tmux "has known limitations on certain operating systems and traditionally works best on macOS". The second place is claude --worktree <name> --tmux, which creates a tmux session for a worktree. Teams are covered in "Agent SDK and agent teams".

herdr

herdr calls itself a terminal workspace manager for AI coding agents. Its README (version 0.9.5) makes the same core promise as tmux, that a background server keeps terminals running when you close the client or lose an SSH connection, and adds what tmux leaves to you. It detects coding agents inside panes and marks each one working, blocked, done, idle or unknown. Its CLI and local socket API (a Unix domain socket, or a named pipe on Windows) have agent-level verbs. Its nouns are session, workspace (one per project), tab, pane and agent.

What adopting one costs you

A multiplexer is the most privileged row of the map. Its server holds every terminal you run inside it, and its socket is a control channel: whoever can talk to it can read your panes and type into them, including into an agent that runs with broad permissions. herdr's Windows page spells out one case. A server started from an elevated terminal refuses ordinary clients by default, and switching on allow_unelevated_clients "allows ordinary local processes belonging to that account to control administrator panes".

Look at the install route with the same eye. herdr's README offers a script piped to a shell (curl … | sh, or irm … | iex in PowerShell) next to package managers and release binaries; the piped form runs whatever the server returns that day, so download the script and read it, or take the binary. Then look at what the tool changes outside itself. herdr integration install claude is documented as writing a hook script into your Claude configuration directory and adding hook entries to its settings.json. That is a reasonable thing for it to do, and it is exactly the kind of change you want to know about before it happens, not after.

If the work is a batch of non-interactive runs, you do not need a multiplexer: start claude -p processes from a script and collect their JSON (Lab 4 does this). A multiplexer earns its place when sessions are interactive, long-lived, and need a person or another agent to look in and steer.
Driving an interactive agent by typing into its pane bypasses nothing and guarantees nothing. The text arrives as if you had typed it, at whatever moment the script fires, whether the agent is at its prompt, in the middle of a tool call or showing a permission dialog. Read the pane or wait for a state first, and treat a state as a hint.

What a collection is

A skill collection is a git repository of skill folders that somebody published, usually straight from their own setup. There is no registry in the package-manager sense, no signing, and no build: you are taking Markdown files, and sometimes scripts, from a branch that moves. Reading one collection closely

The Pocock repository is a good first read because it is small and nearly all prose. Its skills split on who may invoke them. At the commit vetted in Lab 1, 23 of the 38 carry disable-model-invocation: true: you type those by name and they orchestrate. The rest are model-invoked and hold the reusable discipline. The split shows in the smallest file in the repository:

---
name: grill-me
description: A relentless interview to sharpen a plan or design.
disable-model-invocation: true
---

Call the Skill tool with "grilling".

That is the whole skill: 157 bytes that hand over to a model-invoked skill, grilling, whose 2 KB body describes how to interview you in rounds. Nothing in either file runs code.

Three other things in the same repository show why you read before you install.

  • The plugin is a subset. .claude-plugin/plugin.json lists 27 skills. The misc and in-progress groups are not in it, so "the plugin" and "the repository" are different sets of files.
  • A skill can install enforcement. git-guardrails-claude-code (in misc) tells the agent to copy a bundled shell script into .claude/hooks/ or ~/.claude/hooks/ and to add a PreToolUse hook to a settings file. The script is 507 bytes of bash that needs jq, and the hook it adds matches the Bash tool only. On a Windows machine where shell commands go through the PowerShell tool, that guard would be installed and never fire (the Hooks module explains the matcher).
  • A skill can tell the agent to install packages. setup-pre-commit contains npx husky init. The skill does not run it; the model does, through your shell tool, under your permission rules.

None of this is hidden or hostile. It is what "instructions plus optional scripts" looks like in practice: the file you install is harmless text, and its effect is whatever the text persuades an agent with your tools to do.

Installers and directories

The npx skills command that both READMEs mention is the open skills CLI from the vercel-labs/skills repository (version 1.8.1, MIT, needs Node.js 22.20 or later). Its README describes npx skills add <owner/repo> with --skill to pick one, -a claude-code to pick the agent and -g for a global install instead of the current project. It installs by symlink from each agent's folder to one canonical copy, or by copy with --copy. It records each project skill in skills-lock.json with a computedHash, a SHA-256 over the installed files, which npx skills check and npx skills update compare against. It also "collects anonymous usage data" unless DISABLE_TELEMETRY=1 or DO_NOT_TRACK=1 is set. The lock file is a real control. The installer is also one more program that runs with your privileges and fetches from the network, and @latest means a different program each release. This module describes it and does not run it.

Directories and lists are where you will meet most collections. The skills.sh site is the directory the skills CLI points to. The Claude Marketplace web catalogue lists plugins from Anthropic's marketplaces, shows install counts and marks some plugins "Anthropic verified". The awesome-claude-code list is a single long README with sections such as Agent Orchestration, Skills, Status Lines, Security and Observability; it states that it has no affiliation with Anthropic, and the list itself is under a Creative Commons licence that forbids derivatives. An entry on any of these is a pointer. Install counts and stars measure how many people followed the pointer.

One format, several agents

Collections travel between agent products because the folder format is an open specification, Agent Skills. The Claude Code docs list the six frontmatter fields the specification allows: name, description, license, compatibility, metadata and allowed-tools. Claude Code accepts those and adds its own (hooks, context, model, paths and the rest). Two consequences for a reader of other people's skills. A field Claude Code does not recognise is ignored without an error, so a skill written for another agent loads here with part of its frontmatter silently inert. And files meant for other products ride along: every skill folder in the Pocock repository has an agents/openai.yaml that Claude Code never reads.

Judge a collection by reading three of its skills end to end, including the largest and one that mentions a setup step. Ten minutes of reading tells you more than any count on a directory page.

Why review is the control

There is no gate between a third-party skill and your session other than you. A skill's description enters the context of every session, its body enters when it is invoked, and from then on it is instructions with the same standing as your own. A plugin goes further and can run code that Claude Code's permission rules and sandbox do not cover, because those govern the tool calls Claude makes, not the hooks, monitors and servers a plugin runs by itself. So the review happens before the files reach a folder Claude Code loads from, on a copy you treat as data.

What Claude Code offers for pinning

The marketplace reference gives git-based plugin sources (github, url, git-subdir) two fields. ref is a branch or tag and defaults to the repository's default branch. sha is a full 40-character lowercase commit SHA, and when both are set Claude Code checks out sha. An archive source takes a sha256 digest, and Claude Code refuses the install when the download does not match. A marketplace itself can be added at a branch or tag with owner/repo#ref.

{
  "name": "formatter",
  "source": {
    "source": "github",
    "repo": "acme/formatter",
    "ref": "v2.0.0",
    "sha": "a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6e7f8a9b0"
  }
}

A tag is a name and can be moved; a SHA cannot. Anthropic's community marketplace works this way: where its catalogue pins a plugin to a commit SHA, "which it does for nearly every entry", Claude Code refuses to install a different commit.

Updates follow from how Claude Code computes a plugin's version: the version in the plugin's manifest first, then the one in the marketplace entry, and otherwise the commit SHA shortened to 12 characters. Auto-update refreshes each marketplace that has it on, recomputes versions and replaces the cached copy when one changed. It is on by default for Anthropic's official marketplaces and off for every other marketplace unless you set autoUpdate on the marketplace's entry or flip the toggle under /plugin. In an interactive session it runs after your first message, after a random delay of up to ten minutes, and tells you with Plugin updated: <name> · Run /reload-plugins to apply. The details, and the environment variables that switch it off, are in "Plugins and marketplaces".

A community collection distributed through claude-plugins-official inherits that marketplace's default: auto-update on. Reviewing the author's repository and then installing from the official marketplace gives you a reviewed first version and unreviewed later ones.

Vendoring by hand

For a few skills, a copy in the project is the simplest pin there is. The procedure is five steps, and Labs 1 to 3 walk through it.

  1. Clone without checking out a branch, then check out one commit by SHA.
  2. Review that commit with the checklist.
  3. Copy only the skill folder you reviewed into .claude/skills/. Keep the licence file with it.
  4. Record provenance in a register file in the project: source URL, path, commit, a content identifier, licence, who reviewed it and when.
  5. Commit. From now on the skill changes only through your own history.

Git already gives you a content identifier. Every file in a commit has a blob ID, and git hash-object computes the same ID for a file on disk, so one comparison proves that your vendored file is byte-for-byte the file you reviewed:

git -C mp-skills rev-parse "6fd9479:skills/productivity/grilling/SKILL.md"
git hash-object --no-filters proj\.claude\skills\grilling\SKILL.md
8ca78c6d8f901aab0c5a1f896034b70e666ff2a3
8ca78c6d8f901aab0c5a1f896034b70e666ff2a3

The skills CLI's skills-lock.json does the same job with a SHA-256 over the whole skill folder. Either works; what matters is that the identifier is written down next to the commit it came from.

Reviewing an update

An update review is cheaper than the first review because you only read what changed. Ask git for the difference between the commit in your register and the candidate, limited to the path you vendored:

git -C mp-skills fetch origin
git -C mp-skills log --format="%h %cs %s" "$pin..$new" -- skills/productivity/grilling
git -C mp-skills diff "$pin..$new" -- skills/productivity/grilling

In Lab 3 the repository moved by 50 files between the two commits, and the vendored skill by three added lines and one removed, in two commits. That ratio is typical and it is the argument for a path-limited diff. Read frontmatter changes first (a new allowed-tools or hooks line changes what the skill may do), then new files, then new commands in the prose. Take the update by copying the file at the new commit, check the blob ID again, and change the register line. If you decline, write that down too, with the reason.

Pin to a 40-character SHA, record it where the next engineer will look, and treat "update" as a code review of one diff.

What a dependency costs after day one

A skill you did not write keeps charging you after the install.

  • Review on every update. The diff is small, and it recurs for as long as you track upstream. The repository in the labs had 26 more commits between the two pins, under four weeks apart.
  • Context. Every installed skill's description is in every session. The 27-skill plugin from the last lesson adds about 1,200 tokens whether or not you use more than two of them.
  • Fit. Community skills encode their author's workflow. The Pocock engineering skills expect a one-time setup skill to record your issue tracker, triage labels and documentation layout, because the others depend on those choices. If your workflow differs, you carry the mismatch in every invocation.
  • Platform assumptions. A hook script written in bash with jq, matched on the Bash tool, is not a guard on a machine where commands go through PowerShell.
  • Names. A personal skill beats a project skill of the same name. Two collections that both ship a code-review or a tdd will collide, and one of them will lose without an error.

The 30-line alternative

Many good community skills are short. The grilling skill adopted in the labs is 2 KB of prose: interview in rounds, number the questions, give a recommended answer, look facts up instead of asking. Once you have read it, you know the technique, and a version in your own words, with your own terms and nothing you do not use, is an hour's work that you never have to re-review. The author's README says as much: "Hack around with them. Make them your own." Reading other people's skills to learn what works and then writing your own is a legitimate way to use a collection, as long as you respect the licence when you copy text.

Short prose skill, you would change the wording anywayWrite your own, crediting the idea if you borrowed the structure

    Expected: a decision line. "Reject, because it needs a hook I cannot read" is a complete result.

  5. If you adopt: do it at project scope in a scratch project first, as in Lab 2, with a register line. If you adopt a plugin, install it from a marketplace entry pinned to the SHA you reviewed, or with auto-update off, and note which. Remove it again when you are done unless you mean to keep it.

    Expected: a register line with source, path, commit and content identifier, and an init line whose skills or plugins array shows the item.

Self-check

Done-test. You are done when decision.md answers five questions without you opening the repository again: what kind of thing is it, which commit or version did you read, what can it run on your machine, what did you decide, and what would make you look at it again.

Did you run anything from the item before the decision line was written? If yes, redo the review in a fresh clone and treat the machine state as changed by the item.

Is the adopted copy pinned? A register line with a SHA, or a marketplace entry with sha, is a pin. "I installed the latest" is not.
