A prompt change that feels better is an anecdote. An eval is a fixed set of cases, a scoring rule and a repeatable run, so a change to a prompt, a model or a setup becomes a measurement with a number and an error bar. This module builds that harness with headless runs, shows how to pair and repeat the runs, how to read a small result honestly, and how to catch answers that are confident and wrong.

After this module you can

  • Build a golden set of cases with expected answers and a grader that scores a run with no human in the loop.
  • Choose the cheapest grader that works (exact match, code check, model judge) and audit a model judge against hand labels and a position swap.
  • Run a paired, repeated, randomised A/B of two prompts with the model, effort, tools and settings pinned, and measure the noise floor first.
  • Read a result as wins, losses and ties with an exact sign test and a bootstrap interval, and say how many cases you would need to see a given improvement.
  • Measure the rate of confident wrong answers separately from accuracy, and test an abstention rule.
  • Price an eval run on a subscription plan (window share) and on an API key (dollars), and decide when a batch run pays.

The failure an eval prevents

You change a prompt, try it on three inputs, and it looks better. Three weeks later a case you did not try breaks, and nobody can say whether the change caused it. The model is not deterministic, so one run of one input tells you almost nothing about either prompt. An eval replaces the three-input impression with a fixed list of cases that every candidate runs against, so the comparison is the same each time.

What measuring gets you

In the first lab you run a 12-case ticket classifier three times with the same prompt. The model was Haiku 5.5. Each repeat scored 11 of 12, and the same case (a copier that stopped scanning to email after a mail password change, expected "printer", answered "auth") failed all three times. No case flipped between runs. That is two findings a single impression would not give you: the baseline is 11 of 12, and the miss is systematic, not noise. A systematic miss is something a prompt change can fix. A case that flips between runs is noise, and no prompt change can be judged against it.

The whole 36-run baseline cost about $0.003 at list price and a median of about 1,020 ms per call. Evals of this size are cheap enough that skipping them is hard to defend.

Eval versus test

A unit test passes or fails the same way every run. An eval returns a rate with variance, so you compare rates between arms and ask whether the gap is bigger than the noise. The rest of this module is about that question.

Never compare two prompts on fewer cases than you can list in a file, and never on one run per case.
Cases you wrote while tuning the prompt are not a test of it. Keep some cases you did not look at while editing, and add every real failure you meet in use to the set.

The golden set

A golden set is a file of inputs with the expected answer, small enough to run on every change. Build it from real inputs, and include the hard ones on purpose: ambiguous cases whose correct answer is "unclear", cases with a plausible decoy, and cases that need the model to decline. In the labs the set has five labels and two ticket types designed to mislead: a copier problem triggered by a password change, and a vague ticket with no device named.

Use the first grader on the list that can score the task. If you can make the model answer in a constrained form (one word, a number, JSON), you turn a judge problem into an exact-match problem. The lab harness normalises an answer by stripping punctuation and lowercasing it, then compares it to the expected value.

The model judge and its limits

A judge is a second model call with a rubric: "reply PASS only if the summary names the affected system, states the impact, and makes no claim that is not in the ticket." It is fast and scales, but it is a measuring instrument that you must calibrate. Two known weaknesses:

  • Leniency. The judge passes an answer you would fail. Measure it: hand-label a handful of outputs, count how many the judge passes that you failed.
  • Position bias. In a pairwise comparison, the judge prefers the first or second slot regardless of content. Test it by judging each pair in both orders; a pair judged differently depending on order shows the verdict depends on slot, not quality.

In lab 3, Haiku 5.5 as judge agreed with six hand labels 6 of 6, including two summaries that invented a cause and one that was vague, and passed nothing you failed. In the position swap it picked the same summary in both orders for 2 of 3 pairs; on the badge-reader pair it picked slot 2 in both orders, so one of those two verdicts was wrong. Six labels is far too few to trust the judge in general, but it is enough to show that the audit catches something.

Auditing a judge

  1. Hand-label 20 to 50 outputs, including several you know are bad.
  2. Run the judge and report agreement, judge-passed-your-fail, and judge-failed-your-pass separately. The first error type is the dangerous one.
  3. For pairwise judging, run both orders and discard or flag pairs whose verdict follows the slot.
  4. Re-audit when you change the judge prompt or the judge model.
A judge you have not audited against hand labels is an opinion with a cost.
Do not let a model judge grade its own arm's output without a hand-labelled check; the judge and the candidate may share the same blind spots.

Noise floor first

Before comparing two prompts, run one prompt against itself. Lab 1 does this: three repeats, 36 runs, same score each time, no case flipping. That is a quiet task, and it tells you a gap of one case between arms is a real difference on this model. If your baseline flips cases between repeats, the noise floor is the number of flips, and an arm difference smaller than that is not evidence.

The harness

The harness is one script, eval.ps1, that builds the list of case, arm and repeat jobs, shuffles it with Get-Random, runs claude -p for each with the case text on stdin, grades the answer, and writes one CSV row per run with the score, output tokens, cost and duration. A second script, pairs.ps1, collapses the rows into one line per case: correct runs for A, correct runs for B.

Change one thing, run every case under both arms several times in shuffled order, and record the model id with every row.
An alias such as haiku in a saved eval means the baseline changes under you when the alias moves. Two results on different dates may not be comparable.

Wins, losses and ties

For each case, subtract A's score from B's. Positive is a win for B, negative a loss, zero a tie. Ties carry no information about which arm is better; the evidence is in the cases that moved. In lab 2, prompt B added two label rules to prompt A. A scored 11 of 12 on both repeats, B scored 12 of 12 on both. Per case, 11 cases were 2 and 2 and case 9 was 0 and 2. That is 1 win, 0 losses, 11 ties.

Exact sign test

The sign test asks: if the arms were equal, how often would the wins and losses split this unevenly? With n untied cases and the smaller side k, the two-sided p-value is twice the probability of k or fewer successes in a fair coin flipped n times, capped at 1. With 1 win and 0 losses, n is 1, and p is 1.000. A single win cannot be told from luck.

Bootstrap interval

The paired bootstrap resamples the per-case differences with replacement many times and reports the middle 95 percent of the resampled means. Lab 2 gave a mean B minus A of 0.167 correct runs per case (of 2) with an interval of [0.000, 0.500]. The interval touches zero, which agrees with the sign test: the data are compatible with no improvement.

The instrument

Paste your paired scores into the readout below, one line per case, the A score then the B score separated by a comma, for example 2,2 or 0,2. It returns the wins, losses and ties, the exact sign test, and the bootstrap interval. Try the lab 2 values (eleven lines of 2,2 and one 0,2), then change them to see how many clean wins it takes.

Practical versus statistical

A result can be significant and still not worth shipping, or not significant and still worth a larger run. Put cost and latency next to the score. In lab 2 arm B cost about $0.00285 against $0.00098 for A at list price (about 2.9 times), with mean latency 1,113 ms against 973 ms. A follow-up check of 12 extra runs showed why: B's output tokens ranged from 3 to 91 per run, because Haiku 5.5 spends output tokens on thinking, while A's were about 4. A longer prompt did not cost three times as much because of its length; it changed how much the model thought. The JSON result carries this in usage.output_tokens_details.thinking_tokens.

Report wins, losses and ties with the p-value and interval, and put cost and latency beside them.
A p-value of 1.000 on 12 cases is not evidence that the prompts are equal. It is evidence that 12 cases cannot tell.

Accuracy hides the dangerous error

A wrong answer that looks like a right one is more costly than a refusal. Accuracy lumps the two together. Split the failures by type: wrong answer given, answer declined, format broken. The cases to build for it are ones where the right answer is "the input does not say".

The abstention test

Lab 4 uses eight change notes asking for a TCP port. Four state the port. Four do not (a service restarted, an API moved, a mail relay that came back after a certificate renewal, a PostgreSQL server upgrade) and each has a decoy: a well-known default port the model could supply from general knowledge. The correct answer for those four is NONE.

ArmExact matchFabricated a portDeclined in prose
A: "Reply with the port number only."4 of 80 of 44 of 4
B: A plus "If the note does not state the port, reply NONE; a default port is a guess, not a statement."8 of 80 of 40 of 4

Neither arm fabricated a port on this model. The difference is format. Arm A declined in sentences ("the PostgreSQL default is 5432 but db-01 may be configured differently"), which an exact-match grader scores as wrong and which a downstream script cannot parse. Arm B returned the single token NONE. The prose answer for the PostgreSQL note named the default port while declining, which is the shape of a fabrication waiting to happen if the next model is less careful. Count it separately: grade "stated a port", "declined", and "wrong port".

Techniques that move the rate

TechniqueWhat you addHow you test it
Explicit abstentionA defined token for "not stated", and a rule that a default is a guessCases with no answer; count fabrications and prose declines
GroundingAnswer only from the supplied text; quote the evidenceGrade the quote with a code check (is it a substring of the input)
VerifierA second call checks the first answer against the sourceAudit the verifier against hand labels as in lesson 2
Regression setEvery confident wrong answer from real use becomes a caseRerun the set on each change

The code check for evidence is the cheapest: ask for the sentence the answer came from, then test in code that the sentence appears in the input. An answer with no matching evidence is scored as a failure, whatever the answer was.

Grade fabrications as their own column, and give the model a defined way to say "not stated".
Zero fabrications on eight cases says little. The abstention rate needs the same sample-size thinking as accuracy; a rare failure needs many no-answer cases to show up.

Count the calls

An eval is cases times arms times repeats, plus judge calls. Lab 2 was 12 cases, 2 arms and 2 repeats: 48 runs. Add a judge pass and it doubles. Change one factor and the cost multiplies, so size the set from the power table before adding repeats.

Subscription plan

On a subscription the fee is flat and the eval draws down your 5-hour window and the weekly limit, which span all models. total_cost_usd in the JSON result is a client-side estimate from a bundled price table, not billing data, and on a subscription it is notional. Use it to compare arms by relative cost; it is not what you pay. The lever on a plan is share of the window: Haiku uses less than Sonnet or Opus for the same call, and a 12-case, 48-run eval on Haiku is a small bite. Run large evals when you are not about to need the window for real work, and do not leave an eval looping against a limit.

API key

With an API key the cost is dollars at list price: input, output, cache write and cache read at the rates for the model. Lab 1's 36 runs cost about $0.0029 at the Haiku 5.5 rate. Two levers exist that a plan does not give you:

  • --max-budget-usd caps spend for a headless run.
  • The Batch API is 50 percent off input and output, up to 100,000 requests or 256 MB per batch, with results available within 24 hours. It suits a large nightly regression set that nobody is waiting for. Whether Claude Code itself submits batches is not documented on the pages read for this module; the batch route means calling the API directly.

Spend where the variance is

Run the cheap model for the wide first pass, and spend on a stronger model or more repeats only on the cases that flip. A grader that is exact match costs nothing; reach for a judge only after a code check cannot do the job.

Size the set from the power table, price it as cases times arms times repeats, and use the cheapest grader that scores the task.
Do not read a small total_cost_usd on a subscription as free. It still draws down the window, and a large looping eval can hit the limit and stop your real work.

    Set-Content -Encoding utf8 eval.ps1 @'
param([string]$Cases = 'tickets.csv', [string[]]$Arms = @('prompt-a.txt'), [int]$Repeat = 1, [string]$Out = 'results.csv', [string]$Model = 'haiku')
$list = Import-Csv $Cases
$jobs = @(foreach ($c in $list) { foreach ($a in $Arms) { foreach ($r in 1..$Repeat) { [pscustomobject]@{ case = $c; arm = $a; rep = $r } } } })
$jobs = $jobs | Get-Random -Count $jobs.Count
$rows = foreach ($j in $jobs) {
  $prompt = (Get-Content $j.arm -Raw).Trim()
  $raw = $j.case.text | claude -p $prompt --model $Model --setting-sources project --strict-mcp-config --tools "" --max-turns 1 --no-session-persistence --output-format json
  $res = ($raw -join "`n") | ConvertFrom-Json
  $got = ([string]$res.result -replace '[^\w ]', '').Trim().ToLower()
  [pscustomobject]@{ id = $j.case.id; arm = $j.arm; rep = $j.rep; expected = $j.case.expected; got = $got
    score = [int]($got -eq $j.case.expected); out = $res.usage.output_tokens; cost = $res.total_cost_usd; ms = $res.duration_ms
    model = ($res.modelUsage.PSObject.Properties.Name -join '+') }
}
$rows | Export-Csv $Out -NoTypeInformation
$rows | Group-Object arm, rep | Sort-Object Name | ForEach-Object { '{0}  score {1}/{2}' -f $_.Name, ($_.Group | Measure-Object score -Sum).Sum, $_.Count }
'{0} runs, {1:N4} USD, median {2} ms, model {3}' -f $rows.Count, ($rows | Measure-Object cost -Sum).Sum, (@($rows.ms | Sort-Object { [int]$_ }))[[int]($rows.Count / 2)], (@($rows.model | Sort-Object -Unique) -join ',')
'@

What is your noise floor on this task? Zero flipped cases in 36 runs, so a one-case difference between arms is a real difference here. Is the case 9 miss noise? No: it failed 3 of 3, so it is systematic and a prompt change can address it. Why random order? So drift over the run does not land on one arm. Why does the harness record the model id?   2. Write the pairing script and the readout script. The readout computes the exact sign test and a paired bootstrap with a fixed seed. Note [math]::Min(1.0, ...): with the integer 1, PowerShell picks the Int32 overload and truncates a p-value of 0.5 to 0.

    Set-Content -Encoding utf8 pairs.ps1 @'
param([string]$Path = 'ab.csv', [string]$A = 'prompt-a.txt', [string]$B = 'prompt-b.txt', [string]$Out = 'pairs.txt')
$rows = Import-Csv $Path
$lines = $rows | Group-Object id | Sort-Object { [int]$_.Name } | ForEach-Object {
  $sa = ($_.Group | Where-Object arm -eq $A | Measure-Object score -Sum).Sum
  $sb = ($_.Group | Where-Object arm -eq $B | Measure-Object score -Sum).Sum
  '{0},{1}' -f $sa, $sb }
$lines | Set-Content -Encoding ascii $Out
$lines
'@
Set-Content -Encoding utf8 abstat.ps1 @'
param([string]$Path = 'pairs.txt', [int]$Resamples = 5000)
$d = @(Get-Content $Path | Where-Object { $_ -match ',' } | ForEach-Object { $x = $_ -split ','; [double]$x[1] - [double]$x[0] })
$w = @($d | Where-Object { $_ -gt 0 }).Count; $l = @($d | Where-Object { $_ -lt 0 }).Count; $t = $d.Count - $w - $l
$n = $w + $l; $k = [math]::Min($w, $l); $tail = 0.0; $c = 1.0
for ($i = 0; $i -le $k; $i++) { $tail += $c; $c = $c * ($n - $i) / ($i + 1) }
$p = if ($n -eq 0) { 1.0 } else { [math]::Min(1.0, 2 * $tail / [math]::Pow(2, $n)) }
$mean = ($d | Measure-Object -Average).Average
$rng = [Random]::new(1)
$means = @(for ($j = 0; $j -lt $Resamples; $j++) { $s = 0.0; for ($i = 0; $i -lt $d.Count; $i++) { $s += $d[$rng.Next($d.Count)] }; $s / $d.Count }) | Sort-Object
'cases {0}: wins {1}, losses {2}, ties {3}; sign test p = {4:N3}' -f $d.Count, $w, $l, $t, $p
'mean B-A = {0:N3}; 95% paired bootstrap interval [{1:N3}, {2:N3}]' -f $mean, $means[[int](0.025 * $Resamples)], $means[[int](0.975 * $Resamples) - 1]
'@

    Expected: No output.
