Everything a coding agent reads becomes part of a request to a model provider, and most of it is also written to a plain-text file on your disk. If you work where protected health information (PHI), personal data or credentials exist, the question is what is permitted to leave, under which agreement, and what stops the rest. This module is the data-handling half of security: it reports what Anthropic's own pages said on 11 November 2026, names the page for each statement, and shows the controls that keep sensitive data out of the request and out of the files that persist.

This module is not legal advice and does not interpret HIPAA or any contract. The plan type and the agreement your organisation signed decide whether PHI may be sent at all. Your compliance office decides what is permitted. Where the pages do not answer a question, the module says so.

After this module you can

  • List what one agent turn sends to the model provider and what it leaves on the local disk, and find a given string in a session's own transcript.
  • Read the retention and training position for a consumer plan, a Team or Enterprise seat, an API key, zero data retention and a third-party cloud platform off the pages that state it.
  • Say which Claude Code configurations Anthropic's pages list as covered by a Business Associate Agreement, which features they exclude, and who decides.
  • Reduce what a task needs before the prompt: schemas instead of rows, synthetic data, and a de-identified copy with stable pseudonyms.
  • Write a UserPromptSubmit hook that blocks a prompt carrying an identifier pattern, a PreToolUse hook that refuses files holding such patterns, and a PostToolUse hook that rewrites a tool result.
  • State what each control cannot catch, and prove a control works with a test that uses no real sensitive data.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The labs were run on 2.1.322.
  • Windows PowerShell 5.1 or PowerShell 7. Hook scripts and the de-identification script are PowerShell with no packages.
  • About $0.05 of Haiku usage at API list price for all five labs, or the same share of a subscription's 5-hour window.
  • Synthetic data only. Every name and identifier in the labs is invented. Do not substitute real records at any step.

If you skipped the prerequisites

From Hooks. A hook is a program Claude Code runs at a fixed point in its loop, registered under hooks in a settings file. It receives one JSON object on stdin. This module uses three events: UserPromptSubmit (a prompt was submitted and the model has not seen it yet; the input carries prompt), PreToolUse (the model wrote a tool call that has not run; the input carries tool_name and tool_input) and PostToolUse (the tool ran; the input adds tool_response). Exit code 0 means success and stdout is parsed as JSON when it is one JSON object. Exit code 2 blocks on a blockable event and stderr is the reason. Any other exit code is a non-blocking error: the action goes ahead. A PreToolUse hook denies with hookSpecificOutput.permissionDecision: "deny", and a UserPromptSubmit hook blocks with decision: "block" and a reason.

From Security. The threat model is three verbs: an agent can read what your account can read, run what your account can run, and send what it has read over the network. Permission rules live under permissions in a settings file as allow, ask and deny; deny is evaluated first and holds in every permission mode. A Read(./path) deny rule covers the built-in file tools and the file commands Claude Code recognises in a shell command (cat, Get-Content and similar). It does not cover a script or program that opens the file itself.

The request is the whole context

Claude Code runs locally and the model does not. The Claude Code "Data usage" page puts it in one sentence: "To interact with the LLM, Claude Code sends data over the network. This data includes all user prompts and model outputs, encrypted in transit via TLS 1.2+." The phrase "user prompts" undersells it. The request that goes to the provider on every turn is the entire working context, and the "Explore the .claude directory" page lists what that context holds when it describes the transcript: "Anything that passes through a tool is written to a transcript on disk: file contents, command output, pasted text", plus the system prompt, tool definitions, request parameters and "the instruction files it loaded, such as CLAUDE.md".

Zero data retention: what it covers and what it does not

There are two separate offerings with the same name. One is an arrangement for the Claude API, which also covers Claude Code when it runs on an API key from that organisation. The other is for Claude Code on Claude for Enterprise. Both are enabled by Anthropic per organisation after a request through sales or the account team; neither is a setting you can flip. The Enterprise page is specific about the edges:

  • It covers "model inference calls made through Claude Code". It does not cover chat on claude.ai, Cowork, artifacts, analytics metadata such as account emails and usage statistics, seat management, or "third-party tools, MCP servers, or other external integrations".
  • It applies "to requests that authenticate into a ZDR-enabled organization. If a developer signs in to Claude Code with a personal account or with an API key from a different organization, those sessions are not covered." The page points to the forceLoginMethod and forceLoginOrgUUID managed settings to pin sign-in.
  • Features that need server-side storage are disabled at the back end: cloud sessions, Remote Control, artifacts, and /feedback, /bug and /share.
  • On the API arrangement, "if metrics logging is enabled in Claude Code, productivity data such as usage statistics is exempted from ZDR and may be retained".

Zero data retention is about Anthropic's servers. It changes nothing on your disk: the transcript, the prompt history and the memory files are still written, in plain text, for cleanupPeriodDays.

Subscription and API

For the other modules the difference between a subscription and an API key is billing. Here it is which contract applies. A personal Pro, Max or Ultra login is under consumer terms, with a training setting the account holder controls and a 30-day or 5-year retention period that follows it. An API key is under commercial terms with no training by default. A Team or Enterprise seat is a subscription in billing terms and commercial in data terms. The API

For the Claude API, the platform page describes "HIPAA readiness": a signed BAA plus a HIPAA-enabled organisation. The plain consequence

No setting an engineer can change on a workstation makes PHI permissible to send. Whether it may be sent is decided by the plan type, the signed agreement, and whether Anthropic has applied the configuration to that organisation. What the engineer controls is the other direction: making sure a session is on the covered route, that uncovered features are not fed PHI, and that the local copies are handled. The support article puts the limit of the vendor's side in one line: "HIPAA-ready" means the product is configured to support your HIPAA obligations under the BAA, and "Compliance remains your organization's responsibility."

A feature can be available and still not covered. The BAA article marks local MCP servers and the IDE extensions as both. A session with the HIPAA configured tag in the footer will still hand a query result to an MCP server if you ask it to.

Minimise before you prompt

The cheapest control is not needing the data. Most engineering tasks that touch a sensitive system are about its structure: a slow query, a failing import, a schema migration, a parser for a report format. The model needs the shape, not the people.

Why "the model will ignore it" is not a control

An instruction in CLAUDE.md such as "never repeat patient identifiers" shapes the output. It does nothing to the input. By the time the model can follow or ignore the instruction, the identifiers are in the request, the request has reached the provider, and the tool result has been written to the transcript. The same is true of asking the model to redact: the unredacted text was sent in order to be redacted. Controls for sensitive data have to act before the request is built, which means before the prompt is submitted or before the tool runs.

De-identification, in the words of the rule

The HIPAA Privacy Rule gives two ways to treat health information as de-identified, in 45 CFR 164.514(b). The first is a determination by a qualified expert that the risk of identification is very small. The second, usually called Safe Harbor, removes a list of identifiers "of the individual or of relatives, employers, or household members of the individual". The list below is the rule's, taken from the eCFR text of the regulation (the HHS guidance page that explains it refused an automated fetch on 11 November 2026, so this is the regulation, not the guidance). It is shortened for reading; use the rule's own wording for any real decision.

Identifiers the Safe Harbor paragraph lists (A to R)
(A) Names. (B) Geographic subdivisions smaller than a State, including street address, city, county, precinct and zip code, with a conditional exception for the first three zip digits that depends on census population. (C) All elements of dates except year for dates directly related to an individual (birth, admission, discharge, death), and all ages over 89, which may be aggregated as 90 or older.
(D) Telephone numbers. (E) Fax numbers. (F) Email addresses. (G) Social security numbers. (H) Medical record numbers. (I) Health plan beneficiary numbers. (J) Account numbers. (K) Certificate and license numbers.
(L) Vehicle identifiers and serial numbers, including license plates. (M) Device identifiers and serial numbers. (N) URLs. (O) IP addresses. (P) Biometric identifiers, including finger and voice prints. (Q) Full face photographic images and comparable images. (R) "Any other unique identifying number, characteristic, or code", except a re-identification code as paragraph (c) permits.

Two conditions sit beside the list. The method also requires that the covered entity "does not have actual knowledge that the information could be used alone or in combination with other information to identify an individual". And paragraph (c) says a code assigned to allow later re-identification must not be "derived from or related to information about the individual", and that the mechanism for re-identification is not disclosed. That second point matters to engineers: a hash of a record number is derived from the record number. Lab 4 therefore uses random pseudonyms held in a mapping file that stays outside the agent's folder. Whether any script's output meets the rule is a determination for your privacy office, not for the script's author.

The limits of pattern matching

Every automated control in this module is a pattern match, and pattern matches fail in both directions.

FailureExampleConsequence
False negative: format driftAn SSN typed as nine digits with no hyphens; a record number with a new prefixThe guard passes it
False negative: no format at allNames, addresses, a rare diagnosis in a small town, "the mayor's daughter"No regular expression exists for it
False negative: free textA notes column that mentions a relative by nicknameColumn-based de-identification leaves it in place
False negative: encodingThe same value inside base64, a PDF, an image or a compressed fileA text scan never sees it
False positiveA part number or timestamp shaped like an identifier; a surname that is also a common wordLegitimate work is blocked, and people start bypassing the guard

Structured columns are tractable: you know which column holds the record number and you can drop or replace it. Free text is where de-identification fails, and it is also where clinical systems keep the most identifying material. A pipeline that handles the columns and passes the notes column through has moved the problem, not solved it. The safe defaults are to drop free-text columns unless the task needs them, and to treat any column you have not classified as identifying.

Use pattern guards to catch mistakes by people who are trying to comply. Do not count on them to make an uncovered route safe for real data.

Synthetic data

For anything that is about code paths, generate data. Keep the generator in the repository so the test file can be rebuilt, give synthetic identifiers a shape that cannot be mistaken for real ones (the labs use MRN-000123 and SSN-shaped strings that start with 900), and make the synthetic file exercise the edge cases that caused the bug: the over-long field, the embedded delimiter, the age over 89. A synthetic file that is safe to paste anywhere is also safe in a transcript, a bug report and a screenshot.

Context that copies itself elsewhere

  • Subagents. A subagent is another model conversation. What the parent passes in its task prompt, and whatever the subagent reads, goes to the provider in the subagent's own requests and is written to projects/<project>/<session>/subagents/. A deny rule or hook registered in settings applies there too; a control that exists only as a sentence in the parent's prompt does not travel.
  • Cloud sessions. The repository is cloned into an Anthropic-managed VM and the transcript is stored by Anthropic. If the repository holds a data extract, the extract is now there. Both zero data retention and the HIPAA configuration disable cloud sessions for this reason.
  • Compaction and resume. A summary is still content. Resuming a session replays its history into a new request, so a value from last week is sent again today.
  • Bug reports. /feedback can include other sessions from the same project from the last 7 days. One report can carry a week of work.

Shared configuration

A project's .claude/ folder and its CLAUDE.md are committed and read by everyone who clones the repository, and by every agent session in it. Review them like code, with one extra question: does any line contain a real record, a real person's name, an internal hostname list or a credential. The mistake is rarely malicious. It is an engineer pasting "an example of the data we deal with" into the instructions so the model understands the format. Give the model a synthetic example instead, and say that it is synthetic.

Decide the retention period for local transcripts on purpose and set it in managed settings. The default of 30 days was chosen for session resumption, not for your records policy.

Blocking a prompt

A UserPromptSubmit command hook receives the common fields plus prompt. To block, print one JSON object with decision set to "block" and a reason; the hooks reference says the reason is "Shown to the user" and "Not added to context". Exiting 2 with the message on stderr does the same. The event has no matcher and a 30-second default timeout, and a hook that times out is discarded and the prompt goes through unless the handler sets onFailure: "block". For a guard, set it.

The hooks reference is direct about the limit: "A blocked prompt never reaches Claude, but its text isn't removed everywhere." By default the block message ends with Original prompt: and the submitted text, and that message is written to the transcript. Returning "suppressOriginalPrompt": true inside hookSpecificOutput removes the text from the message, and the reference adds that it "can still appear in local files such as the session transcript and your prompt history, so a blocking hook isn't a way to keep a secret off disk". Lab 2 counts what remains in both cases.

Blocking a read by content

A deny rule matches a path. A PreToolUse hook is a program, so it can open the file the model asked for and decide on what is inside. That closes the commonest way a path rule fails: the export saved as copy-of-export-final.csv in a folder nobody listed. The hook returns permissionDecision: "deny" with a reason the model reads, and a good reason names the de-identified alternative so the model can carry on. Write the guard to fail closed: if it cannot parse its input or read the file, it denies. Lab 3 builds one and records what still got through.

Rewriting a result

The hooks reference documents an output-side control: a PostToolUse hook may return hookSpecificOutput.updatedToolOutput, which "replaces the tool's output with the provided value before it is sent to Claude". The value has to match the tool's output shape; for Bash that is an object with stdout, stderr, interrupted and isImage, and "a value that doesn't match the tool's output schema is ignored and the original output is used". The warning attached to it is the one to remember: it "only changes what Claude sees. The tool has already run." Use it as a net under the other layers, for output you could not predict, such as a query result. Do not treat it as the main control.

Making it stick

Project settings can be edited by anyone who can edit the repository, and a user can pass --settings with disableAllHooks. Controls that must hold belong in managed settings: a managed-settings.json in the system directory (C:\Program Files\ClaudeCode\ on Windows, /etc/claude-code/ on Linux and WSL, /Library/Application Support/ClaudeCode/ on macOS) or one of the other delivery mechanisms the managed settings page lists. Hooks and deny rules placed there cannot be removed by a lower level. Two keys tighten it further: allowManagedHooksOnly runs only the hooks the organisation deploys, and allowManagedPermissionRulesOnly makes managed settings the only source of permission rules. Put cleanupPeriodDays there too. None of this was run on the lab machine, because it means writing to a system directory; it is reported from the docs.

Secrets are the same problem in miniature

An API key behaves exactly like a patient identifier in this system. If it is pasted into a prompt, printed by a command, or sits in a file the agent reads, it is sent to the provider and written to the transcript in plain text. The directory page says so: "If a tool reads a .env file or a command prints a credential, that value is written to projects/<project>/<session>.jsonl." A key has one property a diagnosis does not: it can be rotated. If one reaches a prompt or a transcript, rotate it first and clean up second.

The controls are the ones above with different patterns: deny rules on credential files, a prompt guard for key-shaped strings, and no credentials in CLAUDE.md or shared settings. The Security module covers the rest, including the sandbox credential settings, environment scrubbing for subprocesses, and keeping the credential off the machine altogether. # deid.ps1: write a de-identified copy of the synthetic patients file. Pseudonyms are random and kept in a mapping file.
param([Parameter(Mandatory)][string]$In, [Parameter(Mandatory)][string]$Out, [Parameter(Mandatory)][string]$MapFile)
$ErrorActionPreference = 'Stop'
$pseudo = @{}
if (Test-Path $MapFile) { Import-Csv $MapFile | ForEach-Object { $pseudo[$_.mrn] = $_.patient_id } }
$rng = [Security.Cryptography.RandomNumberGenerator]::Create()
function Get-Pseudonym($mrn) {
  if (-not $pseudo.ContainsKey($mrn)) {
    $b = New-Object byte[] 4; $rng.GetBytes($b)
    $pseudo[$mrn] = 'PT-' + (($b | ForEach-Object { $_.ToString('x2') }) -join '')
  }
  $pseudo[$mrn]
}
$rows = Import-Csv $In
$thisYear = (Get-Date).Year
$result = foreach ($r in $rows) {
  $age = $thisYear - [int]$r.dob.Substring(0, 4)
  $note = $r.note
  foreach ($x in $rows) {
    $alias = Get-Pseudonym $x.mrn
    $note = $note.Replace($x.name, $alias).Replace($x.phone, '[phone]').Replace($x.mrn, $alias)
    foreach ($part in $x.name.Split(' ')) { $note = $note -replace ('\b' + [regex]::Escape($part) + '\b'), $alias }
  }
  $band = if ($age -ge 90) { '90+' } else { [string]([math]::Floor($age / 10) * 10) + 's' }
  [pscustomobject]@{ patient_id = (Get-Pseudonym $r.mrn); age_band = $band; diagnosis_code = $r.diagnosis_code
                     visit_year = $r.visit_date.Substring(0, 4); note = $note }
}
$result | Export-Csv -NoTypeInformation -Encoding UTF8 $Out
$pseudo.GetEnumerator() | ForEach-Object { [pscustomobject]@{ mrn = $_.Key; patient_id = $_.Value } } | Export-Csv -NoTypeInformation -Encoding UTF8 $MapFile
"rows=$(@($result).Count) patients=$(@($result.patient_id | Sort-Object -Unique).Count)"
'@ | Set-Content -Encoding utf8 {{LAB}}/m22/raw/deid.ps1
Set-Location {{LAB}}/m22/lab4

Self-check

The check reported zero original identifiers. Is the copy free of identifying text? No. The note for one visit still mentions a relative by nickname. The check was built from the same list of known values as the script, so it shares the script's blind spot. A check proves the absence of what you thought to look for.

Why is the mapping file kept outside the agent's working folder? It is the re-identification key. Anyone holding it and the de-identified file holds the original data. The rule text quoted in lesson 4 also says the re-identification mechanism is not disclosed.

Why random pseudonyms and not a hash of the record number? A hash is derived from the identifier, and the rule's paragraph on re-identification codes says the code is not derived from information about the individual. Whether a given scheme is acceptable is your privacy office's call.
