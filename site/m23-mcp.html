The Model Context Protocol is a wire protocol, and it can be read like one: a message format, a version negotiation, a small set of methods, two transports and an authorization scheme. This module walks the specification in that order, shows the bytes Claude Code actually sends, and has you build a working server in plain Node with no SDK so that nothing about it stays a black box. The specification changed shape in its 2026-07-28 revision, so you learn both shapes and see a current Claude Code speak each of them.

After this module you can

  • Name the three MCP roles and say which side owns tools, resources, prompts, elicitation, sampling and roots, and which of those the current revision deprecates.
  • Read and write the JSON-RPC messages by hand: a request, a result, an error object, a notification, the initialize handshake of the 2025-11-25 revision and the per-request _meta of the 2026-07-28 revision.
  • Tell a protocol error from a tool result with isError, and return the right one from your own server.
  • Explain what goes on stdout and what goes on stderr for a stdio server, and what a Streamable HTTP request must carry in its headers.
  • Describe the OAuth-based authorization flow the specification defines for HTTP, and recognise its discovery requests in a server log.
  • Wire a server into Claude Code by configuration file, grant one MCP tool by name, and read the server status, the tool call and the token usage from a headless run.

If you skipped the prerequisites

The Context module shows that everything the model can use costs room in its context window, tools included: a tool's name, description and input schema are text in the prompt. Claude Code softens this for MCP servers by deferring their tools. Only the tool names and the server's instructions load when the session starts, and the full schema of a tool loads when the model searches for it. In that module's measurement of an empty folder, /context listed about 13.8k tokens of deferred system tools that were not counted in the total, and the list of tools changes whenever you add or remove an MCP server. This module explains where those names, descriptions and schemas come from: they are the body of one protocol message, tools/list, and you will write that message yourself.

Three roles

The specification defines three roles. The host is the application the user runs: Claude Code, a desktop chat app, an IDE. The host creates one client for each server it connects to. A server is a program that offers context and actions. The rule that matters for troubleshooting is the cardinality: each client talks to exactly one server, and the host holds the clients. Five configured servers means five clients, five connections and five independent negotiations inside one host.

The host is where policy lives. Per the architecture page, the host controls connection permissions, enforces consent, and aggregates context across clients. A server sees only what its own client sends it. It does not see the conversation, and it does not see the other servers.

The quoted terms in the fourth column are the specification's own. They describe intent, and the specification adds that a host is free to expose any primitive through any interface. Around the primitives sit utilities: pagination, caching hints, progress, cancellation, argument completion and logging. Logging is deprecated in the current revision in favour of stderr for stdio servers and OpenTelemetry elsewhere.

Revisions are dates, and there are two eras

An MCP protocol version is a date string. This module was written from the specification pages of revision 2026-07-28, the newest one published at modelcontextprotocol.io on 11 November 2026, and from revision 2025-11-25, which it replaced. You need both, because the 2026-07-28 revision removed the connection handshake, and the specification itself now speaks of two eras.

RevisionEraWhat changed on the wire
2024-11-05Legacystdio and the HTTP+SSE transport
2025-03-26LegacyStreamable HTTP replaces HTTP+SSE, which is deprecated from here on
2025-06-18LegacyThe MCP-Protocol-Version HTTP header is defined
2025-11-25LegacyLast revision with the initialize handshake and HTTP sessions
2026-07-28ModernStateless: no handshake, no session. Every request carries its version and capabilities in _meta. server/discover is added. Server-to-client requests are replaced by a retry pattern.

"Legacy" and "modern" are the specification's terms: legacy revisions establish a session with initialize, modern ones convey version, identity and capabilities as per-request metadata. An implementation that supports both is "dual-era". Most servers in the field today are legacy. Claude Code 2.1.322 is dual-era: in the labs it asked each server whether it spoke 2026-07-28 and fell back to the handshake when the server did not. Lesson 2 shows both exchanges byte for byte.

When someone says "MCP does X", ask which revision. Sessions, the handshake, ping and server-initiated requests are true of 2025-11-25 and false of 2026-07-28.

What the current revision deprecates

The 2026-07-28 revision introduced a deprecation registry with a minimum twelve-month window. Listed there: Roots, Sampling and Logging (earliest removal in the first revision on or after 2027-07-28), OAuth Dynamic Client Registration, and the HTTP+SSE transport. Deprecated features still work. New servers should not adopt them.

SDKs exist, and the labs do not use them

The MCP project publishes official SDKs: TypeScript, Python, C#, Go, Rust and Ruby at its tier 1, Java at tier 2, Swift, PHP and Kotlin at tier 3. Its documentation tells you to build servers and clients with them, and notes that each SDK adopts new protocol revisions on its own schedule. For a real server, use one: it gives you schema validation, both transports and the authorization flow. The labs here build without an SDK on purpose, so that every byte on the wire is one you wrote and nothing is installed.

Three message shapes

Every MCP message is a JSON-RPC 2.0 object, UTF-8 encoded. There are three shapes, and the presence of id and method tells you which one you are looking at.

ShapeHasRules from the specification
Requestid, method, optional paramsThe id is a string or an integer, never null, and must not match another request the sender still has outstanding
Responseid and either result or errorCarries the id of the request it answers. An error has an integer code, a message and optional data
Notificationmethod, optional params, no idOne-way. The receiver must not reply

Ids are how replies are matched to requests, exactly like a DNS transaction id. Replies may arrive out of order. In Lab 3 Claude Code sent tools/list, prompts/list and resources/list back to back with ids 1, 2 and 3 and matched the three replies by id.

The legacy lifecycle: initialize, initialized, operate, shut down

In revisions up to 2025-11-25 a connection has three phases. Initialization must be the first exchange. The client sends initialize with the protocol version it wants, its capabilities and its name and version. The server answers with the version it will speak, its own capabilities, its name and version and optional instructions. The client then sends the notifications/initialized notification, and normal operation starts. This is the handshake Claude Code 2.1.322 sent to a handshake-only server in Lab 3, unedited apart from line breaks:

<< {"method":"initialize","params":{"protocolVersion":"2025-11-25",
     "capabilities":{"roots":{"listChanged":true},"elicitation":{"form":{},"url":{}}},
     "clientInfo":{"name":"claude-code","title":"Claude Code","version":"2.1.322",
       "description":"Anthropic's agentic coding tool","websiteUrl":"https://claude.com/claude-code"}},
     "jsonrpc":"2.0","id":0}
>> {"jsonrpc":"2.0","id":0,"result":{"protocolVersion":"2025-11-25",
     "capabilities":{"tools":{}},"serverInfo":{"name":"lab-inventory","version":"0.1.0"}}}
<< {"jsonrpc":"2.0","method":"notifications/initialized"}
<< {"method":"tools/list","jsonrpc":"2.0","id":1}

Version negotiation is one round. The client sends a version it supports, which should be its latest. If the server supports that version it must answer with the same string. Otherwise it answers with another version it supports, which should be its latest, and a client that cannot speak that one should disconnect. There is no further bargaining.

Capability negotiation is a declaration by each side, and each side may only use what the other declared. The client above declares roots and elicitation with both modes. The server declares only tools, so the client never asked it for prompts or resources. A sub-flag refines a capability: listChanged means "I will notify you when this list changes", and subscribe on resources means individual resources can be watched.

Shutdown has no message. The transport ends the connection: on stdio the client closes the server's stdin and waits for it to exit, and on HTTP it closes the connection. Claude Code's documentation states what it does to a stdio server: on Windows it closes stdin and ends the process tree if the server is still running 300 milliseconds later. On macOS and Linux it sends SIGINT, then SIGTERM 100 milliseconds later, then SIGKILL after a further 400 milliseconds. A server that needs to flush state has that long.

The modern shape: every request is self-contained

Revision 2026-07-28 removes initialize and notifications/initialized. The protocol is declared stateless: a server must not rely on an earlier request on the same connection for the version, the capabilities or the identity of the client. Each request carries them in params._meta under reserved keys:

_meta keyRequiredMeaning
io.modelcontextprotocol/protocolVersionYesThe version this request is written in
io.modelcontextprotocol/clientCapabilitiesYesThe client capabilities relevant to this request
io.modelcontextprotocol/clientInfoNo, but clients should send itClient name and version, for display and logs only
io.modelcontextprotocol/logLevelNoOpts this request into log notifications at that level
progressTokenNoOpts this request into progress notifications

A request without a required key is malformed and gets -32602. A version the server does not implement gets -32022 with the list of versions it does implement, and the client retries with one of those. Every result carries a required resultType, "complete" for an ordinary result, and the server should name itself in the result's _meta under io.modelcontextprotocol/serverInfo. A new method, server/discover, returns the supported versions, capabilities and instructions in one reply. Servers must implement it. Clients may call it or skip it. This is Claude Code 2.1.322 talking to the dual-era server you build in Lab 2. There is no handshake anywhere in the capture:

Three things to read off it. The metadata repeats on every request, 442 characters on the call above, which is the price of statelessness. A client may add its own _meta keys under its own prefix, as Claude Code does with claudecode/toolUseId. And clientInfo and serverInfo are self-reported: the specification says not to change behaviour or make a security decision on either.

How a client finds out which era a server speaks

On stdio the specification tells a dual-era client to send server/discover first. A discover result means modern. A recognised modern error such as -32022 also means modern, with a different version. Any other error, or no answer within a reasonable time, means legacy, and the client falls back to initialize. The fallback must not depend on one specific error code, because legacy servers answer an unknown first request with whatever they like, or not at all. On HTTP the client sends a modern request and inspects the body of a 400 before falling back.

Claude Code's documentation describes two client runtimes. The newer one, built on version 2 of the MCP TypeScript SDK, adds revision 2026-07-28 and is the default in current versions. It asks stdio, HTTP and claude.ai connector servers whether they support the newer revision and uses it with those that do. Two environment variables control this: MCP_SDK_GENERATION (v1 or v2) pins the runtime, and MCP_PROTOCOL_NEGOTIATION (legacy or auto) turns the probe off or on. With the second one unset, Claude Code can skip the probe for a stdio server for 7 days, for example after the server exited when it was asked.

A hand-written legacy server that answers every unknown method with a success, or that hangs on one, breaks the probe: the client either believes it is modern or waits out a timeout on every start. Answer what you do not implement with error -32601, promptly. Lab 1's 38-line server does, and Claude Code fell back to the handshake in one round trip.
Write new servers dual-era for now: answer initialize for legacy clients, and serve any request that carries io.modelcontextprotocol/protocolVersion statelessly. Lab 2 does it in under 100 lines.

tools/list: the message that fills the context window

A server that declares the tools capability must answer tools/list. The reply is an array of tool definitions. This is the complete definition of one tool from the lab server, as it travelled:

The name, the description and the schema with its per-property descriptions are everything the model knows about your tool. The schema is also the contract the model fills in: enum, required, minimum and a one-line description per property do more for call accuracy than a long tool description. The specification asks servers to return tools in a deterministic order, so that a client can cache the list and the model provider's prompt cache keeps hitting.

tools/call and what comes back

The request names the tool and passes an arguments object. The result has a content array of typed items, and optionally structuredContent and isError.

structuredContent is any JSON value and is meant for programs. A tool that returns it should also put the same data, serialised, in a text item, for clients that only read content. Every content item may carry annotations with audience, priority and lastModified.

Two kinds of failure, and why the difference matters

The specification separates protocol errors from tool execution errors. An unknown tool name, a request that does not match the call schema, or a server fault is a JSON-RPC error. An API failure, an input validation failure or a business-rule failure is an ordinary result with isError: true and a text that says what was wrong. The reason is the reader: clients should pass tool execution errors to the model so it can correct itself, and may or may not pass protocol errors on. These are the two replies from Lab 2, for a host that does not exist and for a tool that does not exist:

{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text",
  "text":"No host named mail-09. Known hosts: web-01, web-02, db-01."}],"isError":true}}
{"jsonrpc":"2.0","id":2,"error":{"code":-32602,"message":"Unknown tool: reboot_host"}}
Write the isError text for the model: say which argument was wrong and what a valid value looks like. The first reply above gives the model the three valid host names, and its next call can be right.
Returning a JSON-RPC error for a bad argument value hides the detail from the model in clients that do not forward protocol errors, and the model retries blind. Returning a successful result with the text "error: ..." and no isError is worse: the client and the model both count it as a success.

List changes, pagination and caching

A server that declared tools: {"listChanged": true} may announce a change with the notification notifications/tools/list_changed, and the client then calls tools/list again. In the legacy era the server sends it on the open connection. In 2026-07-28 nothing is sent unasked: the client opens a long-lived subscriptions/listen request and opts in to toolsListChanged, and change notifications arrive on that request's stream. Resources and prompts have the same notification under their own names. Claude Code refetches the list when the notification arrives, and in a -p run it refreshes only the tool list.

All list methods paginate the same way. A reply may carry nextCursor, an opaque string. The client repeats the request with params.cursor set to it until a reply has no nextCursor. The server chooses the page size and the client must not assume one. In 2026-07-28 list replies and resources/read also carry ttlMs, a freshness hint in milliseconds, and cacheScope, "public" or "private", which says whether a shared intermediary may cache the reply.

Resources

A resource is data with a URI. resources/list returns entries with uri, name, and optional title, description and mimeType. resources/read takes a uri and returns contents, an array whose items carry the uri, a mimeType and either text or base64 blob. resources/templates/list returns URI templates such as file:///{path} for resources that are parameterised. A resource that does not exist is error -32602 in 2026-07-28 (-32002 in earlier revisions, which clients should still accept), never an empty contents array. Watching a resource for changes was resources/subscribe in the legacy era and is a resourceSubscriptions filter on subscriptions/listen now. The server then sends notifications/resources/updated with the URI.

Prompts

A prompt is a named template. prompts/list returns entries with name, optional title and description, and arguments, each with name, description and required. prompts/get takes the name and an arguments object and returns messages, each with a role and a content item. An unknown prompt name or a missing required argument is error -32602.

A transport is a binding

The messages mean the same thing on every transport. A transport only defines how a message is framed and delivered, where request metadata travels, and how cancellation and shutdown are signalled. The specification defines two standard ones and allows custom ones.

stdio: stdout is the wire

The rules are short. The server reads messages from stdin and writes messages to stdout, one per line, and a message must not contain a newline. The server must not write anything to stdout that is not a valid MCP message. It may write anything it likes to stderr, and the client may capture, forward or ignore that, and should not treat stderr output as a sign of failure. The client must not write anything to stdin that is not a valid message.

So stdout belongs to the protocol and stderr is the log. Every stray console.log, a startup banner, a progress line from a library, or a shell profile that prints a greeting lands in the middle of the message stream. What happens next depends on the client. The test client you write in Lab 2 parses every line as JSON and stops on the first one that is not. Claude Code 2.1.322 was more forgiving in Lab 3: a server that printed one banner line before its first reply still connected and worked. That tolerance is not in the specification, so do not build on it.

In Node, console.log writes to stdout and console.error writes to stderr. In a stdio server use only console.error or process.stderr.write for diagnostics, and check any library you import for a habit of printing to stdout.

JSON.stringify without an indent argument never emits a raw newline, because newlines inside strings are escaped as \n. Pretty-printed JSON breaks the framing: each line of it is read as a separate, invalid message.

Claude Code sets CLAUDE_PROJECT_DIR in the environment of a stdio server it starts, so the server can find the project root without trusting its working directory. In 2026-07-28 a stdio process is explicitly not a session: the client may interleave unrelated requests on it, and may restart the process and retry.

Streamable HTTP, 2026-07-28 shape

The server exposes one path, the MCP endpoint, for example https://example.com/mcp, and it accepts POST. The rules for the client:

  • Every message is its own POST. The body is one JSON-RPC request or notification.
  • The Accept header lists both application/json and text/event-stream, because the server chooses per request which one to answer with and the client must handle both.
  • MCP-Protocol-Version is required on every POST and must equal the version in the body's _meta.
  • Mcp-Method is required and mirrors method. Mcp-Name is required on tools/call, resources/read and prompts/get and mirrors params.name or params.uri.

The headers exist so that a load balancer or gateway can route and rate-limit without parsing JSON. Because two sources of truth invite abuse, the server must compare them with the body and reject a mismatch.

It must not send requests of its own. A broken stream loses the request in flight, and the client sends it again as a new request with a new id. The older HTTP+SSE transport

The transport of revision 2024-11-05 used two endpoints, one SSE stream and one POST target. It has been deprecated since 2025-03-26 and the current registry lists it for removal. Claude Code still connects to such servers: its documentation calls the SSE transport deprecated, and from version 2.1.265 a server added with --transport http is tried over Streamable HTTP first and switched to SSE when it does not accept that. Claude Code's configuration also accepts a WebSocket server type, which is outside the two standard transports.

Running an HTTP server on your own machine

The specification's security rules for Streamable HTTP are three, and they are the same ones you would apply to any local admin listener. Validate the Origin header and answer 403 when it is present and not one you expect, because a web page in the user's browser can otherwise reach a local port by DNS rebinding. Bind to 127.0.0.1 and not to all interfaces when the server is local. Require authentication on every connection. Lab 4's listener does all three in 40 lines.

What the specification requires

Authorization is optional in MCP and defined at the transport level. Where it is used, an HTTP transport should follow the specification's OAuth-based scheme. A stdio transport should not: the server takes its credentials from its environment. That one sentence is the whole stdio story, and it is why a stdio server's configuration entry has an env block.

For HTTP the specification assigns OAuth 2.1 roles. The MCP server is a resource server: it accepts access tokens and checks them. The MCP client is an OAuth client acting for the user. The authorization server issues the tokens and may be a different system altogether, such as your identity provider.

Two server-side rules close the loop. The MCP server must check that a token was issued for it as the audience, which is what the resource parameter makes possible, and must answer an invalid or expired token with 401. And it must not pass the token it received on to another service: a server that calls an upstream API needs its own credential for that. The first rule stops a token minted for one server being replayed at another. The second stops your MCP server from becoming a proxy that launders tokens.

Tool names and permission rules

Claude Code exposes every MCP tool to the model as mcp__<server>__<tool>, where the server part is the name from your configuration, not the name the server reports about itself. Characters such as a dot or a space in the server name become underscores. This is the specification's advice in practice: tool names are only unique within one server, so an aggregating client should prefix them and should not rely on serverInfo.name.

RuleMatches
mcp__inventory__ping_hostOne tool
mcp__inventory__* or mcp__inventoryEvery tool of the inventory server
mcp__inventory__list_*That server's tools whose names start with list_
mcp__* as a deny or ask ruleEvery MCP tool of every server. As an allow rule it is skipped: an allow glob needs a literal mcp__<server>__ prefix

An MCP tool that no allow rule covers needs a permission prompt. In a headless run there is nobody to answer it, so the call is denied and listed in the result's permission_denials. Grant exactly the tools a job needs with --allowedTools. Rules in a settings file cannot match on an MCP tool's arguments: Claude Code skips any mcp__ rule written with parentheses.

How the definitions reach the model: tool search

By default Claude Code does not put MCP tool definitions into the context at all. With tool search on, only the tool names and each server's instructions load at session start. When the model wants a tool it calls the built-in ToolSearch tool, and the definition is loaded then. In Lab 3 the model's first action was ToolSearch with the query select:mcp__inventory__ping_host, the result was a tool_reference block, and the real call followed on the next turn.

Subscription and API

Nothing in the protocol differs between a plan and an API key. Self-check

Which line of http.mjs changed in core.mjs to add HTTP? None. The transport imports handle and adds framing, headers and status codes around it. That is what "a transport is a binding" means.

Why does the listener check the token before it parses the body? An unauthenticated caller should not get to exercise the JSON parser or the protocol core at all.

The wrong-token run and the no-header run both end in failed. How do you tell them apart from the server side? The log. With a configured header there is one rejected POST and nothing else. With no header there is a rejected POST followed by the /.well-known/ requests.

Would this listener be acceptable on a shared network? No. A static shared token has no user, no expiry and no audience, and the listener speaks plain HTTP. Lesson 5's scheme and TLS are the minimum there.

// own.mjs: one read-only data source wrapped as one tool. Replace the three numbered parts with your own.
import { createInterface } from 'node:readline';
import { readFileSync } from 'node:fs';

const FILE = process.env.TICKETS_FILE || 'tickets.csv';      // 1. where the data lives (opened read-only, per call)
const tool = {                                               // 2. how the model sees it
  name: 'tickets_for_host',
  description: 'List the tickets recorded for one host in the ticket export. Read-only.',
  inputSchema: { type: 'object', additionalProperties: false, required: ['host'],
    properties: { host: { type: 'string', description: 'Host name, for example web-01' } } },
  annotations: { readOnlyHint: true }
};
function run(args) {                                         // 3. the lookup. Throw for a problem the model can fix
  if (typeof args.host !== 'string') throw new Error('Argument "host" must be a string, for example web-01.');
  const rows = readFileSync(FILE, 'utf8').trim().split(/\r?\n/).slice(1).map((line) => line.split(','));
  const hits = rows.filter((r) => r[1] === args.host);
  return hits.length ? hits.map((r) => `#${r[0]} ${r[2]} opened ${r[3]}`).join('\n') : `No tickets for ${args.host}.`;
}

const text = (t, isError) => ({ content: [{ type: 'text', text: t }], ...(isError ? { isError: true } : {}) });
createInterface({ input: process.stdin }).on('line', (line) => {
  let msg;
  try { msg = JSON.parse(line); } catch { return; }
  if (msg.id === undefined) return;                          // a notification is never answered
  const reply = (body) => process.stdout.write(JSON.stringify({ jsonrpc: '2.0', id: msg.id, ...body }) + '\n');
  if (msg.method === 'initialize') {
    return reply({ result: { protocolVersion: '2025-11-25', capabilities: { tools: {} }, serverInfo: { name: 'own', version: '0.1.0' } } });
  }
  if (msg.method === 'tools/list') return reply({ result: { tools: [tool] } });
  if (msg.method === 'tools/call' && msg.params.name === tool.name) {
    try { return reply({ result: text(run(msg.params.arguments || {})) }); }
    catch (e) { return reply({ result: text(e.message, true) }); }   // a tool execution error: a result, with isError
  }
  if (msg.method === 'tools/call') return reply({ error: { code: -32602, message: 'Unknown tool: ' + msg.params.name } });
  reply({ error: { code: -32601, message: 'Method not found: ' + msg.method } });
});

Your source has 40,000 rows. What happens if the tool returns them all? A text result over 50,000 characters is saved to a file and the model gets a path, and anything over the token limit does not reach the model as content. Bound the result in the tool and let the model ask for the next page.
