Claude Code is one engine with many front ends: a terminal program, a VS Code panel, a JetBrains plugin, a desktop app, a browser page, a phone app, a chat mention and a CI job. They differ in two things that matter to an engineer: where the commands actually execute, and which of your configuration comes along. This module places every surface on that map and then compares the two most people choose between, the terminal CLI and the VS Code extension, feature by feature from the documentation.

After this module you can

  • Say for each surface whether the work runs on your machine, on a cloud VM or on a CI runner, and what that means for files, network and credentials.
  • List what the VS Code extension adds over the CLI and what stays CLI-only, and name the three different ways to run Claude Code inside VS Code.
  • Connect a terminal session to an editor with /ide or --ide and explain what the built-in ide server exposes.
  • Predict which settings, instructions, MCP servers, skills and hooks a given surface will load, including a cloud session that starts from a clone.
  • Start a session in one surface and continue it in another, and say which moves carry the same session and which make a copy.
  • Pick a surface for a task from its constraints: plan or API key, network, and where the code is allowed to live.

What you need

Two questions to ask of any surface

The documentation calls each place you can use Claude Code a surface, and says the same thing on two pages: every surface connects to the same underlying engine. The agent loop, the tools, the permission system and the file formats do not change. What changes is answered by two questions. First: on which computer do the shell commands and file edits run. Second: which configuration is present on that computer when the session starts.

There are three answers to the first question. A local session runs on your machine, with your files, your network position and your credentials. A cloud session runs on a virtual machine, managed by Anthropic by default, that starts from a fresh clone of a repository. A CI session runs on whatever runner your pipeline gives it. Everything else in this module follows from which of the three you are in.

Two rows deserve a second look. The VS Code extension and the JetBrains plugin are both "the IDE integration", but they are built differently: one carries its own engine and draws its own interface, the other is glue around the terminal program. And Remote Control and the web share an address, claude.ai/code, while being opposites on the first question: one executes on your machine, the other on a cloud VM.

Before you compare features, ask where the shell commands run. A surface that runs elsewhere does not have your files, your VPN or your credentials, whatever its interface looks like.

What "front end to the same engine" buys you

Because the local surfaces are front ends to one program, they read the same files. The platforms page puts it in one sentence: configuration, project memory and MCP servers are shared across the local surfaces. A permission rule you wrote for the terminal applies in the VS Code panel. A hook that blocks a command blocks it in the desktop app. The lesson "What is shared and what is not" makes that precise, including the places where it stops being true.

The sentence says local surfaces. A cloud session has none of your user-level setup: it sees what is committed to the repository and nothing from your home folder.

Two programs that look like one

The extension is not a skin over the claude you installed. It bundles its own copy of the CLI for the chat panel, and the docs state that installing the extension does not put claude on your PATH. The reverse also holds: installing the CLI does not give you the panel. A machine with both has two copies of the engine, and they can be at different versions. The extension's version number is the Claude Code version it bundles, so the Extensions view tells you which one the panel runs, and claude --version tells you which one the terminal runs. Many extension features in the docs carry a line such as "Requires Claude Code v2.1.275 or later"; that refers to the extension's version.

Reading the table as an engineer

The pattern is consistent. The extension wins wherever the task is looking at something: a diff beside the file, a plan you annotate, the lines you have selected, a history you can search. The CLI wins wherever the task is composing something: a pipeline, a script, a flag set you can put in version control, a command the panel does not carry. Neither wins on capability of the model or on configuration, because both are the same engine reading the same files.

One row is a security property and easy to miss. In the panel, text you select in a file matched by files.exclude, search.exclude or, by default, .gitignore is withheld from Claude. That filter covers the chat panel only. The same selection made while claude runs in the integrated terminal can reach the model. The docs give the surface-independent fix: a Read deny rule for the path, which blocks both the selected text and the open-file notice.

Do not treat the editor's ignore settings as a data boundary. They protect one front end. A Read deny rule in a settings file protects every local surface, because every local surface reads that file.
If you want to script it, pipe it or pin its flags, use the CLI. If you want to look at it before you approve it, use the panel. If you want both, run the CLI in the integrated terminal and connect it to the editor, as the next lesson shows.

How a terminal session finds the editor

When the extension is active it runs a local MCP server named ide. A claude process started in VS Code's integrated terminal connects to it automatically. From a terminal outside VS Code, you type /ide inside the session to connect; the commands reference describes /ide as "Manage IDE integrations and show status". The flag form is claude --ide, which connects at startup "if exactly one valid IDE is available".

Through that connection, the docs say, the CLI opens diffs in VS Code's native diff viewer, reads your current selection for @-mentions, and asks VS Code to execute cells when you work in a Jupyter notebook. While connected, each prompt you send includes the current selection and the active file's path, and the transcript shows a line of the form ⧉ Selected N lines from <file>. The extension's Attach Selection and Attach Open File settings apply here as well as in the panel.

A rule meant to cover diagnostics everywhere names both. A Read deny rule covers neither.

Since Claude Code 2.1.318 the CLI no longer installs the extension for you when it starts in the integrated terminal. Without the extension, /ide reports "No available IDEs detected" and /status shows the IDE as "Not connected". From an external terminal, /ide still installs it unless autoInstallIdeExtension is turned off.

Going back and forth

The docs state that the extension and the CLI share the same conversation history. To continue a panel conversation in the terminal, run claude --resume and pick it. In the other direction, the panel's Session history lists local conversations, and from extension version 2.1.304 it also lists sessions that claude -p or the Agent SDK started in the workspace. The extension also registers a link handler, vscode://anthropic.claude-code/open, which takes a session parameter with a session ID from the folder open in VS Code and a URL-encoded prompt parameter that pre-fills the prompt box without sending it.

One guard exists against using a conversation twice. If the panel finds that a conversation is still open in another Claude Code process, it shows a notice in place of the prompt box that says using it in two places at once can mix up its messages, and waits for you to close the other copy or choose "Open here anyway".

JetBrains: the CLI with an editor attached

The JetBrains plugin works with IntelliJ IDEA, PyCharm, Android Studio, WebStorm, PhpStorm, GoLand and most other JetBrains IDEs. Its design is the third way from the previous lesson made permanent: the plugin runs the claude command in the IDE's integrated terminal and connects to it. It does not bundle a CLI, so you install both pieces, and the plugin shows a "Cannot launch Claude Code" notification when claude is not on your PATH.

The cloud: a VM, a clone, a branch

A cloud session, also called Claude Code on the web when started from claude.ai/code, runs through four steps on an Anthropic-hosted environment: the repository is cloned to a VM and your setup script runs; network access is set from the environment's access level; Claude works; and when it reaches a stopping point it pushes its branch to GitHub for you to review. The VM is a fresh Ubuntu 24.04 x86_64 machine whatever your own operating system is, with common toolchains installed.

From the terminal, hand-off is one-way. claude --cloud "task" starts a new cloud session, and claude -p "message" --cloud <session-id> queues a follow-up message into an existing one and exits without waiting. claude --teleport pulls a cloud session down; it requires a clean working tree, a checkout of the same repository, the session's branch pushed to the remote, and the same claude.ai account. The local --resume picker does not list cloud sessions.

Remote Control and the phone

Remote Control is the opposite arrangement. The session keeps running on your machine with your filesystem, MCP servers and project configuration, and claude.ai/code or the Claude mobile app becomes a second keyboard and screen for it. You start it with claude remote-control (a server with no local interactive session), claude --remote-control (an interactive session that is also reachable), or /remote-control in a running CLI, VS Code or desktop session. The docs state that the local session makes outbound HTTPS requests only and never opens an inbound port, and that while connected the transcript is stored on Anthropic's servers. Close the terminal or stop the process and the session goes offline.

Some commands stay local: the docs name /plugin and /resume as working only from the local CLI. From the phone or browser you cannot select Bypass permissions.

Phone plus computer switched on: Remote Control, and you keep your local setup. Phone plus computer switched off: a cloud session, and you get the repository and nothing else.

On billing the two worlds differ in the usual way. With a plan, every surface draws on the same plan limits: a cloud session "counts toward your plan's usage limits alongside the rest of your Claude and Claude Code usage". With an API key you pay per token for the CLI, the extension and CI, and the plan-only surfaces are not open to you. The module "Tokens and their price" covers what the numbers mean.

Credentials set in the environment do not reach every surface. The authentication page states that ANTHROPIC_API_KEY, ANTHROPIC_AUTH_TOKEN and apiKeyHelper apply to the CLI and the surfaces that wrap it, including the VS Code extension, the Agent SDK and GitHub Actions, while the desktop app and cloud sessions do not read them and use OAuth.

A key exported in your shell is seen by the panel only if VS Code inherited that shell's environment. The VS Code page describes the symptom: the key is set, and the panel still shows the sign-in prompt. Launch VS Code with code . from that shell, or sign in with your account.
Choose by where the work must run first, by what the account allows second, and by interface last. The interface is the only one of the three you can change your mind about mid-task.

You run read-only commands that show which front ends are installed and which account they use, and fill in a five-row table you will use in the other labs.

  1. Ask the terminal CLI for its version.

    claude --version

    Expected: one line such as 2.1.322 (Claude Code). This is the copy on your PATH, the one a terminal runs.

  2. Ask VS Code for its version and for the Claude Code extension. Both commands only read.

    $code = Get-Command code -ErrorAction SilentlyContinue
if ($code) {
  code --version | Select-Object -First 1
  code --list-extensions --show-versions | Select-String -Pattern 'anthropic\.claude-code'
} else { 'code: not on PATH' }

    Expected: with VS Code and the extension installed, a version line (the docs require 1.94.0 or later) and one line of the form anthropic.claude-code@2.1.x. That number is the Claude Code version the panel runs, and it can differ from step 1. With VS Code installed and no match, the extension is absent. On the machine these labs were verified on, VS Code's code command was not on the PATH and the output was code: not on PATH; the installed-extension branch was not machine-verified.

  3. Ask the CLI how it is signed in. Print only the fields that matter here.

    claude auth status | ConvertFrom-Json | Select-Object loggedIn, authMethod, apiProvider | Format-List
    loggedIn    : True
authMethod  : claude.ai
