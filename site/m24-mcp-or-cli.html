An agent can reach a capability two ways: through an MCP server that publishes typed tools, or through a command-line program it drives with the shell tool. The choice looks like a matter of taste until you price it, and the price is not where the folklore says. This module builds one small capability both ways, runs the same task through each with the same model, and reads the difference off the transcript: tokens by type, requests, cost, tool-result size, permissions and what each approach leaves behind for an auditor.

After this module you can

  • Build one capability as a shared core with a CLI front end and an MCP front end, and show that both return the same answers.
  • Run the same task through each front end three times with --output-format stream-json and tabulate input, cache-write, cache-read and output tokens, API requests, cost and correctness.
  • Explain, from the measured numbers, what a tool definition costs with tool search on and off, and where the larger fixed cost of a request actually sits.
  • Show how an unfiltered tool result raises the size of every later request, and design a result that is filtered at the source.
  • Write the permission rule for one MCP tool and for one CLI subcommand, and say what each leaves in the transcript.
  • Pick MCP or CLI for a new capability from a decision table that weighs surfaces, auth, auditing and maintenance, not only tokens.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The labs were run on 2.1.322 with Haiku 5.5.
  • Node 22 or later and Windows PowerShell 5.1 or PowerShell 7. The labs use no packages: the CLI and the MCP server are plain Node files.
  • About $0.10 of Haiku usage at API list price for all the labs, or the same share of a subscription's 5-hour window. The labs make about 40 headless runs.

If you skipped the prerequisites

Tokens and their price: every API request re-sends the whole prompt (system prompt, tool definitions, history). The usage block splits it into input tokens (not cached), cache write tokens (stored for later, priced above input), cache read tokens (a repeat of a stored prefix, priced far below input) and output tokens. A long prefix is cheap per request once cached, so what matters is how large the prefix is and how many requests a task needs. MCP: a server is a separate process that Claude Code talks to with JSON-RPC. It answers tools/list with a name, description and JSON Schema per tool, and answers tools/call with content blocks and an isError flag. A stdio server is started by Claude Code and speaks over its stdin and stdout; a remote server speaks Streamable HTTP. Claude Code exposes each tool as mcp__<server>__<tool>.

The same job, two shapes

"Query the ticket system" is a capability. The MCP version publishes it as three tools, each with a JSON Schema. The CLI version publishes it as one program with subcommands and a usage text. The agent meets them differently. A CLI is reached through the shell tool the agent already has: it runs --help if it does not know the syntax, writes a command line, reads stdout, and sees stderr and the exit code when something fails. An MCP tool is reached through the MCP client inside Claude Code: the model produces a structured call, Claude Code validates nothing for you beyond transport, and the server replies with content blocks. The model never sees a command line, and the server never sees a shell.

The shape you will build

The lab writes four small files: store.mjs (the core, about 2 KB), tk.mjs (the CLI front end, about 1.3 KB) and tk-mcp.mjs (the MCP front end, about 2.5 KB), plus a generator for 120 synthetic tickets. The MCP front end is larger because it also carries the schemas and the JSON-RPC plumbing. That is a real cost of the MCP path, and it is paid once by the author, not per request by the agent.

Put the logic in a core both front ends call. Then the choice between MCP and CLI stays reversible, and a thin wrapper can be added later for the other kind of client.
Writing the capability inside the MCP server first and the CLI "later" ends with two implementations that disagree on filtering, defaults and error text. Build the core first.

What a request carries

Every request to the model carries the system prompt, the definitions of the tools the model may call, and the whole history so far (see Tokens and their price). Tool definitions are the part this choice changes. A CLI adds none: the Bash tool is already there, and the program's usage text enters the history only if the model asks for it. An MCP tool adds a name, a description and an input schema, which is the cost most people mean when they say "MCP is heavy".

Claude Code defers that cost by default. With tool search on, only the names of MCP tools (and server instructions) load at session start. The model finds a tool through the built-in ToolSearch tool, and the matching definitions are loaded on demand. At the API level this is the tool search tool: tool definitions carry defer_loading: true, and a search returns tool_reference blocks that the API expands into full definitions. The platform docs recommend tool search when you have 10 or more tools or more than 10k tokens of definitions, and say standard tool calling is the better fit for fewer than 10 tools or when every tool is used in every request.

Three switches control it. ENABLE_TOOL_SEARCH unset or true defers MCP tools, false loads all of them upfront, and auto or auto:N loads them upfront while their definitions stay under 10% (or N%) of the context window. "alwaysLoad": true in a server entry exempts that server. A description is cut at 4,096 characters when it loads upfront and at 16,384 when it loads through tool search, so put the words a search would match near the start.

Two things stand out. First, a request is about 21,700 tokens before any MCP server is attached, and a three-tool server adds about 110 of them with tool search on and about 640 with it off. At this size the tool schemas are not where the cost is. Second, turning tool search off adds about 15,600 tokens even with no MCP server at all. The headless /context report shows why: with tool search on, "System tools" is 11.6k and "System tools (deferred)" is 13.8k; with it off, "System tools" is 27.7k. With tool search on, the MCP overhead of a handful of tools is small enough to ignore. It scales with tool count and schema size, so measure a server with 30 tools, not 3.

A deferred MCP tool whose arguments are easy to guess is sometimes called without its schema. It works until a schema has an unusual field name. Put argument names in the tool description, and use alwaysLoad for the two or three tools that are used on every turn.

A tool result is paid for on every later request

A tool result joins the history and stays in the prefix of every request after it. Cached, it is cheap per request, but it makes each request larger and it lengthens the whole task. Which front end returned it does not matter. The size of the result is set by the program, so that is where it has to be controlled.

Claude Code has backstops, and they sit high. MCP output is limited to 25,000 tokens by default (MAX_MCP_OUTPUT_TOKENS), a warning shows above 10,000 tokens, and a successful text result over 50,000 characters is saved to a file. Bash output read back into a result is limited to 30,000 characters by default (BASH_MAX_OUTPUT_LENGTH, maximum 150,000). A result of 27,000 characters passes both. For Bash calls the cost docs also show a PreToolUse hook that rewrites a command so only the last 100 lines come back.

The CLI arm shows a second effect. A missing count subcommand turned into extra turns.

Design a result for a model

  • Return the answer shape, not the table: a count with --by, a search with filters and a limit.
  • One line per record with the fields a decision needs, and a separate get for the whole record.
  • Say what was left out: (2 more: add filters or raise the limit) tells the model how to continue.
  • Make errors teach: "severity" must be one of: low, medium, high lets the model fix the next call without a lookup.
  • Set a default limit in the program, so the safe call is the short one.
Filter at the source. A limit, a count and one line per record move the bill more than the choice between MCP and CLI does.

Where the credential lives

An MCP server gets its credentials from its own configuration, outside the conversation. The server entry has an env block for a stdio server and headers (or a headersHelper that generates them) for an HTTP server. A project-scoped .mcp.json can reference shell variables with ${VAR} or ${VAR:-default} in command, args, env, url and headers, so the file can be committed while the value stays on each machine. A server that uses OAuth is signed in from an interactive session with /mcp or claude mcp login <name>; a claude -p run has no panel to run that flow, so the sign-in must already exist.

A CLI gets whatever the shell around it provides: environment variables, a config file, or a login the tool stored itself. The agent's shell commands run in that environment, so a secret exported there is readable by any command the agent writes. CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1 strips credentials from the environment of Bash commands, hooks and stdio MCP servers, recognising them by variable name or value shape. It leaves GITHUB_TOKEN and the proxy variables in place so that GitHub tooling keeps working, and it leaves a secret whose name and value do not look like a credential. The docs call it one layer, to be used with narrow permission rules.

Permission rules

MCP tools are matched by name only: mcp__tickets or mcp__tickets__* for the whole server, mcp__tickets__ticket_count for one tool. An mcp__ rule with parentheses is skipped when a settings file loads, so you cannot allow a tool for some arguments and not others. The docs give one route for matching an MCP parameter: a deny rule passed with --disallowedTools. Allow rules accept a tool-name glob only after a literal mcp__<server>__ prefix.

Bash rules match the command text Claude writes, with * as a wildcard: Bash(node tk.mjs count *). Claude Code splits a compound command at &&, ||, ;, |, |&, & and newlines, and every part must be allowed, so a rule for one program does not approve it chained to another. A rule matches the command in the form it was written, not the same program invoked another way. This gives a CLI finer control over arguments than an MCP tool has (count * allowed, search * not), and it gives the model more ways to wander: it can pipe, redirect or script around the program, and each of those parts needs its own approval. Lab 5 shows both.

What each leaves behind

The session transcript records every tool call. An MCP call is stored as a tool_use block whose name is mcp__tickets__ticket_count and whose input is a JSON object you can query by field. A CLI call is stored as a tool_use block named Bash whose input is one command string, and an audit has to parse that string. For OpenTelemetry export, OTEL_LOG_TOOL_DETAILS=1 adds tool input arguments and MCP server names to the telemetry; it is off by default and ignored in project settings. The Telemetry module covers the export itself.

Use MCP when you need to grant or deny one named operation and report on it by field. Use a CLI when you need to constrain by argument pattern, and accept that the audit reads command strings.
A broad Bash rule such as Bash(node *) approves every Node script in the project, including ones the agent has just written. Name the program and the subcommand.

Where each one works

A CLI is useful to three audiences with no extra work: the agent, a person at a shell, and a script or scheduled job. An MCP server is useful to any MCP client, including clients that have no shell tool, and it can be shared through a project's .mcp.json or shipped inside a plugin. The protocol itself is client-neutral: the MCP module covers the transports and the lifecycle.

Claude Code runs in several places (see Where Claude Code runs). A cloud session runs in a cloud environment, which the docs describe as the saved configuration for network access, environment variables and setup scripts. Whatever the agent needs there must be reachable from that environment: a CLI has to exist in the container, and a remote MCP server has to be reachable over the network the environment allows. The same page notes that a session waiting for an MCP connector approval or a sign-in counts as inactive and can expire.

Maintenance

The two interfaces age differently. An MCP tool's schema is a published contract: the client validates against it, a server can change its tool list while connected and send list_changed, and the protocol itself has dated revisions that clients and servers negotiate (the MCP module lists the current one). The hand-written server in this module speaks the older 2025-11-25 revision and worked unchanged under Claude Code 2.1.322, which is the point of negotiation. A CLI's contract is its flags and its output format, which nothing validates. Rename a flag and every prompt, skill and CLAUDE.md line that spells it out is wrong, and the failure shows up as a usage error the model then has to recover from.

Both need an owner for the same things: the core logic, its tests, its credentials and its version. The MCP path adds a process lifecycle (start, reconnect, timeouts) and a schema to keep in step with the code. The CLI path adds the instructions that teach the model to call it.

Version the interface you cannot validate. For a CLI that means one usage text, kept next to the code, that the agent reads on demand, instead of copies of the syntax scattered across prompts.

  2. Write the core. Both front ends call run() and nothing else. It filters, counts, limits to 20 rows by default, says how many rows it left out, and rejects a bad filter value with a message that lists the valid ones.

    Set-Content -Encoding utf8 -Path store.mjs -Value @'
// store.mjs: the capability itself. Both front ends call run() and nothing else.
import { readFileSync } from 'node:fs';
const all = () => JSON.parse(readFileSync(new URL('./tickets.json', import.meta.url), 'utf8'));
const KEYS = ['host', 'severity', 'status'];
const ENUM = { severity: ['low', 'medium', 'high'], status: ['open', 'closed'], by: KEYS };
const match = (f) => (t) => KEYS.every((k) => !f[k] || t[k] === f[k]);

export const VERBOSE = process.env.TK_VERBOSE === '1';   // lab 4: whole records as JSON, no limit, no count

function search(f) {                                      // oldest first
  const rows = all().filter(match(f)).sort((a, b) => a.opened.localeCompare(b.opened) || a.id - b.id);
  if (VERBOSE) return JSON.stringify(rows, null, 2);
  const shown = rows.slice(0, Number(f.limit) || 20);
  const more = rows.length - shown.length;
  return (shown.map((t) => `${t.id} ${t.host} ${t.severity} ${t.status} ${t.opened} ${t.title}`).join('\n') || 'no tickets match')
    + (more > 0 ? `\n(${more} more: add filters or raise the limit)` : '');
}
function count(f) {
  const rows = all().filter(match(f));
  if (!f.by) return String(rows.length);
  const groups = {};
  for (const t of rows) groups[t[f.by]] = (groups[t[f.by]] || 0) + 1;
  return Object.entries(groups).sort((a, b) => b[1] - a[1]).map(([value, n]) => `${value} ${n}`).join('\n');
}
function get(f) {
  const t = all().find((x) => x.id === Number(f.id));
  if (!t) throw new Error(`no ticket with id ${f.id}`);
  return JSON.stringify(t, null, 2);
}

export const commands = VERBOSE ? { search, get } : { search, count, get };
export function run(name, f = {}) {                       // returns text, or throws an Error fit to show the caller
  if (!commands[name]) throw new Error(`unknown command "${name}"; commands: ${Object.keys(commands).join(', ')}`);
  for (const [k, v] of Object.entries(f)) {
    if (![...KEYS, 'limit', 'by', 'id'].includes(k)) throw new Error(`unknown option "${k}"`);
    if (ENUM[k] && !ENUM[k].includes(v)) throw new Error(`"${k}" must be one of: ${ENUM[k].join(', ')}`);
  }
  return commands[name](f);
}

  4. Write the MCP front end. It is a stdio server: one JSON-RPC message per line in and out, three tools with schemas, and a tool error returned as a result with isError: true. A notification (a message with no id) is never answered.

    Set-Content -Encoding utf8 -Path tk-mcp.mjs -Value @'
// tk-mcp.mjs: the MCP front end. stdio transport: one JSON-RPC message per line in, one per line out.
import { createInterface } from 'node:readline';
import { run, VERBOSE } from './store.mjs';

const str = (description, values) => ({ type: 'string', description, ...(values ? { enum: values } : {}) });
const id = { id: { type: 'integer', description: 'Ticket id, for example 1001' } };
const filters = { host: str('Host name, for example db-01'), severity: str('Severity', ['low', 'medium', 'high']), status: str('Status', ['open', 'closed']) };
const tool = (name, description, properties, required = []) => ({ name: 'ticket_' + name, description,
  inputSchema: { type: 'object', additionalProperties: false, properties, required }, annotations: { readOnlyHint: true } });

const tools = VERBOSE ? [
  tool('search', 'Return the tickets that match the filters as JSON.', filters),
  tool('get', 'Return one ticket as JSON.', id, ['id'])
] : [
  tool('search', 'List matching tickets, oldest first, one line each: id host severity status opened title.',
    { ...filters, limit: { type: 'integer', minimum: 1, maximum: 200, description: 'Maximum rows (default 20)' } }),
  tool('count', 'Count matching tickets. With "by", return one "value count" line per group.',
    { ...filters, by: str('Group the count by this field', ['host', 'severity', 'status']) }),
  tool('get', 'Return every field of one ticket as JSON.', id, ['id'])
];

const methods = {
  'initialize': () => ({ protocolVersion: '2025-11-25', capabilities: { tools: {} }, serverInfo: { name: 'tickets', version: '1.0.0' },
    instructions: 'Read-only queries over the ticket file: search, count and get tickets by host, severity and status.' }),
  'ping': () => ({}),
  'tools/list': () => ({ tools }),
  'tools/call': (p) => {
    try { return { content: [{ type: 'text', text: run(p.name.replace('ticket_', ''), p.arguments) }] }; }
    catch (e) { return { content: [{ type: 'text', text: e.message }], isError: true }; }   // a tool error is a result, not a protocol error
  }
};

createInterface({ input: process.stdin }).on('line', (line) => {

# show.ps1: Get-Run turns one stream-json run file into one table row. Show-Calls lists what the run did.
function Read-Run($file) { Get-Content $file | Where-Object { $_.StartsWith('{') } | ForEach-Object { $_ | ConvertFrom-Json } }
function Get-Run($file, $want) {
  $lines = Read-Run $file
  $r = $lines | Where-Object { $_.type -eq 'result' } | Select-Object -First 1
  $u = $r.usage
  $asst = @($lines | Where-Object { $_.type -eq 'assistant' })
  $calls = @($asst | ForEach-Object { $_.message.content } | Where-Object { $_.type -eq 'tool_use' })
  $requests = @($asst | ForEach-Object { $_.message.id } | Select-Object -Unique).Count      # one message id per API request
  [pscustomobject]@{
    run = $file -replace '\.jsonl$', ''; requests = $requests; calls = $calls.Count
    input = $u.input_tokens; cache_write = $u.cache_creation_input_tokens; cache_read = $u.cache_read_input_tokens; output = $u.output_tokens
    prompt_total = $u.input_tokens + $u.cache_creation_input_tokens + $u.cache_read_input_tokens
    cost = [math]::Round($r.total_cost_usd, 5); correct = [bool]($r.result -match [regex]::Escape($want))
  }
}
function Show-Table($names, $want) { $names | ForEach-Object { Get-Run "$_.jsonl" $want } | Format-Table -AutoSize | Out-String -Width 220 }
function Show-Requests($file) {   # the prompt size of each API request in a run: input + cache write + cache read
  $seen = [ordered]@{}
  foreach ($l in (Read-Run $file | Where-Object { $_.type -eq 'assistant' })) { $seen[$l.message.id] = $l.message.usage }
  ($seen.Values | ForEach-Object { $_.input_tokens + $_.cache_creation_input_tokens + $_.cache_read_input_tokens }) -join ' '
}
function Show-Calls($file) {
  foreach ($l in (Read-Run $file)) {
    if ($l.type -eq 'assistant') { $l.message.content | Where-Object { $_.type -eq 'tool_use' } | ForEach-Object { 'tool_use    ' + $_.name + ' ' + ($_.input | ConvertTo-Json -Compress) } }
    if ($l.type -eq 'user') { $l.message.content | Where-Object { $_.type -eq 'tool_result' } | ForEach-Object {
      $t = if ($_.content -is [string]) { $_.content } else { ($_.content | ForEach-Object { if ($_.text) { $_.text } else { $_ | ConvertTo-Json -Compress } }) -join ' ' }
      'tool_result ' + $t.Length + ' chars: ' + $t.Substring(0, [math]::Min(110, $t.Length)).Replace("`n", ' / ') } }
    if ($l.type -eq 'result') { 'result      ' + ([string]$l.result).Replace("`n", ' / '); 'denied      ' + (($l.permission_denials | ForEach-Object { $_.tool_name + ' ' + ($_.tool_input | ConvertTo-Json -Compress) }) -join '; ') }
  }
}

Settings, flags and fields used in this module

ItemWhat it does
--mcp-config FILE with --strict-mcp-configLoad MCP servers from the file and ignore every other configured server
--allowedTools "mcp__tickets"Allow every tool of the tickets server without a prompt; mcp__tickets__ticket_count allows one tool
--allowedTools "Bash(node tk.mjs count *)"Allow Bash commands that match the pattern, per subcommand of a compound command
--append-system-prompt TEXTAdd text to the system prompt; the labs use it to tell the model a CLI exists
--output-format stream-json --verboseOne JSON event per line: assistant messages with tool_use blocks, user messages with tool_result blocks, and a final result with usage, total_cost_usd and permission_denials
ENABLE_TOOL_SEARCHUnset or true: MCP tools deferred. false: all loaded upfront. auto or auto:N: load upfront while definitions stay under 10% (or N%) of the context window
"alwaysLoad": true in a server entryLoad that server's tools upfront whatever the tool search setting
MAX_MCP_OUTPUT_TOKENSMCP output limit, 25,000 tokens by default; a warning shows above 10,000 tokens; a text result over 50,000 characters is saved to a file
BASH_MAX_OUTPUT_LENGTHCharacters of Bash output read back into the result; default 30,000, maximum 150,000
CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1Strip credentials from the environment of Bash commands, hooks and stdio MCP servers
OTEL_LOG_TOOL_DETAILS=1Include tool input arguments and MCP server names in telemetry (off by default)
/context, also claude -p "/context"Prints context use by category, with MCP tools and system tools shown as deferred or loaded

Permission rule shapes

RuleMatches
mcp__tickets or mcp__tickets__*Every tool of the server
mcp__tickets__ticket_countThat one tool, whatever its arguments
mcp__tickets__ticket_count(host:db-01)Nothing: an mcp__ rule with parentheses is skipped
Bash(node tk.mjs count *)Commands that start with node tk.mjs count; each part of a compound command is checked on its own
Bash(node tk.mjs --help)Exactly that command

Failure modes

SymptomCauseFix
The model calls a deferred MCP tool with empty or guessed arguments and gets an errorThe tool's schema was not loaded when it called; tool search loads schemas on demandPut the argument names in the tool description and server instructions, or set alwaysLoad for the few tools used every turn
A task takes four or five requests where two would doSearch step, retry after a rejected call, or a usage lookup for a CLITell the model the syntax up front (CLAUDE.md, skill, server instructions) and make errors name the valid values
Every request after a lookup is 10,000 or more tokens largerA large tool result stays in the historyFilter, count and limit in the tool; return one line per record and a "more" hint
A CLI task burns turns on denied pipes, redirects and node -eThe Bash rule names one program; the model reached for other commands to post-processGive the CLI the filtering it needs (a count subcommand), or allow the extra commands deliberately
Prompt grows by 15,000 or more with tool search offBuilt-in deferred tools load upfront too, not only MCP toolsLeave ENABLE_TOOL_SEARCH unset unless a gateway or a model requires otherwise
Server tools missing in a -p runServer still connecting, failed to start, or needs OAuth that was never completedRead mcp_servers in the system/init event of a stream-json run (and mcp_server_errors for a skipped --mcp-config entry); sign in from an interactive session first
