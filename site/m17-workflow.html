The first weeks with Claude Code go better with a small set of habits than with a large set of configuration. This module is the working loop: look before you change, plan when the change is worth planning, give the agent a check it can run, undo cheaply when it goes wrong, keep parallel work apart, spend reasoning effort on purpose, and let nothing reach a shared branch that you have not read.

After this module you can

  • Run a task through explore, plan, implement, verify and commit, and say which steps a given task can skip.
  • Enter plan mode three ways, read what it allows and refuses, and predict what a headless run in plan mode leaves on disk.
  • Say which changes the rewind menu can restore, which it cannot, and reach for git when it cannot.
  • Continue, resume, name and branch sessions, and choose between /clear, /compact and a fresh session.
  • Run two sessions against one repository in separate worktrees, merge their branches and clean up.
  • Set the effort level four ways, read its cost from a JSON result, and keep an agent's git rights down to what the task needs.

What you need

  • Claude Code 2.1 or later, signed in (plan or API key). The labs were run on 2.1.322.
  • Git 2.x on the path, and Windows PowerShell 5.1 or PowerShell 7.
  • About $0.08 of usage at API list price for the four measured labs, most of it one plan-mode run that is upgraded to Sonnet, or the same share of a subscription's 5-hour window.
  • No prior module. This one stands alone. It names the modules that go deeper where it only skims.

The loop the agent runs

The Claude Code docs describe one task as three phases that blend together: gather context, take action, verify results. A question about the codebase may need only the first. A bug fix cycles through all three several times. The model decides what each step needs from what the previous step returned, and you can interrupt at any point.

The loop you run around it

Around that inner loop sits yours. The five steps below are this course's framing, assembled from what the docs say about plan mode, verification, checkpoints and git. The docs do not prescribe a ritual; they say a plain first prompt in a fresh session usually does the right thing, and that setup pays off where your project has knowledge, rules or checks the agent cannot see from the code.

StepWhat you doWhat supports itSkip it when
ExploreAsk how the thing works before asking for a changePlain questions; plan mode keeps it read-onlyYou already know the file and the fix
PlanHave the change proposed and read it before anything is writtenPlan modeYou could describe the diff in one sentence

VerifyMake the agent run a check and show you the outputTests, a build exit code, a linter, a diff against a fixtureNever; shrink the check instead
CommitRead the diff, commit one small topic/diff, git, a narrow allowlistThe work is a throwaway experiment

Four ways a session goes wrong

The best-practices page reduces most disappointing sessions to four causes. Knowing which one you are looking at tells you which lever to pull.

Verification you can run

The agent stops when the work looks done. Without something that returns pass or fail, "looks done" is all it has, and you become the test suite. With a check, it closes the loop itself: change, run, read the failure, fix, run again. The docs call the command that runs your existing check the single most useful line in a CLAUDE.md.

How strictFormWho decides it passed
In the prompt"run the auth tests after, and keep going until they pass"The model
As a goal/goal all tests in tests/auth pass and lint is cleanA separate model, after every turn
As a Stop hookA script that exits 2 while the check failsClaude Code itself; the turn cannot end
By a fresh reviewer/code-review on the diffA subagent that never saw the conversation

Whichever form you use, ask for evidence: the command that was run and its output. "All tests pass" on its own tells you little, and reading the output is faster than rerunning the check. The Hooks module builds the Stop gate; this module only uses the prompt form.

Before you ask for a change, decide what command will tell both of you it worked, and put that command in the prompt.

Say what the agent cannot see

A specific prompt works for the same reason a check does: it supplies information the agent does not have. Name the file, describe the symptom, and say what fixed looks like.

Instead ofWrite
"fix the login bug""users report login fails after the session times out. Look at token refresh in src/auth/, write a failing test that reproduces it, then fix it"
"add a report""follow the pattern in disk-report.ps1 and add a memory report with the same switches. No new modules. Run the Pester tests after"

Phrases such as "think step by step" or "be thorough" are ordinary prompt text. How hard the model works is set by the effort level, covered in lesson 5.

Steering

  • Esc stops the agent mid-action and keeps everything up to that point.
  • Typing a correction and pressing Enter while it works queues the message; the agent reads it when its current tool calls finish, inside the same turn.
  • Esc twice on an empty prompt, or /rewind, opens the rewind menu (lesson 3).
  • /clear starts over with an empty context.
A third correction of the same mistake mostly adds to a conversation that already holds two failed attempts, which the model re-reads on every turn. The docs' advice: after two failed corrections, /clear and write one better prompt that folds in what you learned.

What it permits and what it refuses

Plan mode is one of the permission modes. It tells the agent to research and propose changes without making them: it reads files, runs shell commands to explore, and writes a plan, but does not edit your source. Edits stay blocked until you approve the plan.

ActionIn plan mode
Read, search, list filesRuns without asking
Edit or write a source fileBlocked until a plan is approved
Shell command, auto mode available and useAutoModeDuringPlan on (the default)The auto mode classifier reviews it; approved commands run, rejected ones are blocked
Shell command, auto mode not available or useAutoModeDuringPlan offCommands outside the built-in read-only set prompt you
The plan itselfWritten as a file under ~/.claude/plans, or the folder named by the plansDirectory setting
One documented exception: in an interactive terminal session started with bypass permissions available, planning commands get neither the classifier nor a prompt. Plan mode is a working agreement backed by a permission check, and that launch flag removes the check. Do not combine them on a machine you care about.

Approving a plan

When the plan is ready the agent presents it and asks how to proceed.

ChoiceResult
Yes, and use auto modeLeaves plan mode, continues in auto mode. Reads "Yes, auto-accept edits" where auto mode is not available to the session
Yes, manually approve editsLeaves plan mode, you approve each edit

Approval is a mode switch: the session leaves plan mode and starts editing in the mode the option names. It also gives an unnamed session a title generated from the plan. Ctrl+G opens the proposed plan in your text editor so you can change it before the agent proceeds. With the setting showClearContextOnPlanAccept on, the menu gains a first option that approves the plan and clears the planning conversation, so implementation starts from the plan alone.

Plan mode without a person

A claude -p run accepts --permission-mode plan, but there is nobody to approve anything. In the verified lab run the agent explored, wrote the plan file, and ended its turn with the plan as the result text, noting that the tool for requesting approval was not available in the session. No tracked file changed and nothing was denied. That makes headless plan mode a cheap way to get a reviewable proposal out of a script: read the plan, then start a second run to carry it out.

The same run showed a cost detail worth knowing. A session on Haiku is upgraded to Sonnet while it plans; the model configuration page says so, and the result's modelUsage listed only claude-sonnet-5-5 although the run was started with --model haiku. The plan cost about $0.055 at list price against about $0.004 for the Haiku run that then implemented it. The pairing also exists as a model alias you can choose: opusplan uses Opus in plan mode and Sonnet for execution.

When planning is wasted effort

This part is engineering judgment, not a doc rule. A plan costs a round of exploration and a read by you. It earns that when the change touches several files, when you do not know the code, when there are two reasonable designs and you care which is chosen, or when a wrong start is expensive to unwind. It does not earn it for a typo, a rename, a one-line fix, or a question. The docs point the same way from the other side: because the rewind menu can roll code and conversation back, it is low-risk to try the bolder approach first and rewind if it does not work out.

Plan when you would want to review the approach before the diff. If the diff is the approach, skip the plan and read the diff.

What a checkpoint is

Claude Code snapshots a file before its file editing tools change it, and every prompt you send that starts a turn creates a checkpoint. Checkpoints are saved with the conversation, so they are still there after you resume a session. Snapshots are kept for the 100 most recent checkpoints in a session and are swept about 30 days after the session last saved one (the cleanupPeriodDays setting changes that). The feature is on by default; the setting fileCheckpointingEnabled turns it off.

The rewind menu

Run /rewind, or press Esc twice with an empty prompt. If the prompt holds text, the double Esc clears it instead. The menu lists the prompts you sent; pick one, then pick an action.

ActionFiles on diskConversation
Restore code and conversationBack to that pointBack to that point
Restore conversationKept as they areBack to that point
Restore codeBack to that pointKept
Summarize from hereUntouchedEverything after that point becomes a summary
Summarize up to hereUntouchedEverything before that point becomes a summary

The two code options appear only when that checkpoint has tracked file changes to revert. After restoring the conversation, the prompt you selected is put back in the input box so you can edit and resend it. Each use has a typical case: restore both to abandon an approach, restore the conversation alone to keep good edits but drop a muddled discussion, restore code alone to keep the discussion and try the edit again.

What is not tracked

The docs list the limits plainly. Learn this table; it decides when rewind is enough.

ChangeRestored by rewind
An edit made by the agent's file editing tools in your conversationYes
A file only a shell command changed or createdNo. Use version control
A shell command's change to a file the agent had already edited with its file toolsYes, that file is tracked from the first tool edit on
Edits made by a subagent to files your conversation had not editedUsually no. Use version control
Your own edits outside Claude Code, or another session's editsNormally no, unless they touch a file this session edited
Symlinked or hard-linked filesNo. They are skipped with a "skipped N files" warning
Anything outside the file system: a database row, an API call, a deployment, a sent message, a pushed commitNo. Nothing local can
A message you typed while the agent was still working has no checkpoint of its own; the menu marks it "No code restore". To undo the edits made after it, select the prompt that started the turn, which reverts the whole turn's edits.

The docs' own summary: checkpoints are for quick, session-level recovery and work alongside git, not in place of it. The habit that makes both work is in lesson 6: start each task from a clean tree, so git diff shows exactly what the session did and git can undo whatever rewind cannot.

Rewind for the last few minutes of tool edits. Git for everything on disk. A permission rule for everything that leaves the machine.

Sessions are saved and tied to a folder

A session is a saved conversation tied to a project directory. Claude Code writes it to a local transcript as you work, so you can leave and come back. Each new session starts with an empty context window; nothing carries over from the last one except what lives in files such as CLAUDE.md. The Context module covers what fills the window and what compaction keeps; the Session transcripts module covers the files on disk. This lesson is only about the moves.

You want toDo this
Pick up the most recent session in this folderclaude --continue
Choose from a listclaude --resume, or /resume inside a session
Go straight to oneclaude --resume <name-or-id>
Name a session at launchclaude -n disk-report
Name it later/rename disk-report
Find the session that opened a pull requestclaude --from-pr 123
Try another direction and keep the original/branch try-streaming, or claude --continue --fork-session
Ask a side question without adding to the history/btw

Name anything that will span more than one sitting. A name you set, or the title Claude Code generates from your first prompt, works as a resume handle. Resuming reopens the same session id and appends to it; branching or forking copies the history into a new id and leaves the original unchanged.

A resumed session restores the conversation, the model and, when you resume from a terminal by name or id, the permission mode it was in (a session that ended in plan mode comes back in plan mode). It does not restore launch flags such as --mcp-config, --settings or --add-dir; pass those again.

Sessions created with claude -p are left out of the session picker and out of claude --continue. Resume one by passing its session id to claude --resume, or use claude -p --continue, which does include them. And if you open the same session in two terminals without forking, both write into one transcript and the messages interleave.

Clear, compact, or start fresh

MoveWhat it doesUse it when

Current models have large windows and Claude Code compacts on its own, so running out is rare. The reason to clear is cost and focus: every request sends the whole conversation, so a session that has collected three unrelated tasks re-reads all three on every turn of the fourth. That re-read is discounted while the prompt cache is warm and full price once it expires. The docs give the cache about an hour on a subscription and five minutes on an API key, cloud provider or usage credits, so on an API key a coffee break is enough to make the next turn of a long session a cold one. /compact is itself a large request because it reads the whole conversation to summarise it. The Tokens and Cutting cost modules do the arithmetic.

Worktrees: two sessions, one repository

Two sessions in the same folder edit the same files and will overwrite each other. A git worktree is a second working directory with its own files and its own branch that shares the repository's history. Give each session a worktree and the edits cannot collide.

claude --worktree feature-auth
claude -w bugfix-123
FactValue
Where the worktree is created.claude/worktrees/<name>/ under the repository root
BranchNew, named worktree-<name>
No name givenClaude Code generates one
Starting commitThe default branch on the remote (worktree.baseRef "fresh", the default); with no remote it falls back to your local HEAD. Set "head" to branch from your current work
NeedsA git repository with at least one commit
Name already existsThat worktree is opened, not recreated

A worktree is a fresh checkout, so files git ignores (.env, installed dependencies) are not there. List the small ignored files you need in a .worktreeinclude file at the repository root, in .gitignore syntax, and Claude Code copies them into each worktree it creates. Add .claude/worktrees/ to your .gitignore so the worktrees do not show up as untracked files in the main checkout.

While a session is in a worktree, Claude Code blocks file-tool edits that target the main checkout, shell commands whose working directory is the main checkout, and git commands redirected there. The docs are plain about the gap: the checks read paths and command text, not what a command writes, so a copy or a shell redirect into the main checkout is treated like any other shell command under your permission settings. For PowerShell commands only the working-directory check applies.

Worktrees share more than history with the main checkout: git commands in a worktree write to the one shared .git directory, and project-scope plugins load in every worktree. The Orchestration module covers running many sessions at once; a worktree per session is the file-level half of that.

One task, one session, one branch, one folder. If two of those are shared between two agents, expect a collision.

What effort controls

Effort is a setting sent with each request that tells the model how much work to put into the response. The API docs describe it as a behavioural signal, not a strict token budget, and it affects all output: the text, the tool calls (lower effort means fewer and terser calls) and the thinking. On current models reasoning is adaptive: the model decides at each step whether and how much to think, and the effort level moves that decision.

LevelThe docs' guidance on when to use it
lowQuick exchanges where you review each result: brainstorming, a first sketch, a rename
mediumDay-to-day engineering work with a clear scope. The default on Fable 5.2, Opus 5.5, Sonnet 5.5 and Haiku 5.5
highWork where verification matters or edge cases are likely, such as a bug in code you did not write
xhighDeeper reasoning at higher token spend
maxHard problems you want worked through without you. Prone to overthinking on ordinary tasks; test before adopting it

All five levels exist on the Fable models, Opus 5.5, Sonnet 5.5 and Haiku 5.5. Opus 4.6 and Sonnet 4.6 have no xhigh. If you set a level the model lacks, Claude Code uses the highest supported level at or below it. The scale is calibrated per model, so medium on one model is not the same amount of work as medium on another.

Setting it

When more than one source sets a level, Claude Code takes the first of: the environment variable, a level picked in the session, the --effort flag, your settings, the model's default. A new level picked mid-session starts with your next message; a turn already in progress may finish at the old one. For a single hard question in otherwise routine work, the docs suggest putting the word ultrathink in that prompt: Claude Code recognises it and asks for deeper reasoning on that turn without changing the setting. Other phrases ("think hard", "think more") are passed through as ordinary text.

An exported CLAUDE_CODE_EFFORT_LEVEL silently beats /effort and --effort. If the level you pick does not seem to take, check your shell profile and CI variables before anything else.

Extended thinking

Extended thinking is the reasoning the model emits before it responds. Claude Code collapses it by default; Ctrl+O opens the transcript viewer where it shows. On Opus 5.5, Sonnet 5.5, Haiku 5.5 and the Fable models thinking cannot be turned off: the session toggle (Alt+T on Windows and Linux, Option+T on macOS), the alwaysThinkingEnabled setting and MAX_THINKING_TOKENS=0 have no effect there, and the effort level is the only control. Those switches still work on older models selected by full id.

What it costs

Thinking tokens are billed as output tokens, and you are charged for all of them even when the text is collapsed, summarised or not returned at all. Output is the expensive side: five times the input price on every current model. So a higher effort level costs twice over, in more thinking per step and in more steps, since the agent checks more edge cases and makes more tool calls.

The effort lab measures this on one small reasoning question on Haiku 5.5: 341 output tokens at low, 424 at medium, 390 at high and 798 at max, with the same correct answer every time. Over 90 percent of those output tokens were thinking; the JSON result reports them as usage.output_tokens_details.thinking_tokens. Two readings follow. The levels are a tendency, not a ladder with fixed steps (high came in under medium in that run). And on a question the model already gets right, more effort buys only a longer wait.

On an API key that difference is money per token. On a subscription the same tokens draw down the 5-hour window and the weekly limits, and the dollar figure in a result is a list-price estimate, not a charge. Either way the docs' advice is the same: leave the default alone until a task costs more than it should or comes back wrong for lack of care, then move one level for that kind of task.

Raise effort when being wrong is expensive and the mistakes are the easy-to-overlook kind. Lower it when you are steering every step anyway.

What Claude Code does with git by default

These points come from the docs and from the commit lab; the habits after them are plain engineering sense and are labelled so.

  • When a conversation starts, Claude Code gives the model a git status snapshot (current branch, main branch, git status output, recent commits) and built-in instructions for writing commits and pull requests. The setting includeGitInstructions: false leaves both out.
  • Commits the agent makes get a Co-Authored-By trailer naming the model, with a noreply address. The attribution setting changes or removes it (attribution.commit, attribution.pr, or false for none). Your own instruction about attribution in CLAUDE.md takes precedence unless the line is set in managed settings.
  • You can ask for a pull request directly ("create a pr for my changes"). When the agent creates it with gh pr create, the session is linked to the pull request and claude --from-pr <number> finds it again. The docs' own tip: review the generated pull request before submitting it.
  • /diff shows the working tree's changes inside the session, including the agent's edits so far.
  • In auto mode the classifier blocks, by default, a force push, commands it presumes discard uncommitted work (git reset --hard, git checkout -- ., git restore ., git clean -fd, dropping a stash) and git commit --amend on a commit the session did not create. That is a model's judgment, applied after your own rules.
  • In a claude -p run with no permission mode set, anything that would need approval is denied unless an allow rule covers it. In the commit lab an allowlist of git add and git commit let the agent commit, and a request to push came back in the result's permission_denials without having run.

Habits (engineering sense)

HabitWhy it pays with an agent
Start every task from a clean treegit diff then shows exactly what the session did, and git can undo what rewind cannot
One small commit per verified stepA bad step is one revert, not an afternoon of untangling. An agent produces changes faster than you can review a large one
Read the diff before every commitThe summary the agent gives is its account of the work; the diff is the work. Look for files you did not expect
Let the agent write the message, then read itIt has the whole change in context and writes a fair first draft. A message that claims more than the diff shows is a finding
Work on a branch or worktree, merge by pull requestThe last word belongs to branch protection and a person approving the merge, not to the agent's summary
Commit before a risky promptThe cheapest checkpoint there is, and it covers shell side effects on tracked files

What it should never do unasked

The docs draw the line with a table of who has the last word: the agent's summary of what it did on one side, branch protection and a person who approves the merge on the other. Turn that into rules the harness enforces. Saying "don't push until I've reviewed" in the conversation does register with the auto mode classifier, but the docs warn it is still a model reading a transcript and the sentence can be lost when the conversation compacts.

ActionStanceControl
git add, git commit on a work branchAllowAllow rule, or the allowlist of a headless run
git pushAsk"ask": ["Bash(git push *)"] in .claude/settings.json, the docs' own example
Force push, rewriting published history, deleting branchesDenyA deny rule; deny rules hold in every permission mode
Merge to the main branch, release, deployHuman onlyBranch protection on the server, where no local setting can reach
On Windows the shell tool may be PowerShell, not Bash. A rule written only as Bash(git push *) does not match a push sent through the PowerShell tool. Write both: Bash(git push *) and PowerShell(git push *).

The Security module covers permission rules and the sandbox in depth, and the Hooks module shows how to turn "never" into a guard that cannot be argued with.

Self-check

Which commit did the two worktree branches start from? Your local HEAD, because this repository has no remote. With a remote, the default base is the remote's default branch, so unpushed commits would be missing unless worktree.baseRef is "head".

Did either session touch the main checkout? No. Each ran with its worktree as its working directory; main's motd.txt and status were unchanged until you merged.

Who resolved the conflict? You did. Worktrees stop sessions from colliding while they work, not when their branches meet. Splitting work so two sessions do not rewrite the same lines is still your job.

Why were the worktrees locked? Claude Code locks a worktree when it creates it. An interactive session releases it on exit; a -p run has no exit prompt, so the lock stays until you unlock it or a later session's sweep does.

Self-check

Did more effort change the answer? No. The question is within reach at every level, so the extra thinking bought only a longer wait. That is the docs' warning about max on ordinary tasks, in miniature.

Is low, medium, high a strict ladder? No. In the verified run high used fewer output tokens than medium. Effort is a behavioural signal and single runs are noisy; the Evals and A/B testing module shows how to compare settings with repeats.

Why does total_cost_usd not follow the output tokens? On a prompt this small the system prompt and tool definitions dominate. A run that has to write them to the cache costs three to four times one that reads them, whatever the effort level. Compare output tokens, or compare warm runs only.

What would a ratio of 2.3 mean on a real task? More than 2.3 times the output bill, because at higher effort the agent also makes more tool calls and each one is another request. On an API key that is money at the output rate; on a subscription it is a faster-draining window.
